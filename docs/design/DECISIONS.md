# VibeLang decision log

Working log, 2026-10-16. The spec (`src/`), the prototypes, and the end-user docs follow this file. Evidence paths are relative to the repository root.

## Declarations: TypeScript syntax only

**D1. Services are abstract classes**. The `service` keyword is removed.

```ts
abstract class Users {
  abstract find(id: string): Effect<User, UserNotFound, never>
  abstract rename(id: string, name: string): Effect<void, UserNotFound, never>

  static readonly layer = Layer.effect(Users, () => {
    const db = Database()
    return { find(id) { … }, rename(id, name) { … } }
  })
}
```

- A class declared in a `.vibe` file is a service when it is `abstract`, has no `extends` clause or type parameters, and every instance member is abstract (methods with full contracts, `abstract readonly` values). Static members are allowed and stay on the class, matching Effect 4's `static readonly layer` idiom.
- The compiler makes service classes nominal: plain abstract classes with the same members collapse structurally, so providing one service type-checks as providing another, and the program dies at run time with `Service not found` (`experiments/tests/service-identity/probe.ts`).
- The key is derived from package, module path, and class name, and duplicates are rejected program-wide (unchanged from the earlier `service` rule).
- Emit: an Effect 4 `Context.Service` class, so TypeScript code sees an ordinary service. (Superseded by D45: the class form breaks `implements`; the emission is an interface plus a key class.)
- Implement a service with an object literal or a class that `implements Users`. `extends Users`, `new Users()`, `instanceof Users`, and a generic service class are errors with fixes.
- Evidence that this reuses no valid TypeScript meaning: `Users.find(id)` on an abstract member is TS2339 and `Users()` is TS2348 today. Evidence that it rarely collides with ordinary inheritance: Smithers has no abstract classes in 4,461 files; opencode has 5 in 3,235, and its only fully abstract one extends another class.

**D2. Control operations are abstract classes that extend the global `Control`**. The `control` keyword is removed.

```ts
abstract class Approval extends Control {
  abstract approve(request: string): Effect<boolean, ReviewBusy, never>
}
```

**D3. Errors use the global `TaggedError`**. `class UserNotFound extends TaggedError("UserNotFound")<{ readonly id: string }> {}` is exactly Effect's `Data.TaggedError`. Errors that must be serialized use `Schema.TaggedError`, which real code already prefers (312 `Schema.TaggedError` to 133 `Data.TaggedError`). Deriving the tag from the class name is a later proposal, not v0.

**D4. The prelude**. In scope in every `.vibe` file without an import: `Effect` (namespace and the `Effect<A, E, R>` type), `Schema`, `Layer`, `TaggedError`, `Control`, and the built-ins `pipe`, `wire`, `fork`, `handle`, `resume`, `resumeWith`, `abandon`. Everything else is imported from `effect`. Measured: `Effect` is imported by 77-81% of Effect files, `Schema` by 39-44%, `Layer` by 34-44%, and nothing else by more than 22%. `Context` is not needed once services are classes; `Option` and `Array` would shadow JavaScript names. 2026-10-24 (real-world migration): the program loads effect's declarations for a `.vibe` file with a function that compiles to an Effect though it names neither the prelude nor effect's root: one that throws, a producer, or one that declares `using`. Before, such a function had its plain type, and its declaration said so, while its JavaScript returned an Effect: `export const make = (name: string) => { if (name === "") throw new TypeError("empty"); return { name } }` was declared `(name: string) => { name: string }`. Where effect does not resolve at all, each function that is an Effect by what it does is EK1011; a plain function keeps its plain behavior and is not reported. Case `effect-loaded-by-throw`; Go test `TestMissingEffectReportsEffectFunctions`. 2026-10-25 (real-world migration): a call of a built-in whose failures are expected (D101), `JSON.parse`, `decodeURI` or `decodeURIComponent`, loads effect too. Before, `export const line = (asked: string) => JSON.parse(asked)` in a file with no other Effect operation was declared `(asked: string) => any` while its JavaScript returned an Effect that fails with SyntaxError, and since EK1011 it was that error, which said to install an effect that was installed. Case `effect-loaded-by-parse`.

## Code that is not Effect

**D5. Calls to non-Effect code need a declared trust level**.

| Callee | Rule |
| --- | --- |
| A function returning `Effect` (VibeLang or TypeScript) | Calls run it (unchanged) |
| JavaScript language built-ins: `String`, `Array`, `Math`, `JSON`, `Number`, `Object`, `Map`, `Set`, `RegExp`, deterministic `Date` parsing | Trusted contracts shipped with the compiler give each one a control class (`pure` or `sync`) and say which exceptions are expected failures (for example `JSON.parse` fails with `SyntaxError`) and which are defects |
| Platform APIs: `node:*` modules and browser globals such as `fetch`, `setTimeout`, `process`, `localStorage` | Not callable from `.vibe` files (EK4402); the error names the Effect module to use (D6) |
| Clock and randomness reads: `Date.now()`, `new Date()`, `Math.random()`, `crypto.randomUUID()` | Use `Clock`, `DateTime`, and `Random` so tests control them (EK4403) |
| Any other plain TypeScript or JavaScript function | Needs an explicit boundary: `Effect.try` or `Effect.tryPromise`, or a trusted contract declared once for that function. A bare call is an error (EK4401) whose fix offers both |

Pure helpers written in `.vibe` get inferred contracts and compile to plain JavaScript (D10), so most project code never needs a boundary.

**D6. The standard library is Effect's**. VibeLang adds no Node.js clones. Mapping: files → `FileSystem`; paths → `Path`; HTTP → `HttpClient` and `HttpApi`; child processes → `effect/process`; timers → `Effect.sleep` and `Schedule`; environment → `Config`; console → `Console` and `Effect.log`; time → `Clock` and `DateTime`; randomness → `Random`; crypto → `Crypto`; sockets → `effect/socket`; workers → `effect/workers`; terminal → `effect/cli` and `Terminal`; storage → `KeyValueStore`; SQL → `effect/sql`. Runtimes come from `@effect/platform-node`, `-bun`, and `-browser`.

## Calls, programs, and pipelines

**D7. Program values are functions with no arguments**.

**D8. No `|>` in v0; keep the `pipe(program, …stages)` built-in** (amended by D110; superseded by D154). TC39's pipeline operator collides with "calls run": in `f(x) |> Effect.retry(%, p)` the call runs before the pipe sees it, and every stage that calls a combinator would run too. The pipe census shows the payoff is small: outside tests, 1.1% and 2.6% (opencode) of Effect pipes keep two or more stages once statements replace `map`, `flatMap`, `catch`, and `ensuring` (`docs/research/pipe-census.md`). Revisit if the TC39 proposal reaches Stage 3.

**D9. A function value passed where a plain JavaScript function is expected** (amended by D66, D112, D113) passes the plain-JavaScript variant if the function is eligible (D10); otherwise it is EK4301.

**D10. Plain JavaScript compilation** (amended by D65, D67). A function compiles to plain JavaScript when it performs no Effect operation (control class `pure` or `sync`, which now excludes `Effect.sync` bodies and every other Effect boundary) and its E is `never`. Generated code keeps source evaluation order. `pure` permits inlining, never removal or reordering. Pure recursion runs on the JavaScript stack, like any JavaScript function; past the host limit it is a `RangeError` defect (resolves O10). Functions that can pause use heap frames and recurse without limit.

**D11. Higher-order functions compile to frames in v0**; per-call-site specialization comes later.

**D12. A function type without a contract accepts any contract** (amended by D68) (P14 kept). It means "inferred from each call's argument", never `never`. This is a partial-annotation spelling, tracked with O7.

## Errors and cleanup

**D13. `catch` handles a failure only when the cause contains no defect and no interruption** (amended by D305 and D306); otherwise the whole cause propagates (`Effect.catch` swallows a defect from a mixed cause).

**D14. Only `using` acquisitions belong to the block.** A resource acquired without `using` belongs to the caller, even when the same block also has a `using`.

**D15. A failure during cleanup is never dropped**, including during explicit `abandon` under interruption.

## Handlers and concurrency

**D16. v0 exposes `handle`, `resume`, `resumeWith`, and `abandon`. `transfer` stays inside the standard library** (producers' external iteration, the Stream adapter) until a continuation can no longer outlive its capturing fiber. Resolves O3.

**D17. `resumeWith` runs code whose R is `never`** (an injected requirement resolves in the capture-time Context).

**D18. A clause whose last step is `resume` compiles to the kernel's tail-resume shape**, so producers run in constant stack (the generator-shaped clause leaks two frames per element).

**D19. `fork` is block-owned** (amended by D96): the child is interrupted when its block exits. `Effect.forkScoped` (adds `Scope` to R) and `Effect.forkDetach` give longer lifetimes (resolves O5).

**D20. A TypeScript function whose R contains a control operation cannot be called from VibeLang in v0** (EK4202), because it may fork internally where the handler cannot reach.

**D21. Each `Effect.provide` builds its layers once.** Provide the application layer once, at `main`; programs with several entry points use `ManagedRuntime`.

## Calls the confident spec needed (2026-10-16)

These fill gaps the decisions above left open. All are defaults; the spec's chapters cite them.

**D22. Effect's own packages are trusted**. An export of `effect` or an `@effect/*` package that does not return an `Effect` is a `sync` call whose exceptions are defects, exactly as inside `Effect.gen` today; a callback it calls synchronously follows D9. Values and functions that those exports return are trusted on the same terms: a `Brand` constructor and its methods, the function `Match.exhaustive` returns, and the stage a dual API returns when called without its data argument (amended 2026-10-16 after the docs consistency pass). Without this, D5 would demand a boundary around every `Option.map`. Evidence: D6 makes Effect the standard library; `Option` and `Result` are plain data in Effect 4 (`experiments/node_modules/effect/src/Option.ts:57`, `Result.ts:68`).

**D23. A trusted contract is a JSDoc tag on the TypeScript declaration** (amended by D100, D101, D108). `/** @vibelang trusted */` declares a synchronous function `sync`; each `@throws {T}` names an exception class that is an expected failure and joins E; any other exception is a defect. The tag cannot be put on a function that returns a Promise or an `Effect`. A function from a package you cannot edit is trusted by re-exporting it from a `.ts` file you own, with the tag. Inside the callback of an explicit boundary (`Effect.try`, `Effect.tryPromise`, `Effect.sync`, `Effect.promise`), calls to plain TypeScript are allowed; platform APIs (EK4402) and clock or randomness reads (EK4403) are not. Reasons: TypeScript syntax only, as in D1; it is the same metadata channel the compiler already writes into declarations; `@throws` is standard JSDoc.

**D24. A call runs its result only when the call's type is `Effect<A, E, R>` itself** (amended by D90, D109). A type that extends `Effect` and carries structure of its own (`Config`, `Exit`, a service class, a `TaggedError` instance) is data when a call returns it; calling such a value runs it; `new` never runs anything. Without this, `Config.String("X")` would read the variable before `Config.withDefault` could see it, and a function returning an error instance would fail. Evidence: `Config<T> extends Effect<T, ConfigError>` (`Config.ts:113`), `Exit` (`Exit.ts:89`), `Context.Key` (`Context.ts:68`), `YieldableError` (`Cause.ts:1312`). S22-3 amendment to S5-1: at an Effect return boundary, a returned value assignable to the contract's declared success type A returns as data; only a returned Effect subtype that is not assignable to A runs. A contextual A of `unknown` or `any` names no success value: in a function with no written return contract, such as an arrow given to a tsc callback typed `(n) => Effect<unknown>`, a returned subtype runs (S5-1). A contract written on the function, such as `unknown!!`, names its success value, and the subtype returns as data. 2026-10-24 (real-world migration): a call of a value of type `any` returns its value, since `any` is not Effect itself, and nothing says whether the callee returns a program. Where that value is what an Effect function or a program returns, the warning EK4409 names the call: `Effect.updateContext(() => execute(), f)` with `execute: any` lowered the program to `Effect.sync` and succeeded with the Effect `execute` returned, silently. A typed callee settles it, and a project may adjust the warning as it does EK2004 (D241). Case `any-call-program-value.fail`.

**D25. `using` adds no masking policy of its own**. An acquisition is masked or interruptible as its `Effect.acquireRelease` says: masked by default, so cancellation waits for the acquisition and then releases it; `{ interruptible: true }` for a wait on the outside world that cancellation must reach. Evidence: K15a-K15c.

Amended 2026-10-23: the guarantee covers the acquisition's own release, not the `[Symbol.dispose]()` that `using` adds (D94). An interruption that arrives while the acquisition is masked is delivered as that mask ends; when the mask ends the acquisition, as in `using r = Effect.uninterruptible(() => …)`, the value never reaches `using`, so a Disposable made there is not released (pending case `scopes-using-pending-interrupt`). Registering the release inside that mask needs `using` to mask the acquisition, as `Effect.acquireDisposable` does, which stops cancellation from reaching an interruptible acquisition such as Chapter 6's `connect`. Open.

**D26. Producers** (amended by D82) (resolves O4 and the design half of G12).
- `function*` in a `.vibe` file declares a producer; `yield` performs the built-in `Yield` operation. Generator-style Effect code (`Effect.gen`, `Option.gen`) stays in `.ts` files (EK1002).
- `for...of` is chosen by the iterated type: over a producer it installs a `Yield` handler (internal iteration); over a `Stream` it pulls with `Stream.toPull` and closes the stream when the loop exits; over any other iterable it is JavaScript's loop.
- To TypeScript, and wherever a `Stream` is expected, a producer is a `Stream`. The adapter runs the producer on its own fiber and hands over each element only when the stream pulls it, through a zero-capacity handoff (a one-element buffer would let the producer run one element ahead), so a pull from any fiber works and the producer never runs ahead; closing the stream interrupts that fiber, which runs the producer's cleanup. Reason: Stream operators such as `merge` pull on other fibers, and a continuation is fiber-affine (P5). G12 is the confirming experiment.

**D27. `wire` is a compiler intrinsic with a bounded contract** (resolves O6). It reads each argument's `Layer<Out, E, In>` type. An argument whose type does not name its outputs is EK3204; compose it with `Layer.provide`. Inputs no argument provides stay in the result's `In`, as with `Layer.provide`, and are reported with their dependency path (EK3201) where the program's R must be empty. Duplicate outputs are EK3202, cycles EK3203.

**D28. A `catch` over several expected failures receives the first**. The `catch` handles the cause as a whole, as `Effect.catch` does; `Effect.catchCause` sees every failure.

**D29. Proposals P1-P22 are the spec's rules**, as revised by the counterexamples in Chapter 29.

## Tooling (2026-10-16)

All defaults; Chapter 28 of the spec states them with examples. Package names are unscoped and follow the name (D125).

**D30. Installation.** (amended by D80, D83) Two npm packages. `vibelang` ships the fork's single native binary, `vibelang`, through per-platform optional dependencies, as `typescript@7` does. `vibelang` accepts every `tsc` flag and adds no new commands: `vibelang` type-checks and emits, `vibelang --noEmit` checks, `vibelang --watch` and `vibelang -b` rebuild, `vibelang --lsp --stdio` serves editors, and `vibelang --api` serves build tools. `vibelang-runtime` holds the kernel and the runtime helpers; generated code imports only it and `effect`. v0 supports `effect` 4.0.5 exactly (the runtime checks the version at load); the compiler is the TypeScript 7.1 checker (P16), so `.ts` files in the same program check as TypeScript 7.1 checks them; the runtime runs where `effect@4.0.5` and its platform packages run, and the evidence was gathered on Node 26.10 and Bun 1.4.1.

**D31. Build integration.** (amended by D105, D106, D107) Libraries and servers build with `vibelang` or `vibelang --watch`. Applications built with Vite use `vibelang-vite`, which compiles each requested `.vibe` module through `vibelang --api`, returns JavaScript with composed source maps, forwards diagnostics to Vite's overlay, and invalidates a module's importers for hot reload when the module's exported contracts or control classes change, because callers compile differently. Imports name source files: `.vibe` code imports `./welcome.vibe`, the emitted JavaScript imports `./welcome.js`, and TypeScript code imports `./welcome.js`, which the compiler resolves to `welcome.vibe` as it resolves `.js` to `.ts`.

**D32. The editor.** (amended by D76, D79) The language server is the fork's own: `vibelang --lsp --stdio`, from the project's `vibelang`. It serves `.vibe` and `.ts` files of the same program, so one server owns both. The VS Code extension `vibelang.vibelang` registers the `vibelang` language for `*.vibe`, starts that server, and asks VS Code's built-in TypeScript features to stand down in workspaces that contain `.vibe` files. Other editors configure their LSP client to run `vibelang --lsp --stdio` for `*.vibe` and `*.ts`. GitHub highlights `.vibe` as JavaScript unless `.gitattributes` says `*.vibe linguist-language=TypeScript`.

**D33. v0 editor features.** (amended by D77, D78) Hover shows a function's inferred contract and control class and, at a call, the success value. Completions add service members, prelude names, and `catch` narrowing by error class. Quick fixes exist for every EK diagnostic that has a mechanical fix (Chapter 28 lists them). Refactors: convert an `Effect.gen` or `Effect.fn` function into a VibeLang function, convert a `Context.Service` class into an abstract service class, implement a service (scaffold an object literal or an `implements` class), and write the inferred contract as an annotation.

**D34. Diagnostics configuration.** (amended by D61, D104) A `compilerOptions.vibelang` block in `tsconfig.json`. Every EK diagnostic is an error and cannot be lowered, because each marks code with no meaning or code that would compile unsoundly, with two exceptions that are policy, not soundness (amended after the prototype): EK2004 (an Effect try block with E = `never`; D260) is a warning by default, and EK4403 (a clock or randomness read) is an error by default; a project may set either to `"error"`, `"warning"`, or `"off"`, and an EK4403 read then compiles as a trusted `sync` call. The block also holds `"tracing": "none" | "exported" | "all"`, which compiles the chosen functions with `Effect.fn` spans. `vibelang` exits non-zero on any error; diagnostics print at `.vibe` spans.

**D35. One owner per diagnostic.** The compiler owns every type and language diagnostic for `.vibe` and `.ts` files in the program, in the terminal, the editor, and the Vite overlay. Oxlint owns lint: it parses `.vibe` as TypeScript (VibeLang adds no syntax) and runs only syntactic rules there; its type-aware mode (tsgolint) skips `.vibe` files, because tsgolint embeds TypeScript's checker and would analyze the wrong semantics. `vibelang-oxlint-config` sets that override and turns off syntactic rules whose premise VibeLang changes, such as `require-yield`. Vite Plus runs the two through the same pieces, the Vite plugin and the Oxlint config, so no rule has two owners and nothing needs deduplication.

**D36. Debugging.** (amended by D104) `vibelang` and the Vite plugin write source maps composed from `.vibe` through generated TypeScript to JavaScript, so any debugger that reads standard source maps (VS Code's JavaScript debugger for Node.js, Bun, and Chrome targets; Chrome and Edge DevTools; JetBrains IDEs) maps breakpoints and paused frames to `.vibe` lines. Compiled functions, clauses, and producers are generator functions named after their source; region closures are named `<function>$try`, `$catch`, `$finally`, and `$using`. A JavaScript debugger shows only the active JavaScript frames: a continuation held by a clause is a heap value, so a breakpoint in a clause shows the clause, and the body's frames reappear when it resumes. Logical stacks across suspensions come from spans (`tracing`) and Effect's span-based devtools. Amended 2026-10-24 (coverage): code the compiler makes, which no source code stands for, maps to no source position, so V8 coverage (`@vitest/coverage-v8`, `c8`, `NODE_V8_COVERAGE`) counts the code its author wrote. A thunk for a call passed by name (D147), the operands of a catch expression (D236), the function of a throw or do expression (D186, D187), a region's closure, a handle clause's generator, and a block param's or match expression's function start with a source map segment that has no source; ast-v8-to-istanbul and v8-to-istanbul skip a function whose start maps to none. A source function lowered to two functions keeps its position on the one its callers call: an Effect function declaration's forwarding declaration (its generator maps to none), a function or method that returns a direct Effect (D274; its thunk maps to none, and an arrow's concise body maps where the thunk's value does), a method's generator, and a plain function's `$direct` variant (its Effect wrapper maps to none). Coverage tools count an arrow's concise body as a statement, so a thunk whose value runs whenever the code around it runs is `() => { return value; }` with a return that maps to none: a call passed by name, `Effect.suspend(() => { return fetchReport(); })`, a catch expression's left side, and the thunk of an arrow's single-result body, whose concise body stands for it. A value that runs only sometimes keeps a concise thunk and counts as a statement, as the arrow it abbreviates does in Effect TypeScript: a catch expression's fallback, a throw expression, a for concurrent loop's body. Composing maps, as Vite does, drops a segment with no source that starts a line or follows another (`@jridgewell/remapping`), and the tools then read the next segment, so the positions just before and after one map to the last source position again. Stack frames and breakpoints keep their positions: every source expression inside such code keeps its mapping. Rejected: emitting fewer closures, which changes when a by-name expression is evaluated and the run-loop operations D274 measured; and `/* v8 ignore */` hints on compiler-made functions, which would hide the source code inside a thunk and which `c8` reads only from source lines. Evidence: five `.vibe` modules beside the Effect TypeScript an author would write, run by the same tests under `@vitest/coverage-v8` 5.0.5, reported 25 uncovered functions and 33 uncovered statements against the TypeScript's 12 and 22 (a catch expression's unused handler cost four functions, an uncalled arrow three); now 10 and 21, with the same branches, and exactly one function for each source function. Under `c8`, case `coverage-generated-functions` reports 17 functions where it reported 29, and 21 branches where it reported 43. Tests: `packages/vite/test/coverage.test.mjs` and case `coverage-generated-functions` (V8's own counts, mapped through the emitted source map).

## Gaps from the feature-coverage audit (2026-10-16)

`docs/research/effect-feature-coverage.md` left these open after D22-D36. All defaults.

**D37. Effect `catch` never sees an exception no contract lists** (resolves X2; amended by D260). Inside `Effect.gen`, a JavaScript `catch` sees any synchronous exception. In an Effect region, `catch` handles expected failures only (D13), so an exception no contract lists, such as one from `Option.getOrThrow`, `Schema.decodeUnknownSync`, or a trusted function's unlisted exception, is a defect it does not see. This difference is intended: those are Effect's "cannot fail here" forms, and each has a typed form for code that can fail (`Option.getOrElse`, `Effect.fromOption`, `Schema.decodeUnknownEffect`). A `try` block that runs Effects with E = `never` lets defects pass through its `catch`; this is EK2004, a warning by default (D34), with the typed forms and `Effect.try` as fixes. Evidence: Effect.gen's behavior verified on 4.0.5 in the audit; 487 Smithers and 70 opencode files mix JavaScript `try` with `Effect.gen`.

**D38. Runners** (resolves X4). The compiler knows runners by resolved symbol: `Effect.runPromise`, `runPromiseExit`, `runSync`, `runSyncExit`, `runFork`, `runCallback` and their `*With` forms; `ManagedRuntime`'s `run*` methods; `NodeRuntime.runMain` and `BunRuntime.runMain`; and `@effect/vitest`'s `it.effect`, `it.live`, their `.each` and `.prop` forms, and `layer(…)`. A runner may be called where no fiber runs the code: at a module's top level, and in a plain callback passed from such a place to a TypeScript function (a `describe` body, a framework's route handler). Anywhere else it is EK1005, because it would start a root with an empty Context and no handlers, outside the caller's structured concurrency; call the program or `fork` it. Tests in `.vibe` use `it.effect`; Promise-style tests stay in `.ts`.

**D39. A parameter that accepts a function or an `Effect`** (resolves X9). A function argument with parameters is passed as a function. A function argument without parameters is passed as a function when it compiles to plain JavaScript, and is converted to a program when it can pause; the overload or union member that accepts that form is selected. Effect APIs that decide at run time with `Effect.isEffect` (`HttpRouter.add`, `RpcGroup.toLayer`, `Effect.withErrorReporting`) then see the form the compiler chose.

**D40. Effect 4 service features on abstract-class services** (resolves X12). Static members stay on the emitted class: `static readonly layer` holds the default Layer, and a static `make` method plays the part of Effect 4's `make` option (`Layer.effect(Users, () => Users.make())`). A service class that declares `static readonly default`, a value of the service's own type, compiles to a `Context.Reference` whose `defaultValue` returns it, so using it adds nothing to R. Effect's own `Context.Reference(key, { defaultValue })` works unchanged, because a call that returns a key is data (D24).

**D41. Members of a service** (amended by D90) (resolves X13). `S.member(args)` looks the service up, so `S` joins R whatever the member returns, and then applies the call rule to the member: an `Effect` runs; a plain value is returned through a trusted call when the service comes from Effect's packages (D22) or the member carries `@vibelang trusted`, and is EK4401 otherwise. A member that is an `Effect` value runs when called: `Terminal.readLine()` lowers to `yield* (yield* Terminal).readLine`, a row of its own in the call table. Value members are read from the implementation: `Settings().baseUrl`. A member the service declares wins over the key's own members (`pipe`, `key`, `of`, `use`, and, because the key is a class, `name`, `length`, `call`, `apply`, `bind`), so `Rpc.call(…)` reaches the service; a static member with the same name as a service member is EK3006.

**D42. Workflow bodies are ordinary programs** (resolves X17). Effect's workflow engine runs a body on a forked child (`workflow/Workflow.ts:695-780`) and suspends it durably by interrupting that fiber (`Workflow.ts:1031-1036`); every execution, first or replay, reruns the body from the start. A body written in VibeLang therefore behaves as any interrupted and rerun program: held continuations are abandoned through their owners and finalizers run (T4), each execution captures fresh continuations (T11), and no producer position or handler state survives into the next execution. Side effects belong in activities, as in Effect. A handler installed outside `Workflow.execute` cannot reach a control operation inside the body, which runs on another fiber (EK4201 applies). Confirming experiment: G18.

**D43. `Effect.callback` is an explicit boundary** (narrows X11). Its register function may call plain TypeScript, as the D23 boundaries may, and its `resume` takes an `Effect<A, E, R>` (`Effect.ts`). `.vibe` code passes an `Exit`, `resume(Exit.succeed(value))`: an `Exit` is an Effect, and a call returns it as data (D24), whereas `Effect.succeed(value)` would run where it is written. Platform APIs stay behind Effect modules (EK4402), and an adapter for a resource uses the runtime's `suspend` in TypeScript, which reports a lost race (Chapter 6).

## Defaults from the prototype compiler (2026-10-16)

`prototype/esc/FINDINGS.md`: a prototype compiler on `typescript@5.9.3` and `effect@4.0.5` compiles 46 example files written from the spec (26 run, 20 fail with their expected codes) and matches 25 of the spec's 28 claimed contracts. These defaults settle what it found underspecified.

**D44. "The expected type" is the declared, uninstantiated parameter type of the resolved overload**. TypeScript's instantiated contextual type is circular: in `ids.map((id) => Users.find(id))`, `U` is inferred from the lambda itself. If overload resolution fails, the candidates whose arity fits are used. The instantiated type is used only when the declared type is a bare type parameter fixed by another argument, such as `Layer.succeed`'s `NoInfer<S>`. 2026-10-24 (real-world migration): where the declared type says nothing, a contextual type that is the lambda's own type, which a type parameter that the lambda fixed has after inference, as in `check(() => make())` with `check<T>(actual: T)`, is dropped: it says nothing about the lambda's form, and reading its return type re-entered the lambda's own (TS7024). Case `lambda-own-contextual-type`.

**D45. A service compiles to an interface plus a key class** (supersedes D1's emit clause). Effect's `Context.Service` class form makes the instance type the identifier, so `class UsersFake implements Users` is TS2720 and a parameter typed `db: Users` means the identifier. The emission that works is an interface for the shape, with an optional brand `readonly "~vibelang/service"?: "<key>"`, merged with a class whose static side is a `Context.Key` (`prototype/esc/scratch/probe2.ts`): R stays nominal, `implements` works, and a parameter typed with the service means its methods. Control operations and services with a default emit the same way from the runtime's `controlKey` and `referenceKey`.

**D46. Failure lowering** (findings 11, 12, 14). `finally` lowers to `Effect.onExit`, because `Effect.ensuring` requires a cleanup whose E is `never`, and D15 lets cleanup fail. `throw e` lowers to `return yield* Effect.fail(e)`, so narrowing after the `throw` is kept. E is defined as the type of the expected failures in causes made only of expected failures: a cause that also holds a defect or an interruption may carry `Fail` reasons outside E, which no VibeLang `catch` recovers (K14).

**D47. A block is a Scope region when it declares `using` or calls `fork`**, even with no `using`; without this rule a fork-only block found no `Scope`.

**D48. `Scope` joins the prelude**. In Effect 4, `Scope` is a module, and the type is `Scope.Scope`; contracts name it constantly. The prelude's `Scope` is the module, and the type `Scope` means `Scope.Scope`, as `Effect` does for `Effect.Effect`.

**D49. Collections of programs convert** (amended by D69, D111). An iterable or record of functions without parameters converts to Effects where an iterable or record of Effects is expected, so `Effect.all(stores.map(makeSync), { concurrency: 4 })` type-checks and runs.

**D50. `Continuation<V, E, H>`**. V is what the perform site receives, E the operation's declared errors (what `resumeWith` may raise), and H the result type of the enclosing `handle`. Under a deep handler, `resume(k, v)` returns H: the resumed program runs until it reaches the reinstalled prompt, where `onReturn`, or a later clause that does not resume, produces the value. The checker computes H as the least type containing `onReturn`'s result (the program's A without one) and every clause's return type, taking each `resume`'s type as H.

**D51. Foreign calls at a module's top level, and `@throws`** (amended by D100, D101). EK4401 applies inside functions only: a module's top level runs outside every program, where `Effect.try` would be EK1001, so a plain call there is an ordinary JavaScript call and an exception fails the module's import, as in TypeScript. Each `@throws {T}` names an exported class, and the generated code tests `instanceof T`.

**D52. Inference details** (amended by D71, D72, D73) (findings 7, 10, 13). E and R of a recursive function come from a fixpoint over its strongly connected component of the call graph; when A depends on the recursive result, the contract must be written (EK2102). The iteration stays inside the component (amended 2026-10-16 after the single-pass experiment): the checker checks the component's bodies, then rechecks only those bodies, with the E and R found so far as the members' contracts, until E and R stop growing. The rows are finite and each step only adds to them, a `catch` that removes a fixed set of failures included, so the iteration ends. No function outside the component is rechecked, and no lowering decision waits for it. The probe `isEven`/`isOdd`, whose cycle carries `Odd`, needs it: one pass without it gives `isEven` an E of `never`. A is widened as TypeScript widens a function's inferred return type. Definite assignment is checked on the source, before lowering, because region closures defeat TypeScript's own analysis.

**D53. Diagnostic codes follow the prototype.** (amended by D67, D70, D71, D74) EK1003 is `async` or `await`, EK1004 is `using` at a module's top level, EK1005 is a runner inside code a fiber runs (D38), EK2003 is a return annotation that is not a full `Effect<A, E, R>` (until O7), EK2004 marks an Effect try block with E = `never` (D260), EK2005 is a `resumeWith` program outside the operation's contract (D17), EK2102 is a recursive A that needs a contract, and EK3001-EK3006 are a duplicate key, `extends`, `new`, `instanceof`, a generic service, and a static that shares a service member's name. Chapter 28 lists every code.

**D54. Regions inside a plain-JavaScript function** (completes D10 with D5; amended by D260 and D282). A function that compiles to plain JavaScript may contain `try`, `catch`, and `finally`, and they compile to JavaScript's own statements, because nothing inside can pause or be interrupted. The catch receives every JavaScript exception as `unknown` (D260); defects are classified only when an exception escapes into an Effect caller. A function that declares `using` compiles to frames. Amended 2026-10-23 (release correction): D282 supersedes the catch described here. A plain function's `throw` is a typed failure, and its catch receives the typed failures its try block raises; every other exception passes through it.

## Defaults from the single-pass experiment (2026-10-16)

`prototype/single-pass/RESULTS.md`: TypeScript 5.9.3, patched to classify each lambda per overload candidate inside `chooseOverload`, reaches the prototype's final lowering for all 46 example files with one check per file: 817 call sites, 257 lambdas and methods, 0 disagreements, and byte-identical output, in 46 checks instead of 124. Two synthetic probe files produce 17 disagreements: 16 that follow from 6 lambdas with two self-consistent lowerings, where the prototype keeps the one its first guess reaches, and 1 from mutual recursion, settled by D52's amendment.

**D55. A method that implements a plain-function member** (amended by D67, D74) (2026-10-16). When a class in a `.vibe` file implements an interface member whose declared type is a plain function, such as `Equal.Equal`'s `[Equal.symbol](that): boolean` or `Hash.Hash`'s `[Hash.symbol](): number`, the method compiles to a plain JavaScript method if it is eligible under D10; otherwise it is EK4301. VibeLang callers call it as a plain method, because its declared type is not an Effect. A method that implements a service member, whose declared type returns an Effect, compiles to an Effect function as before.

**D56. A lambda's form is decided against each overload candidate**. A lambda passed as an argument compiles in one of three forms: a plain function, an Effect function, or a program (D7). While TypeScript checks the arguments against a candidate, the lambda takes the form that candidate's declared parameter type asks for (D44), and the candidate that TypeScript's first-applicable rule selects decides the form: with overloads, the first candidate that accepts the lambda in the form that candidate expects wins. The lambda's own inferred type never decides its form; the prototype's two answers came from letting it. A lambda with no expected type, such as a returned lambda or an argument for a bare type parameter that no other argument fixes, is plain when D10 allows and an Effect function otherwise; D8's look-ahead for `pipe` stays. Each lambda is checked at most once per form, and its first classification against a candidate stands, so a deferred re-check never reclassifies it. The call rule applies to the call node itself, so a type guard still narrows (`Exit.isFailure(x) ? x.cause : …`), and a call to a D10 function from plain code has the plain variant's type. D10 eligibility is computed on demand, when a caller's typing needs it, as a greatest fixpoint over the callee's strongly connected component: the component compiles to plain JavaScript when each member would with the calls inside the component counted as plain.

## Calls made for the end-to-end build (2026-10-16)

These decisions close the open design questions.

**D57. Partial annotations use `infer`** (amended by D67, D74, D93, D127, D308, D309) (resolves O7). In the return annotation of a function with a body, a channel written `infer` followed by any name is inferred; every other channel is checked.

```ts
function find(id: string): Effect<User, infer E, never> { … }       // checks A and R, infers E
function load(id: string): Effect<User, never, infer R> { … }       // promises no failures, infers R
function plan(id: string): Effect<infer A, PlanError, Database> { … }
```

- Leaving a channel out is EK2003 in that position, never a silent `never` and never a silent inference: `Effect<User>` there asks "did you mean `never` or inferred?", and both fixes are offered (`Effect<User, never, never>` and `Effect<User, infer E, infer R>`). Everywhere else (parameter types, aliases, abstract members, `.ts` files), `Effect<User>` keeps its TypeScript meaning, defaults included.
- The name after `infer` is documentation only and is not in scope anywhere. `infer _` is allowed.
- Why `infer`: it is TypeScript syntax that the TypeScript 7 parser already accepts in that position (verified on the fork, 2026-10-16), and its existing meaning, "let the compiler find this type", is the meaning here. The alternatives fail: `?` does not parse in TypeScript 7 (TS1110), `_` is an ordinary type name a program may declare, and omission is the silent confusion settled decision 2 forbids.
- D12 stands: a function type without a contract accepts any contract.

**D58. The name stays EffectScript** (resolves O9; superseded by D125). The binary was `esc`, the extension `.es`, and the npm scope `@effectscript`; the repository is `github.com/roninjin10/effectscript`, private. An unrelated compile-to-JavaScript language uses the name at `github.com/EffectScript/effectscript`.

**D59. Upstream issues are drafted, not filed** (resolves O8). Upstream issue drafts live in `docs/upstream/`; filing in a third-party project requires maintainer approval.

**D60. One private repository, `github.com/roninjin10/effectscript`**. The compiler is microsoft/TypeScript's tree in `typescript/`, imported in one commit without its 349 MB of test baselines, with the VibeLang compiler commits on top; the spec, docs, runtime, and tools live beside it, so one commit can change the compiler, the runtime, and the docs together.

## Decisions from the end-to-end build (2026-10-16)

These entries record implementation decisions. The known gaps distinguish implementation snapshots from subsequent fixes.

**D61. EK diagnostics use the TypeScript transport**. An EK diagnostic is a TypeScript diagnostic with source `EK`, on upstream's content-mapper path. The CLI prints `error EK1003:`; the language server sends `{source: "ES", code: 1003}`, which VS Code shows as `EK(1003)`. `@ts-ignore` and `@ts-expect-error` do not apply to EK diagnostics. An EK diagnostic can hide the TypeScript errors it explains. Bad values in `compilerOptions.vibelang` use TypeScript's own option codes (TS5023, TS6046, TS5024). Design tradeoff: editors show `EK(1003)`, not `EK1003`. The CLI and editor share one diagnostic path.

**D62. The runtime exports define the prelude**. A `.vibe` file loads the runtime only when it uses a prelude name it does not declare at top level, so files without prelude names compile as plain TypeScript. Prelude names resolve after every scope and before globals. Emitted JavaScript imports `Effect`, `Layer`, `Schema`, and `Scope` as `import * as X from "effect/X"` and the rest as named imports from `vibelang-runtime`; `.d.ts` files use `import type`.

**D63. Local imports name source files**. A `.vibe` file imports `./x.vibe` or `./x.ts` by source name with no flag (no TS5097); specifiers become `.js` in JavaScript and `.d.ts` output. `./x.js` probes `.vibe` after `.ts` and `.tsx`, so `.ts` wins when both exist; `./x.vibe` falls back to `x.d.ts`.

**D64. Acceptance cases compare diagnostic sets and result lines**. A failing compiler case passes when its exact set of error codes matches (TypeScript codes count, warnings do not), which catches regressions; a runnable case compares only its `@@result` line, so programs may log. EK1002 is defined by type: a `function*` passed where the parameter's type returns a lib `Generator` or `Iterator`. EK1004 also covers class static blocks.

**D65. Plain VibeLang calls run inline everywhere**. A call from a `.vibe` file to a plain function runs inline as `f$direct(a)` everywhere, including a module's top level, because it computes a value and runs no program.

2026-10-21 implementation note: default imports use the same plain path with or without named or namespace bindings, including an empty named list, `default as` imports and re-exported defaults. The `plain-default-import-shapes` acceptance case checks their success values at runtime.

2026-10-23 implementation note: in a file emitted as CommonJS, a call reaches an imported variant through the module its import requires, `(0, math_1.double$direct)(n)`, and a local export list defines its variants on `exports`, because TypeScript's CommonJS transform finds names through the checker and cannot see the variants import or export an ES module gets. Each exported variant is exported and hoisted like its Effect form. Before, the call ran the Effect form and returned an Effect value, and `f$direct` was never exported. The `plain-import-shapes-cjs` acceptance case checks every import shape, a tagged template, a function value and an export list before its import at runtime.

2026-10-23 implementation note: `export default double`, where `double` is a plain function, local, imported or a namespace member, also exports its variant, `export const default$direct = double$direct`, as `export default function` does. Before, a default import of such a module called `default$direct`, which the module never exported: an ES module failed to load and CommonJS threw. The `plain-export-default-assign` acceptance case and its CommonJS twin check it.

**D66. Plain overloads reject suspending function values**. An overload candidate that asks for a plain function rejects a `.vibe` function value that can pause, as it rejects such a lambda (D56 extended to function values); a TypeScript function that returns an Effect passes as data; when every candidate rejects, EK4301 reports against the first candidate's form.

**D67. Plain return annotations preserve plain function types**. A function with a plain return annotation keeps that type and compiles to one plain function; only unannotated or Effect-contract functions get the `$direct` plus `Effect.sync` pair, whose TypeScript type is `(…) => Effect<A, never, never>` (chapter 15's one calling convention). Design tradeoff: it interacts with EK2003, D55 methods need the annotation, and editors show plain helpers with an Effect type unless hover says otherwise. An explicit plain type supports JavaScript protocols and avoids an unwanted Effect wrapper. 2026-10-24 (real-world migration): a lambda with a return annotation whose body calls the variable whose initializer holds it, as in `const Recursive = Flow.make(…, { body: (p): Node<number> => Recursive.call(p) })`, takes its annotation's form before its body is read: TypeScript types that body only once the variable has a type, and reading it sooner reported TS7022. The deferred check still reports a body that cannot be plain (EK2003). Case `annotated-lambda-reads-its-variable`.

**D68. Contract-less callback parameters carry E and R**. D12 (a callback parameter without a contract accepts any contract) applies to declarations, methods, and function expressions that are not call arguments; the added type parameters are named E and R (then E2, R2) and appear in `.d.ts` output. Design tradeoff: a contract-less callback cannot be called inside a synchronous JavaScript callback such as a `sort` comparator (EK4301). D12 needs effect-polymorphic declarations without treating missing channels as never. 2026-10-24 (real-world migration): an optional call of such a callback, `f?.(x)`, runs the callback when it is present, as `f(x)` does, and its E and R reach the function's contract (EK2001, EK2002). Before, the optional call's signature read its return type again from the annotation and lost the Effect the parameter's type gave it, so the call returned the callback's program unrun, with no diagnostic. The added E and R default to `never`, in the checker and in `.d.ts` output (`<E = never, R = never>`): a call that omits an optional callback adds no failure and needs nothing, where both were `unknown`. Cases `optional-callback-runs`, `optional-callback-contract.fail`.

**D69. Programs lower according to their source form**. A program lambda lowers to `Effect.gen(function* …)`, a converted function value to `Effect.suspend(v)`, and an array or record of programs built at run time to `$programs`. Each conversion preserves cold execution and the collection shape.

**D70. Jumps cannot leave a finally block**. A `return`, `break`, or `continue` that leaves a `finally` block is a new error, EK2006; in JavaScript such a jump discards the failure in flight, and compiling `finally` to Effect cleanup cannot honor it. Added to chapters 17 and 28. **controversial**.

**D71. Recursive catch and return types can require a contract**. EK2102 also covers a `catch` variable or return type typed before its cycle's E and R are known; the fix is a written contract. The checker cannot revise a type already cached before the recursive channels are known.

**D72. Pure recursion keeps TypeScript diagnostics**. EK2102 applies only to functions that run Effects; a pure recursive function keeps TypeScript's TS7023, which a plain annotation fixes (consistent with D67). Only functions that run Effects need VibeLang recursive-channel inference.

**D73. Calls use the written contract**. A call to a function with a complete written contract adds the contract's E and R, not what its body does. A caller must rely on the public contract rather than a narrower implementation.

**D74. Methods allow plain annotations**. Methods are exempt from EK2003 for a plain annotation, because a method implementing a plain-function member is declared that way (D55).

**D75. The compiler binary identifies as VibeLang**. The binary built from `tsc/cmd/tsc` always identifies as VibeLang (`vibelang --version` prints `VibeLang 0.0.1 (TypeScript 7.1.0-dev)`); there is no `cmd/vibelang`, which keeps the upstream diff to one seam.

**D76. TypeScript editor ownership requires disabling the built-in extension**. The VS Code extension serves `.ts` files only when the built-in TypeScript extension is off (disabled, or `useTsgo` in Cursor); this replaces the spec's "set `typescript.validate.enable` to false", because the server reads that setting and would drop all its diagnostics, `.vibe` included. Design tradeoff: D32 expects an automatic stand-down.

**D77. Hovers distinguish calls and plain helper signatures**. In `.vibe` files a hover adds "Runs here and returns `T`" at a call that runs, and shows a plain function's direct signature with what TypeScript callers see; `.ts` files keep TypeScript's hover. **controversial** (wording). A call exposes its success value while a helper must explain its TypeScript-facing Effect form.

**D78. Prelude and service members complete in scope**. Prelude names complete as in-scope names that local declarations shadow, and `Users.` lists the service's members. Programmers need the same discoverability as explicit imports and Context members.

**D79. The editor reuses TypeScript grammar and project-local vibelang**. The TextMate grammar is VS Code's TypeScript grammar with root scope `source.vibe` (inner scopes keep `.ts` so themes apply); `vibelang` is found from the `vibelang.server.path` setting, then the nearest `node_modules/.bin/vibelang`, then `PATH`; the extension does not run in untrusted workspaces. Existing themes and project compiler versions must keep working.

**D80. The runtime checks Effect metadata at load**. The runtime checks Effect's version by importing effect's package metadata with a static JSON import attribute, which works in Node, Bun, and bundlers.

**D81. Callback adapters use the public kernel API**. The runtime exports `suspend`, `handoff`, `Resumer`, and `HandoffProtocolViolation` for TypeScript callback adapters (D43). TypeScript adapters need cancellation-aware handoff and lost-race reporting.

**D82. Runtime extraction preserves the prototype ABI**. The extraction kept the prototype helpers' behavior and continuation parameter order; discrepancies with the spec are documented in packages/runtime/README.md, not fixed silently. Inherited limits: Stream adaptation keeps a one-element buffer (D26's zero-capacity handoff is unfinished, for F7); `$programs` handles iterables, not records (for F2); `$trusted` matches exceptions by name or tag (for F8).

**D83. Scaffolds use absolute file dependencies**. Setup writes absolute `file:` dependencies on the repository's packages into new projects instead of `bun link`; nothing registers globally and nothing is published, so a project keeps working only while the checkout stays where it is.

**D90. Service member calls are structural**. The member-call rule (D41) is structural: it applies to any Context key whose service type declares the member, which covers `.vibe` services, TypeScript `Context.Service` classes, and Effect's `FileSystem` and `Path`. Calling an Effect value with no arguments runs it (chapter 13's `p()` rule, applied generally). Both rules apply only inside `.vibe` function bodies.

**D91. Control calls look up their implementation**. A control-operation call lowers like a service call, `yield* (yield* Approval).approve(x)`, as the prototype did (chapter 13 prints `yield* Approval.approve(x)`); `handle` provides an implementation that performs the kernel operations. Design tradeoff: F7 may change it.

**D92. Methods lower when their body or expected type needs Effect**. A method in a `.vibe` file becomes an Effect when its body runs or looks up an Effect, or when its expected type returns one; it stays a method whose body is `return Effect.gen({ self: this }, function* () { … })`. The method must retain its receiver while running a generator body. Amended 2026-10-23 (release correction): a generator binds `super` and `arguments` afresh, so `super` there was a SyntaxError and `arguments` the generator's own. The function that binds them in the source now declares `const super_1 = (key) => super[key]` and `const arguments_1 = arguments` at the top of its body when code that the lowering moves into a generator reads them, as an Effect method's body, an Effect arrow and a try statement's regions do; a call is `super_1("m").call(this, …)`, and an assignment to `super.m` calls a second arrow, `superSet_1("m", value)`. Evidence: `effect-method-super`.

**D93. Service keys and declarations have a stable shape**. A service key is the package name (the directory name when there is none), the module path, and `#Name`. Declaration files use the runtime types `ServiceKey` and `ReferenceKey`. A default service needs `static readonly default` (without `readonly` it is an ordinary static). EK2101 requires all three type arguments on `Effect<…>`. `wire` emits its arguments consumers first; EK3204 applies when `Out` is `any` or `unknown`. Design tradeoff: the `readonly` requirement and EK2101's strictness. Package and module identity keep services distinct and explicit contracts bound provider analysis.

**D94. Using classifies its initializer**. A call that runs an Effect is an acquisition: it gets the block's Scope, `Scope` leaves R, and no `Symbol.dispose` is required. Any other initializer must be a Disposable, `null`, or `undefined`. A Disposable value of either kind also gets `[Symbol.dispose]()` at block exit, so an Effect whose own release already disposes it disposes twice.

Amended 2026-10-23: an acquisition's value with `Symbol.asyncDispose` and no `Symbol.dispose` gets an awaited `[Symbol.asyncDispose]()` at block exit when the acquisition registered no release of its own in the block's Scope; before, nothing released it. A resource that releases itself keeps only its own release, so an asynchronous release, such as a stream's, never runs twice.

Clarified 2026-10-26: the protected Disposable pattern acquires a plain `{ value: disposable }` holder with `Effect.acquireRelease` and disposes `holder.value` in release. Bind the holder with `using`: it has no disposal method, so this closes exactly once on success, failure, defect, and pending interruption (`scopes-using-holder`). Binding the Disposable itself and disposing it in release still closes it twice under D94; the synchronous/asynchronous asymmetry is unchanged and needs an owner decision.

**D95. For-using bodies own a region per iteration**. In an Effect function, `for (using x of values)` makes each iteration's body a Scope region; the value is taken first, and `using` or `fork` inside the body join that region. Resources and children must end with the iteration that owns them.

Amended 2026-10-26: a C-style `for (using x = value; test; step)` acquires its head once in a Scope region around the whole loop, preserving its labels. That region releases on normal completion, typed failure, defect, interruption, and jumps out of the loop, in reverse declaration order. A `for (using x of source)` over an iterator, producer, or Stream releases the iteration's value before closing its source on an early exit; the source closes on failure and interruption too. Cases: `scopes-using-for-head`, `scopes-using-for-of-iterator`, `scopes-using-loop-exits`, and `scopes-using-for-of-labels`.

**D96. Expression-bodied forks retain Scope**. A `fork` belongs to the innermost block around it; an arrow function with an expression body has no block, so `() => fork(p)` is `Effect.forkScoped` and keeps `Scope` in R. Design tradeoff: it differs from `() => { return fork(p) }`; alternatives are treating expression bodies as blocks or reporting a returned block-owned fiber.

**D97. Continuation result types use the program's original result**. A clause receives `Continuation<V, E, H>`. Without `onReturn`, H is the handled program's A; with `onReturn`, H is `never`, because TypeScript fixes H before checking that callback. The `handle` result unions the program's result (or `onReturn`'s result) with each clause's result and includes their errors and residual requirements. Design tradeoff: a non-tail resume can be typed more narrowly than its runtime result when another clause returns early with a different type. This keeps handler inference usable without circular callback inference; it does not implement D50's full result fixpoint. Amended 2026-10-23: the narrower type compiled programs that failed when they ran, such as a clause that wrote `const n: number = resume()` while another clause returned `"early"`. In a handle statement, a non-tail resume now has the type of every value the statement can end with: what its try block and its clauses return, and `undefined` when the block, or a clause that has not resumed, ends another way. A clause's return computed from resume's own result stays out of that type, since it would need the fixpoint; the warning EK2119 marks one that does not fit, and a written success type covers it. The `handle` function keeps the types above, and a clause that reads a non-tail resume's result where the handle can produce a value of another type is EK2110.

**D98. Producers are lazy Streams with two consumption paths**. A `function*` declaration or function expression returns `Stream<T, E, R>`; generator methods remain JavaScript generators. Direct `for...of` consumption runs the producer under a Yield handler on the consumer's fiber. Consumption through Stream operators starts a producer fiber on the first pull and uses a handoff with no buffer. Closing either path runs producer cleanup. This supplies D26's lazy Stream interoperability and bounded stack without running ahead of the consumer. Not controversial.

**D99. Handler reach checks inspect declared requirements and known fiber boundaries**. EK4201 checks Effect's named forking combinators, nonsequential `concurrency` options, concurrent zip calls, `fork`, `detach`, `forkIn`, the await operations, `for concurrent` with a limit other than 1, and producer arguments that require controls. A program passed by name (D147) needs what running it adds, as the lambda that runs it would, and each element of an await operation's operand is its own program. A branch that handles its controls internally passes. EK4202 rejects a non-VibeLang callee whose declared return requirements name a control; generic requirements stay subject to the argument checks. These checks identify unreachable handlers while the runtime enforces fiber ownership. Not controversial; static detection has the gaps recorded below.

**D100. Foreign calls are plain wherever no fiber runs**. Code no fiber runs is plain JavaScript for EK4401 too: a module's top level and the plain callbacks it passes to TypeScript functions (`describe` bodies, route handlers), the same places D38 allows runners.

**D101. Expected foreign failures come from explicit parsing contracts**. Only built-ins that parse outside text declare expected failures (`JSON.parse` with `SyntaxError`, `decodeURI` and `decodeURIComponent` with `URIError`); every other built-in's exceptions are defects. Trusted failures make named functions and free lambdas Effects but stay defects in plain callbacks. Each `@throws` class must be exported by a module the `.vibe` file imports, else the call is EK4401. Design tradeoff: the plain-callback leniency.

**D102. Platform APIs and globals are restricted**. EK4402 at value imports of Node built-ins and `bun:` modules (type-only imports allowed) and at each reference to a listed platform global, including inside boundaries and at top level; web standards that touch nothing outside the program are allowed (`URL`, `TextEncoder`, `AbortController`, `structuredClone`, `Headers`, `Response`). Design tradeoff: `console.log` and `createServer` need a `.ts` module (examples/http-api moved its server layer to `src/server.ts`). Effect services provide typed errors and replaceable platform access. D108 supersedes the import restriction.

**D103. Top-level program calls have one diagnostic**. EK1001 covers any top-level call that would run a program, including service member calls and Effect-value calls, reported once at the outermost call. The outermost call identifies the attempted execution without duplicate errors.

**D104. Generated names and spans follow source names**. Compiled generators are named after their function, variable, or property (an object method `{ *name() {} }.name` when the body refers to that name); `tracing: "exported"` spans exported functions, `"all"` every named lowered function plus methods through `Effect.withSpan("Class.method")`; anonymous lambdas get no span. Named generators and spans make source-level failures identifiable.

**D105. Vite uses one project compiler subprocess**. Amends D31's mechanism, preserving the behavior. `vibelang-vite` compiles the whole project with one shared `vibelang` subprocess per source revision and serves the output cached under `node_modules/.vibelang/`, instead of `vibelang --api`. Whole-project compilation keeps contracts consistent without depending on the API transport.

**D106. Edits invalidate all loaded VibeLang modules**. After an edit the plugin invalidates every loaded `.vibe` module and its transitive importers, because callers compile differently when a contract changes.

**D107. Vite sources stay under its root**. Sources must sit under Vite's root; the plugin overrides emit paths and source roots there so output lookup and source maps are predictable. This restricts monorepos.

**D108. EK4402 reports platform execution, not imports**. Supersedes the import half of D102; its globals list and allowed web standards stand. EK4402 fires where `.vibe` code runs a platform API (a call, `new`, tagged template, or property read of one, including by destructuring or spreading), not where it names one. Imports, re-exports, value uses, and namespace member reads as values (`os.EOL`) are allowed, so `NodeHttpServer.layer(createServer, { port })` compiles in `.vibe`. A call EK4402 reports is not also EK4401. Known gap: a platform function reached through a local alias, a parameter, or an object a platform call returned is not followed. Platform integrations must be able to pass host functions to Effect adapters without calling them.

**D109. Only Effect itself selects an Effect callback form**. An expected callback or program asks for the Effect form only when its type is effect's own `Effect` interface, or a type parameter constrained to it; subtypes such as `Config` are data (D24), so `Config.orElse`'s fallback stays plain.

**D110. Pipe looks ahead without checking its first stage early**. The `pipe` look-ahead (D8) reads the first stage's callee signatures, or a function value's own signatures; it runs only when the first argument can be a program, and never checks the stage early. Reading signatures avoids circular inference from a prematurely checked stage.

**D111. Program collection conversion covers iterables**. The D49 conversion covers any iterable (`Set`, a `Map`'s values) through its iterated type; an iterable never converts as a record, matching `Effect.all` at run time.

**D112. Mixed plain and Effect callback returns prefer plain when eligible**. A callback whose expected return mixes plain and Effect (`boolean | Effect<…>`) is plain when D10 allows and an Effect function otherwise; the same holds wherever both forms fit.

**D113. Plain contract lambdas expose their success type**. A lambda with a contract that takes the plain form has type `(…) => A`; where only a plain function fits, inference from its annotation starts from A.

**D120. Local runtime installs use the packed tarball** (amends D83). Projects and examples install `vibelang-runtime` from the tarball packed by `scripts/setup.sh`. Refresh existing projects with `bun update vibelang-runtime vibelang vibelang-vite` after rerunning setup; examples do not commit `bun.lock`. A folder dependency loaded a second copy of Effect, preventing block-owned forks from stopping and programs from exiting. The tarball keeps the runtime and program on one copy. Not controversial.

**D121. Effect trust follows re-exports and returned values** (extends D22). Trust covers functions re-exported by Effect's packages and values returned by their calls. `assert` and `expect` from `@effect/vitest` are trusted; imports of those functions from `vitest` remain EK4401. The program's own `.ts` code keeps D5's boundary rule. Design tradeoff: this widens trust to Vitest through `@effect/vitest`. Tests need usable assertions without per-call foreign boundaries.

**D122. Runners check every unprovided service** (amended by D312). EK3201 fires at every runner for a service it does not supply. A root runner supplies no services; `it.effect` supplies `Scope` plus services from its `layer(...)` context. Missing requirements must fail during compilation rather than as a runtime service lookup. Amended 2026-10-23 (release correction): an entry module's `main` (D135) is a root runner's program, since its entry statement runs it with `NodeRuntime.runMain` or the runtime's copy. The check visited only runner calls in the source, never the statement the lowering appends, so `export function main() { Console.log(Users.find("1")) }` compiled without a word and died with `Service not found`. It is a warning, adjustable as D34's policy codes are, because the same module may be a library: the platform guides' `greeting.vibe` exports a `main` that another module runs with `NodeServices.layer`, and a test runs with test layers, and a package's importer may live in another program; reporting an error there rejected programs that ran correctly. Evidence: cases `entry-main-services.fail` and `entry-main-services-error.fail`.

**D123. Declaration prelude imports avoid existing bindings**. A `.d.ts` that already binds a prelude name imports the prelude type under a free alias such as `Effect_1`. Generated contracts must not introduce duplicate identifiers into declaration consumers. Not controversial.

**D124. Setup repairs stale vibelang launchers**. Setup relinks a `vibelang` launcher that points into another checkout or at a missing file. Switching workspaces must leave the configured launcher pointing to an available compiler. Not controversial.

## Fewer tokens: declarations (2026-10-16)

A measurement over the docs and examples found the ceremony; these forms remove it. Each form is parser sugar for the long form, which still compiles, so checking, emit, declaration files, and the language service treat both the same.

**D126. `error` declares a tagged error class**. `error NotFound { id: string }` is short for `class NotFound extends TaggedError("NotFound")<{ readonly id: string }> {}`: the tag is the class name, every field is readonly, and `error Timeout` declares an error without fields. Type parameters follow the name. `error` stays an ordinary identifier unless another identifier follows it on the same line. Amended by D278 (error declarations are classes), D279 (`schema error`) and D304 (a family's tag type).

**D127. Effect types are written `Result!Error!Dependencies`** (amends D57; superseded by D308, which retired the form; restored by D309 as an alias of `Effect<A, E, R>` and the documented form). `User!NotFound!Db` is `Effect<User, NotFound, Db>` anywhere a type can appear. An empty slot is `never`: `User!NotFound!`, `User!!Db`, `User!!`. Dependencies left out entirely, as in `User!NotFound`, are `infer R` in the return annotation of a function with a body and `never` everywhere else; errors cannot be left out once a `!` is written, so inferring them takes no annotation or `Effect<A, infer E, ...>`. Unions bind inside a slot: `User!NotFound | Timeout!Db` fails with `NotFound | Timeout`. A slot that starts with `{` is empty, because in a declaration the `{` starts the body; an object type after a `!` needs parentheses. The parser expands the form to `Effect.Effect<A, E, R>`, which resolves whether `Effect` is the prelude's or imported from `effect`, so declaration files read `Effect.Effect<A, E, R>`; hovers and contract messages about `.vibe` code use the `!` form. The postfix `!` of JSDoc types no longer parses in `.vibe` files. `Effect<A, E, R>` stays accepted. Controversial because `!` reads as negation or non-null to a TypeScript programmer.

**D128. `service` and `control` declare services and control operations** (amended by D220, which D223 reverted: written without `class`; extended by D281: `service Name: Type`). `service Users { find(id: string): User!NotFound; region: string }` is short for `abstract class Users { abstract find(id: string): User!NotFound; abstract readonly region: string }`, and `control Approval { approve(request: string): boolean!! }` for the same with `extends Control`. Every member without a body or initializer becomes abstract, and every value member also readonly; static members, such as a layer, stay as written. A member's contract uses the `!` form; a plain return type is not an Effect, so it stays EK2101 rather than quietly meaning `A!!`, which would wrap an alias that already names an Effect type. Without a body, left-out dependencies are never, so `find(id: string): User!NotFound` needs no trailing `!`. A member with an implementation is EK2103, because it would make the class an ordinary abstract class instead of a service. The parser marks the class's `abstract` modifier as synthesized, which is how the checker tells the declaration from a hand-written class. Not controversial.

**D129. `layer` declares a layer** (superseded by D221: a layer is `Layer.effect(Service) { ... }`). `layer UsersLive: Users { const directory = Directory(); find(id) { ... }; readonly region = "eu" }` is short for `const UsersLive = Layer.effect(Users, () => { const directory = Directory(); return { find(id) { ... }, region: "eu" } })`. Statements run once, when the layer builds; members are methods, `name(params) { ... }` or `*name(params) { ... }`, and values, `readonly name = value`, which is not a statement in TypeScript, so it cannot be mistaken for an assignment to an outer variable. Without statements the layer is `Layer.succeed(Users, { ... })`. A method starts with a name and parameters followed by a return type or a `{` on the same line, which a call statement cannot be. Statements come before the members, so the expansion keeps source order; one that follows them is EK2104. Scoped setup works because Effect 4's `Layer.effect` supplies the layer's own Scope. Static layers inside a service stay as written. Not controversial.

**D130. `with` provides a layer to a block** (amended by D172: the keyword is now `provide`; extended by D173: providers may be `Key = value`). `with AppLive { ... }` runs its statements with the services the layer provides, as `Effect.provide(() => { ... }, AppLive)` does, except that the statements are code of the enclosing function: a `return` returns from it, and `break` and `continue` leave its loops. A module is strict code, where JavaScript's `with` statement is a syntax error, so the word is free. The parser reads the block as an ordinary `Block`, flagged `NodeFlagsVibeLang`, whose first statement holds the layer expression, so TypeScript checks both as ordinary code; the analyzer gives the block the errors of its statements and the layer, and the requirements of its statements that the layer does not provide plus the layer's own; the lowering runs the statements as a region closure under `Effect.provide`. The layer expression may be a layer, an array of layers, or a `Context`, as `Effect.provide` accepts. A function with a `with` block is an Effect. A `with` block at a module's top level is EK1001. Not controversial.

**D131. Catch clauses name the failures they handle** (superseded by D216). `try { ... } catch (e: NotFound) { ... } catch (e: Busy | Offline) { ... } catch (e) { ... }`: each clause handles the failures whose `_tag` belongs to its type, a final untyped clause handles the rest, and without one a failure no clause names propagates with its type. The parser writes one catch clause whose block tests `$isFailure<T>($caught)`, a runtime type guard, clause by clause, so TypeScript narrows each clause's variable and the failures left after the chain; the lowering passes the guard the `_tag` of each member of `T`. A failure raised inside a clause is not tested by the clauses after it, as in other languages with several catch clauses. Matching by `_tag` covers tagged errors from other packages, such as `Schema.SchemaError`, and type aliases of unions; a member without a literal `_tag` is EK2105, and a clause after an untyped one is EK2106. A single untyped clause parses as before. Not controversial.

**D132. Handle clauses follow a try block**. `try { BODY } handle Approval.approve(request) { CLAUSE }` handles the control operations that BODY performs, as `handle(() => BODY, Approval, { approve(request, k) { CLAUSE } })` does, except that BODY and CLAUSE are code of the enclosing function: a `return` returns from it, and `break` and `continue` leave its loops. A clause's parameters take the operation's parameter types, and in its own code `resume(value)`, `resume()` for a `void` result, `resumeWith(program)`, and `abandon()` act on its continuation, which it never names. A clause continues after `resume` once the try block finishes, and the statement then ends as the block did, as a pending `return` waits for a `finally` block; a clause that ends without resuming abandons the block, and the statement completes. Several clauses may follow one try, one per operation of each control they name (EK2108; a name that is not a control is EK2107); the first control's handler is innermost. Catch clauses and a `finally` block may follow the handle clauses and cover the block and the clauses. The parser writes `try { BODY } catch ($performed) { if ($performed) { const [$k, request] = $clause(Approval.approve); CLAUSE } }`, flagged `NodeFlagsVibeLang`, so TypeScript's flow analysis lets a clause start anywhere in the block; `$clause` types the bindings, and `$k` makes `resume` return `never`, so a clause that ends with a resume does not complete normally. The lowering runs BODY as a region under the runtime's `handle` and each clause as a generator that returns the statement's completion record, with the tail-resume request (D18) for a resume at a clause's end. `handle(...)` stays the expression form, which returns a value and takes `onReturn`. Not controversial.

**D133. `schema` declares a struct schema and its type** (extended by D280, the alias form `schema Name = <type>`). `schema User { id: string; nickname?: string; role: "admin" | "member"; home: Address }` is short for `const User = Schema.Struct({ id: Schema.String, nickname: Schema.optional(Schema.String), role: Schema.Literals(["admin", "member"]), home: Address })` and `interface User extends Schema.Schema.Type<typeof User> {}`. The parser writes each field's schema from its type: a primitive keyword, a literal (`Schema.Literal`), a union of literals (`Schema.Literals`) or of other forms (`Schema.Union`), `T[]`, `ReadonlyArray<T>`, and `Array<T>` (`Schema.Array`), a tuple, `Record<K, V>`, an object type (a nested `Schema.Struct`), or the name of another schema, which the struct refers to as a value, so any schema constant can be named. `name?: T` is `Schema.optional`, which accepts an absent key or `undefined` whatever `exactOptionalPropertyTypes` says, so decoding accepts every value the type allows; exact optional keys, checks, and transformations stay with `Schema.Struct`. Any other type, and a name whose value is not a schema, is EK2109. The interface is derived from the struct, not from the written field types, so the type and the schema cannot disagree; the written types are not checked as types. The interface goes to the parser's reparse list, which puts it before the constant in the same statement list. Not controversial.

**D134. Members are readonly unless written `mutable`**. In a `.vibe` file, every property signature and index signature of an interface or an object type is readonly unless it is written with `mutable`: `interface Cart { id: string; mutable items: Array<Item> }` means `interface Cart { readonly id: string; items: Array<Item> }`. The parser adds the `readonly` modifier, so declaration files write it and TypeScript code sees the same types. `mutable` is a modifier only when a member name follows it on the same line, so a member named `mutable` parses as before. Class members keep TypeScript's rule, and arrays and tuples are untouched, so `ReadonlyArray` is still written. A schema field written `mutable` gets `Schema.mutableKey`; an error's fields stay readonly whatever is written, because Effect's `TaggedError` types them `Readonly`. Readonly limits writes through the type, not the object: TypeScript lets a mutable object be assigned to a readonly type, so callers in either language pass the same values. Controversial because the same interface means different things in a `.ts` and a `.vibe` file, and code ported from TypeScript that writes through an interface gets TS2540 until its members say `mutable`; the payoff is that immutable data, the common case in Effect code, no longer repeats `readonly` on every field, which the docs and tests wrote 186 times.

**D135. An exported `main` runs when the host starts its module** (amended by D312). A module that exports a function declaration named `main` with no parameters ends with `if (import.meta.main) NodeRuntime.runMain(main())` in its JavaScript, so `node dist/main.js` runs the program, and importing the module, from a test or another module, runs nothing. `NodeRuntime` comes from `@effect/platform-node` when that package resolves from the module; the program resolves it as an implicit import of every module with such a `main` to find out. Without it, the module calls the runtime's `$runMain`, which `Runtime.makeRunMain` builds to behave as `NodeRuntime.runMain`: Effect's runner reports a failure nothing reported, SIGINT and SIGTERM interrupt the program where the host has a `process`, and the exit code follows `Runtime.defaultTeardown`. So a program needs no platform package to run, and Bun and Deno, which also set `import.meta.main`, run it the same way. A module that calls a runner at its top level, any call of a function named `runMain`, `runPromise`, `runFork`, `runSync`, or `runCallback`, starts its program itself and gets no entry statement, so a program never starts twice; that is how an application provides layers or passes runner options. A `main` that compiles to plain JavaScript runs through `Effect.sync`. The examples' `run.vibe` files and the template's runner call are gone. `import.meta.main` needs Node.js 24.2 or later, and VibeLang already requires Node 26. Amended 2026-10-23 (release correction): bundles ran the wrong mains. esbuild, Rollup, Rolldown and Vite keep `import.meta` as it is in an ES module bundle, so every bundled module's `import.meta.main` was the bundle's, and an imported module's `main` ran before the entry module's; in a CommonJS bundle they empty `import.meta`, so no `main` ran and the program exited 0. A file emitted as CommonJS failed to load at all, since `import.meta` is an ES module's. Now the module ends with `runtime.$entry(import.meta.main, import.meta.url, main, () => NodeRuntime.runMain(main()))`, and `$entry` runs the arrow when the host started the module: never when `import.meta.main` is false; when it is true and `import.meta.url` names the file the host started (`process.argv[1]`, as given or with its links resolved), only if that file, which the host has already loaded and which `$entry` imports, exports this `main`, as an unbundled module and a bundle's entry module do; when it is true and names another file, as Bun, webpack and Rspack write each module's own URL beside a per-module `import.meta.main`, always. When `import.meta.main` is undefined, in a CommonJS bundle or in a file emitted as CommonJS, which passes `void 0` for both, `main` runs when the host's CommonJS main module (`process.mainModule`) exports it, once that module has run. A host that names no started file, such as Deno, trusts `import.meta.main`; a host that sets neither, such as a browser, runs nothing. Where `$entry` imports the started file or asks the CommonJS main module, `main` starts once that file has finished evaluating, not as its own module's last statement. Rejected: entry statements only for configured entries (a module that is both a library and a program, which this decision allows, stops running when started), and comparing `import.meta.url` with the started file alone (every module of an ES module bundle has the bundle's URL). Evidence: `packages/unplugin/test/entry.test.mjs` bundles compiled output with esbuild, Rolldown, Rollup, Vite, webpack, Rspack and Bun, as ES modules and as CommonJS; the plugin fixture's `script.vibe`; `packages/runtime/tests/entry.test.ts`; case `entry-main-commonjs`.

## Fewer tokens: calls (2026-10-16)

The token-reduction proposals were measured on the docs and examples (59,572 word and punctuation pieces in 632 code units). These decisions cover calls; the declaration keywords have their own section.

**D146. Every export of `effect`'s root is in scope** (extends D4 and D62). A `.vibe` file sees every namespace and function that the `effect` package exports from its root, such as `Console`, `Stream`, `Option`, `Schedule`, `Duration`, `flow`, and `identity`, without an import, after the runtime's prelude names. A local declaration or import shadows one. A global value that JavaScript itself defines wins, so `Array`, `String`, `Number`, `Boolean`, `Symbol`, `BigInt`, `Function`, and `RegExp` keep their meaning and Effect's modules with those names need an import under another name; a host global such as the DOM's `Option` does not shadow Effect's. The emitted JavaScript imports each used module from `effect/<Module>`, never from the root, which would load every module. Subpath packages such as `effect/http` still need imports: their names (`HttpRouter`, `HttpServerRequest`) belong to one kind of program. Imports from `effect` were 5.9% of the corpus.

**D147. Calls are passed by name where a program is expected** (extends D7 and D49). Where a parameter's declared type expects an `Effect`, including an array element or record field of `Effect.all`, an argument expression that calls a `.vibe` function, a function that returns an `Effect`, or a service member is passed by name: the callee receives a program that evaluates the expression each time it runs, as if the source had written `() =>` before it. `fork(fetchReport())`, `Effect.timeout(slowReport(), "20 millis")`, `Effect.race(cachedReport(), slowReport())`, `Effect.all([a(), b()])`, `HttpRouter.add("POST", "/users", createUser())`, and `NodeRuntime.runMain(main())` all mean what they mean in Effect. Elsewhere the call runs where it stands: `Console.log(fast())` logs fast's result, and `Effect.succeed(work())` succeeds with it. An expression whose value is already an `Effect` keeps its meaning. Each overload candidate decides by its own declared parameter, as for lambdas (D56). This applies to every Effect-typed parameter, including a plain callee such as `Stream.fromEffect`. Constructing that cold program does not lift an enclosing plain-annotated factory; its calls run when the Stream is consumed. EK1001 does not apply at the top level to a call passed by name. A hover on the callee says the call is passed as a program and runs later. Controversial because the call site no longer shows whether a call runs now or later; the parameter's type decides, and the hover says which. A program of several statements still needs `() => { … }`. Thunks around single calls were 2.6% of the corpus. 2026-10-24 (real-world migration): where a call runs, its contextual type is its success value's, which says nothing about the type arguments of the Effect its callee returns, so TypeScript infers none from it. Before, TypeScript inferred them as if the contextual type were that Effect, and an error instance, itself an Effect that fails with the error, gave E its own type: `function f(): Late!! { return late() }` was EK2001 for a `late` whose E no argument names. Where the contextual type is an Effect, the call stands where a program is expected, and TypeScript infers from it as usual. Case `running-call-contextual-type`. 2026-10-25 (real-world migration): a call that runs and never succeeds, stored in a variable, an object literal's field, an array literal's element or an assignment, is the warning EK1012. Running it where it stands is this decision's rule, and only a declared Effect type holds a program there (D262, D265, D269), so the binding or field never holds a value: an untyped `const missing = Effect.fail(new Missing())` failed the function at the const, and `{ follow: followUntil() }` ran an endless loop while the object was built, where Effect TypeScript stored both programs to run later. Nothing changes in what compiles; the note names the spellings that keep the program, a function (`() => followUntil()`) or the declared Effect type (`const missing: never!Missing! = …`, a declared object type), and the statement that runs it here. A stored call that succeeds with a value is not reported: nothing tells it from `const user = Users.find(id)`. EK1012 is adjustable, as EK4409 is. It fires in one of the 496 acceptance cases on `main`, `pipe-asserted-program`, whose `Effect.flip(erased())` the types say never succeeds because an assertion erased its failure channel (it succeeds when it runs), and none of the 747 documentation blocks. Cases `never-stored.fail`, `never-stored-spellings`.

**D148. Boundary hatches run plain TypeScript** (amended by D229-D232). The prelude's `sync`, `try`, and `callback` are escape hatches whose first arguments are plain TypeScript, not VibeLang (D232). `sync(() => …)` is `Effect.sync`, so a throw is a defect; `sync(async () => …)` is `Effect.promise`. `try(() => …)` is `Effect.try`, so a throw is an expected `Cause.UnknownError`, or what an optional second argument such as `(error) => new BadJson({ error })` makes of it; `try(async (signal) => …)` is `Effect.tryPromise`. `callback((resume, signal) => …)` is `Effect.callback`: `resume(value)` succeeds, `resume.fail(error)` fails, `resume.exit(exit)` adopts an Exit, and a function the body returns runs on interruption, awaiting its PromiseLike result. A returned `Effect<void, never, R>` is the interrupt finalizer itself, and its requirements join the callback's R. Registration runs lazily on every execution; the first resume wins, normal completion skips the finalizer, and interruption aborts the signal before running and waiting for the finalizer with interruption disabled. Cleanup throws and promise rejections remain defects. This matches Effect 4.0.5 `src/internal/effect.ts:1161-1205,1210-1216` and its public finalizer type in `src/Effect.ts:1853-1859` (S19-30). A single expression is a hatch too, evaluated when the Effect runs: `sync(crypto.randomUUID())`. Inside a hatch's first argument there is no VibeLang lowering: calls do not run, so calling a `.vibe` function gives an inert Effect value for `runPromise` or `runFork`; `throw`, `async`, and `await` keep their JavaScript meaning; platform APIs and clock reads are allowed (no EK4401, EK4402, or EK4403); `return` returns from the hatch's function; and the function captures nothing of the `.vibe` file, whose values arrive as inputs (D229, D230). A hatch is recognized by name when no scope around the call declares it, so a parameter named `callback` stays a parameter. Controversial because VibeLang now has two meanings for the same function syntax, decided by the call it sits in; the hatch names keep that visible at the call site.

**D149. `try(` is a call in `.vibe` files.** A try statement starts with a block, so `try (` never starts one; the parser reads `try(…)` as a call whose callee is the identifier `try`, which only the prelude can bind. Effect's `{ try, catch }` options object passed to the hatch is EK4404, an error: the hatch would treat it as a value and succeed with the object itself.

**D150. Runners lead back in** (extends D38). `runPromise`, `runFork`, `runSync`, and `runCallback` are in the prelude, re-exported from `effect/Effect`. They are called from plain TypeScript: a `.ts` file, a hatch's body, or a module's top level. EK1005 still reports one in code a fiber runs, and does not apply inside a hatch.

**D151. The Effect module's most used functions need no prefix** (extends D146). `all`, `die`, `forEach`, `log`, `logDebug`, `logInfo`, `logWarning`, `logError`, `race`, `repeat`, `retry`, `sleep`, `timeout`, and `withSpan` are in scope as the Effect module's functions: `sleep("1 second")`, `retry(fetchUser(id), policy)`. They were 329 of the 538 `Effect.` member uses in the docs and examples. Operations that VibeLang spells another way stay qualified: `Effect.fail` is `throw`, `Effect.provide` is `with`, `Effect.scoped` and `acquireRelease` are `using`, and `Effect.sync`, `promise`, `try`, and `tryPromise` are the hatches (D148). Names that read poorly alone, such as `result`, `exit`, and `service`, stay qualified too. A local declaration shadows one; the emitted JavaScript imports each one used from `effect/Effect`.

**D152. Values of Effect's data types take their module's functions as methods** (extends D146). A value whose type one of `effect`'s data-type modules declares takes that module's data-first functions as methods: `readings().filter(hot).take(2)` is `Stream.take(Stream.filter(readings(), hot), 2)`, and `maybe.map(format).getOrElse(() => "none")` is `Option.getOrElse(Option.map(maybe, format), () => "none")`. The modules are `BigDecimal`, `Cause`, `Chunk`, `DateTime`, `Deferred`, `Duration`, `Effect`, `Exit`, `Fiber`, `HashMap`, `HashSet`, `Option`, `Queue`, `Ref`, `Result`, `Schedule`, `Sink`, and `Stream`; the module is the one whose declaration file declares the value's type, and every member of a union must come from the same module, as `None` and `Some` do. A function is a method when its first parameter is named `self`, effect's name for the data-first form of a dual, or ends in `OrOptions`, as in `Stream.flatten`. The receiver is that parameter, written as the call's `this`, so TypeScript checks it and infers type parameters from it, and a type guard on it narrows the receiver: after `if (maybe.isSome())`, `maybe.value` is defined. A type's own members win, so an `Effect`'s `pipe` stays its own, and arrays, strings, and objects keep JavaScript's methods. A method that returns an Effect is a call like any other, so it runs: `fiber.join()` waits for the fiber. The emitted JavaScript calls the module's function, so bundlers drop unused functions as they do for Effect code. Hover on a method names the function it calls, and completion after a dot lists the module's methods. The docs codemod rewrote 180 blocks and removed 682 of 62,163 proxy tokens (1.1%). Controversial because Effect gave up fluent methods on purpose, for tree shaking and one calling style: VibeLang keeps tree shaking, since the methods exist only at compile time, but the same dot now reaches a member on one type and a module function on another, and a member that a later Effect release adds to a type takes the call from the module function of the same name.

**D153. A method of a data type exists only in a call** (EK4501). `const read = maybe.getOrElse` has no function value to bind, because the lowering rewrites the call, not the property. EK4501 reports the access and suggests calling it or passing the module's function, `Option.getOrElse`, itself.

**D154. `.vibe` files have the Hack pipe operator** (supersedes D8). `x |> f(%, a)` evaluates the body `f(%, a)` with the topic `%` standing for `x`, as in TC39's Stage 2 proposal: `fetchUser(id) |> retry(%, policy) |> timeout(%, "1 second")`. The operator is `|` directly followed by `>`; it binds looser than every binary operator and the conditional operator, as an assignment does, and associates to the left. A body is a conditional expression, so an arrow function, an assignment, or a yield there needs parentheses. `%` where an expression starts is the topic of the innermost pipe whose body holds it; after an operand, `%` is still the remainder operator, so `n |> % % 2` is `n % 2`. The pipe has its body's type, and the body has the pipe's contextual type. Hover on `%` shows its type and whether it is a value or a program. The emitted JavaScript has no pipe: a topic used once, before anything in the body that could have an effect, becomes the left side itself (`price |> double(%)` is `double(price)`); otherwise the left side runs once into a variable, and a function in the body that reads the topic keeps the value of the evaluation that created it. The formatter keeps `|>` together. VibeLang uses `%`, the token in the proposal's README, although the proposal's wiki disqualifies it for engine parsing complexity; VibeLang's parser decides by position, and VibeLang will follow the token TC39 chooses. The docs rewrite changed 21 blocks, 15 to `|>` and 6 data-type pipes to method chains (D152), and removed only 23 of 61,678 proxy tokens: `x |> f(%, a)` costs what `pipe(() => x, f(a))` costs. Its gain is reading order and any argument position, not tokens. Controversial because the proposal has been at Stage 2 since 2021, its topic token is undecided, and TypeScript will not parse `|>` until Stage 3, so `.vibe` code moves further from TypeScript.

**D155. A topic follows the by-name rule** (extends D147). Where `%` stands for an argument whose parameter expects a program, and the left side runs an Effect, the left side is passed by name: that `%` is a program that evaluates the left side each time it runs, and the left side does not run before the body. `fetchUser(id) |> retry(%, policy)` means `retry(fetchUser(id), policy)`, and in a chain each `%` passes everything before it: `timeout` in `a() |> retry(%, p) |> timeout(%, t)` receives the retried program. Elsewhere the left side runs once, before the body, and `%` is its value. A pipe that passes its left side by name and also uses it as a value is EK1008, because the left side would run both before the body and inside the program. A pipe whose topic is passed by name runs nothing at a module's top level, so EK1001 does not apply to its left side. Controversial for the reason D147 is: the parameter's type, not the source, decides whether the left side runs now or later; the hover on `%` says which.

**D156. Pipe syntax errors**. A body that never uses `%` is EK1006: the left side's value would go nowhere, which the proposal makes an early error. A `%` outside every pipe's body is EK1007; it resolves to the error type, so TypeScript reports nothing more.

## Fibers (2026-10-17)

**D166. `fork` is a keyword**. `fork getUser(id)` parses as `fork(getUser(id))` and `fork { ... }` as `fork(() => { ... })`, so the fiber belongs to the enclosing block (D95) and the operand is passed by name (D147). The operand binds as `await`'s does: `fork a().b` forks `a().b`. The keyword form needs its operand on the same line, starting with a name, `this`, `new`, `super`, `{`, or `await`; `fork(` stays a call, which means the same, and `fork [x]` stays an element access, so no code that parses today changes meaning.

**D167. `await` waits for fibers and Deferreds** (superseded by D225 and D226). Outside an `async` function, `await x` parses as the runtime call `$await(x)`, which runs where it stands: its value is what it waited for and its failures join E. It waits for a `Fiber`, a `Deferred`, or an array, tuple, or object of them, keeping the shape; when one fails, the fibers still running are interrupted and the failure propagates, as `Effect.all` fails fast. `await` before a call that already runs is EK4601, on a promise EK4602, on anything else EK4603, and inside a hatch's function that is not `async` EK4604. `async` stays EK1003, and inside an `async` hatch body `await` keeps its JavaScript meaning (D148).

**D168. `select` races its cases** (superseded by D197). `select { case const x = a(): ... case b(): ... default: ... }` starts each case expression, a program passed by name, in its own fiber in the order written; the first to finish wins, its statements run with its binding, and the others are interrupted; a failure of the first to finish propagates. Of cases ready at once, the first written wins, because a case that finishes while the cases start stops the rest from starting. A `default:` clause runs when no case finishes while they start (a poll). `break` leaves the select, as it leaves a `switch`; the last clause, or `default`, is the final branch, so a select whose clauses all return ends the function. `select {}` waits forever, as in Go. It parses as a labeled block around `$select(...)`, whose result is a union discriminated by the case's index.

**D169. `for concurrent` runs a loop body per item**. `for concurrent(n) (const x of xs) body` parses as `$forConcurrent(xs, n, (x) => { body })`, which is `Effect.forEach` with concurrency `n` (no limit without one) that discards results: every item runs in its own fiber, all join before the loop ends, and a failure interrupts the rest. `continue` ends one item (the parser writes it as a `return` from the body). A `break` that would leave the loop is EK4605 and a `return` is EK4606, because no loop runs on the body's fiber. Use `forEach` for results.

**D170. `detach` and `forkIn` are fork's variants**. `detach(program)` is `Effect.forkDetach`: a fiber nothing owns. `forkIn(scope, program)` is `Effect.forkIn` with the scope first, so the program reads last. Both take the program by name and are prelude names.

**D171. `await`'s types reach one level**. The runtime waits through nested arrays and objects, but its types, and the EK4603 check, accept an array or object only of `Fiber`s and `Deferred`s themselves: recursive conditional types over arbitrary nesting exceed TypeScript's instantiation depth. Nest awaits instead.

## Names follow Effect (2026-10-17)

**D172. The provide block is spelled `provide`** (amends D130). `provide AppLive { ... }` replaces `with AppLive { ... }`, so the keyword is the name of the function it stands for, `Effect.provide`: VibeLang keywords reuse Effect's own names so a reader can map each form back to Effect. The parser reads `provide` as the block form only when a layer expression and an opening brace follow on the same line, so a local function or variable named `provide`, a call `provide(x)`, and an element access `provide[i]` keep their meaning. The old spelling still compiles the same way and draws EK1009, a warning, whose quick fix replaces `with` with `provide`; the language service matches EK quick fixes by the diagnostic source `EK`. The generated region function is `f$provide`. Not controversial.

**D173. `provide Key = value` provides one service** (extends D130). A provide block's providers are separated by commas, and a provider written `Key = value` provides that one service, as `Effect.provideService` does: `provide AppLive, Clock = testClock { ... }` compiles to `Effect.provide` with `[AppLive, Layer.succeed(Clock.Clock, testClock)]`, and the block's requirements drop every provided key. The parser rewrites the list into an array of layers and each `Key = value` into `$provideService(Key, "Key", value)`, a runtime function whose types check the value against the key's service shape. It has one signature, with the name before the value, so a method in the value is checked against the key's shape from the start (D92). `provide(A, Key = value) { ... }` means the same as `provide A, Key = value { ... }`, as `fork(x)` means `fork x`; the parser reads the parenthesized list as an expression, not as arrow-function parameters. 2026-10-24 (real-world migration): a requirement that is a type parameter `R` keeps `Exclude<R, I>` of the services `I` the block provides, as `Effect.provideService` leaves it; the block kept `R`. Case `provide-generic-requirement`.

**D174. An effect module stands for its key of the same name**. In a `Key = value` provider, a module whose export of the same name is a service key stands for that key: `Clock` for `Clock.Clock`, `Random` for `Random.Random`, `Scheduler` for `Scheduler.Scheduler`. Those three are references with defaults, so providing one swaps a runtime service for the block and the fibers it starts without changing any contract. A hover over the key names the service it provides. A key that is neither a service key nor such a module is TS2769, which names the key's expected type. Not controversial.

**D175. A provider list is read element by element**. The analyzer computes what an array-literal provider provides from each element's type. The array's own type merges the elements into one union, and because a layer is contravariant in what it provides, `Layer<Names> | Layer<never>` reduces to `Layer<never>`, which would hide `Names`. This also fixes `provide [NamesLive, RandomLive] { ... }` written as an array. Not controversial.

## Primitives (2026-10-17)

Every Effect primitive has a form in the language itself, in Effect's own words, believable as TypeScript. D176-D180 add the ones the primitives list kept.

**D176. A catch clause typed `Cause` catches every reason** (superseded by D217). `catch (cause: Cause)` (or `Cause<E>`, `Cause.Cause`) is `Effect.catchCause`: it sees expected failures, defects, and interrupts, binds the whole `Cause<E>` where E is what the try block can fail with, and may follow typed and untyped clauses, which still see expected failures only. Clauses after it never run (EK2106). It does not catch a control operation's abandonment, whose internal interrupt unwinds through. A try statement with one makes its function an Effect. A type annotation choosing semantics is new for `catch`; it reuses the typed clauses' shape (D131).

**D177. `throw cause` rethrows every reason**. Throwing a value whose type is a `Cause` (or a union of them) is `Effect.failCause`: the failure keeps every reason, and the Cause's E joins the function's E. Throwing any other value keeps D13's meaning.

**D178. `finally (exit)` binds the Exit**. `finally (exit) { ... }` is `Effect.onExit`: the block runs on every exit without interruption, with `exit: Exit<void, E>`, E being what the try statement can fail with. A success carries no value, because the try block's statements have none; a `return` inside the try block still returns its value. `finally { ... }` keeps D15's meaning.

**D179. `exit`, `interrupt`, and `yieldNow` are bare functions** (extends D151). `exit(program)` is `Effect.exit` with the program passed by name; `interrupt()` is `Effect.interrupt` and `yieldNow(priority?)` is `Effect.yieldNow` or `Effect.yieldNowWith`, functions in the runtime because Effect's own are values. A bare `yield` statement was rejected: it clashes with producers and is not Effect's word.

**D180. `uninterruptible`, `restore`, and `interruptible` blocks**. `uninterruptible { ... }` is `Effect.uninterruptibleMask`; `restore { ... }` inside it runs its statements with the interruptibility the region began with; `interruptible { ... }` is `Effect.interruptible`. Statements inside stay code of the enclosing function, so `return`, `break`, and `continue` keep their meaning. Each block calls the prelude function of its name, `uninterruptible(program)`, `restore(program)`, or `interruptible(program)`, which also take a program directly (by name, D147), so a block read as a block parameter means the same apart from jumps. `restore` finds the innermost region's restore through a fiber reference, so a restore outside any region runs its program unchanged; the block form there is EK2111. At a module's top level the blocks are EK1001. The words are contextual: a name followed by `{` on the same line is a TypeScript syntax error, so no code that parses today changes meaning.

## TC39 forms: blocks (2026-10-17)

**D186. `throw` is also an expression** ([throw expressions](https://github.com/tc39/proposal-throw-expressions), stage 2). In a `.vibe` file, `throw` in expression position takes a unary expression, as the proposal's grammar has it: `users.get(id) ?? throw new NotFound({ id })`, `ok ? value : throw new Invalid()`, `(id) => find(id) ?? throw new NotFound({ id })`. It parses as `(() => { throw operand })()`, so it fails exactly as the throw statement does (an `error` value joins E, a Cause rethrows) and has type `never`; the right side of `??`, `||`, `&&`, and `?:` still runs only when chosen. A statement that starts with `throw` is the throw statement. Its operand is the whole expression, as in TypeScript. In expression position, an unparenthesized `throw` on the left of a binary operator (except comma), as a conditional's condition, or as the operand of `as` or `satisfies` is refused with EK1010: only its unary operand would be thrown. Write `throw (cond ? a : b)` in a catch-expression handler to throw the selected value (S10-12); right-hand throws such as `x ?? throw e` stay legal.

**D187. `do { }` is an expression** ([do expressions](https://github.com/tc39/proposal-do-expressions), stage 1). `do { statements }` in expression position has the completion value of its last statement: an expression statement, an `if` with an `else` whose branches end in one, a `try`/`catch` whose blocks end in one, or a `throw`. A declaration, a loop, or an `if` without `else` at the end is TS1109, and a `return` inside is TS1108, as the proposal forbids it. It parses as `(() => { ...; return last })()`, so it runs where it stands, and a parameter that expects a program takes it by name (D147): `race(do { sleep("1 millis"); "cached" }, fetch())`. A statement that starts with `do` is the do-while statement.

**D188. A block after a call is its program** ([block params](https://github.com/samuelgoto/proposal-block-params), stage 1; Design tradeoff: where the block goes depends on the callee's type). In a `.vibe` file, a `{` on the same line after a name, a property access, or a call passes the block as a program: `f { block }` is `f(() => { block })`, and `f(args) { block }` is `f(args, () => { block })`, one call. Where `f` is an Effect dual, the block takes the place of its program: the checker also resolves the call against `f`'s data-first signature with its first parameter moved last and its data-last signature flattened to `(args, self)`, so `withSpan("load") { ... }`, `timeout("1 second") { ... }`, and `semaphore.withPermits(1) { ... }` infer every type parameter from the arguments and the block together. The lowering emits `f(block, args)` or `f(args)(block)` for those forms and `f(args, block)` otherwise, as in `it.effect("greets") { ... }`. When several forms fit, the data-first form wins, then the data-last, then the appended call. A block param body is a function body, so a value needs `return`. A heritage clause, `new`, and a provide block's providers keep their own `{`.

## TC39 forms: await operations (2026-10-17)

**D196. The await operations start programs concurrently** (amended by D258). `await.all x`, `await.allSettled x`, `await.race x`, and `await.any x` come from the [await operations](https://github.com/tc39/proposal-await.ops) proposal (stage 1); an object operand comes from [Await Dictionary](https://github.com/tc39/proposal-await-dictionary) (stage 3, `Promise.allKeyed`). The parser writes them as calls of the runtime's `$awaitAll`, `$awaitAllSettled`, `$awaitRace`, and `$awaitAny`, with the operand bound as `await`'s is. Each element is a program passed by name (D147), started in its own fiber; an element that is a `Fiber` or a `Deferred` already running is waited for, not restarted, and a `do { }` element (D187) is a program with statements. Each operation behaves as the `Promise` method of the same name: `await.all` is `Effect.all` with unbounded concurrency (every result, the shape kept, an object's keys in the order written, fail fast with the rest interrupted, held fibers included); `await.allSettled` is `Effect.all` with `mode: "result"` and never fails with a typed error; defects and interruption propagate; `await.race` is `Effect.raceFirst` over any number of elements (the first to finish wins, success or failure; of elements ready at once the first written wins; an empty race never finishes); `await.any` is `Effect.raceAll` (the first success; failure only when every element fails). A race over an object is EK4608. Controversial: the docs rule is "`await.x` behaves like `Promise.x`; a named Effect function keeps Effect's meaning", so `await.race` takes the first to finish while `race(...)` (D151) takes the first success. The alternative, dropping `race` from the bare functions, loses Effect's own name for the common case.

**D197. `await.race` replaces `select`** (supersedes D168). The earlier `select { case ... }` form was replaced because `case` reads as comparing a value, and "select" is not Effect's word. `select { ... }` still parses so that the checker can report EK4607 at its keyword with the replacement: `await.race [a(), b()]`, one element per case, with `do { ... }` for a case's statements. A `default:` clause has no replacement form; poll with `Queue.poll` and an `if` (or `match`). The runtime keeps `$select`, which `$awaitRace` uses.

## TC39 forms: pattern matching (2026-10-17)

All from the TC39 [pattern matching](https://github.com/tc39/proposal-pattern-matching) proposal (stage 1), under the rule that new syntax comes from TypeScript or a TC39 proposal.

**D206. `match` is an expression of `when` arms**. `match (x) { when P: v; ... default: d; }` takes the proposal's syntax: arms are tried in order, the first match gives the value, and `default:` matches anything and must come last. An arm ends with `;`, and ASI applies. `match (x) {` followed by `when`, `default`, or `}` on the same line starts a match; any other `match(...)` is a call, so a function named `match` keeps working. As in the proposal, `and`, `or`, and `not` cannot share a level without parentheses (EK4705). An arm is one expression; `do { }` (D187) gives it statements.

**D207. The supported subset**. Literals; `let`, `const`, and `var` bindings; array patterns with a rest; object patterns with shorthand bindings, quoted and computed keys, and a rest; identifier and dotted matchers; extractors with an argument list (`Option.Some(let v)`); `and`, `or`, `not`; `if (expr)` guards; `default`; and `x is P`. Deferred: regular expression and relational patterns, `async match`, and iterables in array patterns (D212, D214).

**D208. Option, Exit, Result, and primitive classes are known matchers**. `Option.Some`/`None`, `Exit.Success`/`Failure`, `Result.Success`/`Failure` compile to the module's own guard and read `value`, `cause`, `success`, or `failure`; `String`, `Number`, `Boolean`, `BigInt`, and `Symbol` compile to `typeof`. The bindings get exact types and need no runtime protocol. Controversial: the proposal resolves every matcher through `Symbol.customMatcher` at runtime, so a local variable named `Option` that shadows the module still compiles to `Option.isSome`. The alternative, custom matchers on Effect's data types, needs Effect to ship them and types the bindings loosely.

**D209. Exhaustiveness is checked at compile time for finite unions**. A match without `default` whose subject's declared type is a finite union (literals, `null`, `undefined`, `void`, and objects with a string literal `_tag`, which covers `error` classes, Option, Exit, and Result) and whose narrowed type after the last arm is not `never` is EK4701, as `Match.exhaustive` is. Over any other type, an unmatched value throws the proposal's `TypeError` at runtime (`$noMatch`). Controversial: the proposal has no static check, and a match over `number` without `default` compiles even when an arm is missing; reporting every non-`never` remainder would flag correct matches whose guards TypeScript cannot narrow. Amended 2026-10-21 (D294's note): a class pattern narrows as `instanceof` does, by derivation, so a class that only shares a handled class's fields is still left.

**D210. `or` and `not` cannot bind yet**. A binding inside `or` or `not` is EK4702. The proposal allows a binding in every alternative of an `or`; the lowering writes `or` and `not` as inline boolean expressions, which have nowhere to declare a name.

**D211. `is` binds only in an `if` or `while` condition**. `x is P` is a boolean at `instanceof`'s precedence. With bindings, it must sit in the `&&` chain of an `if` or `while` condition; the names are in scope in the rest of the chain and in the then branch or loop body. Elsewhere it is EK4703. Controversial: the proposal scopes `is` bindings to the enclosing block and the else branch too; this lowering nests the then branch inside the tests, so names cannot reach the else branch or the statements after.

**D212. Unsupported forms are reported, not misparsed**. A regular expression pattern, a relational pattern such as `< 10`, and a computed key other than a name or a literal are EK4704, whose fix is a guard: `and if (n < 10)`.

**D213. Matcher semantics**. A matcher value with a `[customMatcher]` method decides. Otherwise a primitive class tests `typeof`; another class tests `instanceof`; another function is a predicate; any other value matches by SameValue, with `0` matching `-0`. A class is a function written with `class` or one whose prototype has methods, so built-ins such as `Date` and `Map` test `instanceof`. Deviation: the proposal gives built-in constructors brand checks (`Date` matches a cross-realm date), which a runtime helper cannot write.

**D214. Lowering and its limits**. A match after `return` becomes a block whose arms return; a match statement becomes a labeled block whose arms break; any other match becomes an immediately invoked arrow function, which is a VibeLang function, so arms can call Effect functions in every position. The subject is held in a `const` that reads it once, before any arm, as `switch` reads its discriminant, and the checker narrows the subject through the `const` in each arm, as TypeScript narrows a switch's discriminant in its clauses. Limits: an arm of a match in expression position cannot `yield`; array patterns match arrays only; object patterns do not match primitives. Amended 2026-10-26: a subject that was a name, `this`, or a chain of property and literal element accesses had been used directly and read again by each test, so a getter there could select the wrong arm.

**D215. `customMatcher` and tagged errors**. The runtime exports `customMatcher`, the engine's `Symbol.customMatcher` when it has one and `Symbol.for("Symbol.customMatcher")` otherwise. `TaggedError`, so every `error` class, has a static custom matcher: `instanceof` for `is` and `when NotFound:`, and the instance as the single value for `NotFound(let e)`. Two error classes with the same tag therefore stay distinct, unlike `catchTag`.

## Catching with match (2026-10-17)

**D216. A catch clause no longer tests a failure's type** (supersedes D131). Catch the failure and test it with pattern matching (D206): `catch (e) { return match (e) { when NotFound: "missing"; default: throw e; } }`, or `if (e is NotFound) { ... }` in statement form. No special catch syntax remains. A typed clause, `catch (e: NotFound)`, still compiles as D131 describes and draws the warning EK2112.

**D217. Recovering from a whole cause matches on its exit** (supersedes D176). `match (exit(program)) { when Exit.Success(let value): value; when Exit.Failure(let cause): fallback; }`, or `if (outcome is Exit.Failure(let cause))`, sees every reason: failures, defects, and interrupts. A catch clause typed `Cause` still compiles as D176 describes and draws the warning EK2113.

**D218. A match on a caught failure is checked like any match**. An untyped catch variable has the try block's expected failures as its type (D13), so `match (e)` without `default` must handle every one of them (EK4701, D209) and then needs no rethrow; `default: throw e` passes the others on with their types, through a throw expression (D186). The function's E is what the arms let escape.

**D219. The quick fix rewrites retired clauses when the result is exact**. EK2112's fix writes one `match` when every clause is a single `return` of a value and every clause names one variable, and an `if (e is T) { ... } else ...` chain otherwise, ending in `else { throw e }` when no untyped clause followed. A clause's type becomes a pattern only when each union member names a class, such as an `error` declaration or `Schema.SchemaError`; for a type alias or an object type the warning has no fix. EK2113's fix rewrites `try { return X } catch (cause: Cause) { return Y }` as `return match (exit(X)) { ... }`; other shapes keep the warning without a fix.

## Syntax decisions: services and layers (2026-10-17)

**D220. `service class` and `control class`** (amends D128; superseded by D223). A service is `service class Users { find(id: string): User!NotFound; region: string }`, and a control operation is `control class Approval { approve(request: string): boolean!! }`. `service` and `control` are modifiers of a class declaration, as `declare` is, and the members have no bodies, as a `declare class`'s members have none; the meaning is D128's. The spelling was provisional between this, a plain `abstract class`, and D128's `service Users { }`. `abstract class` needs no new syntax but repeats `abstract` on every member; the modifier reads as a TypeScript class and keeps Effect's word, `service`. The spelling without `class` still compiled, with the warning EK2120, whose quick fix inserted `class`. D223 reverses both.

**D221. A layer is a call** (supersedes D129). `const UsersLive = Layer.effect(Users) { const seen = new Set<string>(); return { find(id) { return getUser(id) }, region: "eu" } }` passes the block to Effect's own `Layer.effect` through block params (D188), and `Layer.succeed(Users, { ... })` builds a layer with no setup. It adds no syntax of its own: D129's layer declaration was provisional. The `layer UsersLive: Users { }` declaration still compiles, with the warning EK2121, whose quick fix rewrites it into the call; its EK2104 order rule stays for that spelling.

**D222. A layer block's members are typed by its service**. The block is the effect `Layer.effect` expects, so TypeScript types the returned object against the service: `find(id)` needs no annotation, and a missing or mistyped member is TS2345 at the call, whose message chain names the member that does not fit. A member's own failures and call-time requirements must fit its contract, as in `Layer.succeed` (EK2001, EK3101). The setup's failures and requirements become the layer's, so `wire` places the layers it needs, and a `using` in the setup is released when the layer's scope closes, because Effect 4's `Layer.effect` supplies one. Not controversial.

**D223. Services and controls are written without `class`** (supersedes D220). `service Users { find(id: string): User!NotFound; region: string }` and `control Approval { approve(request: string): boolean!! }` are the spelling again, with D128's meaning. The class keyword is redundant in a service declaration. `service class` and `control class` still compile, with the warning EK2120, whose quick fix removes `class`. Layers stay calls (D221).

## Join (2026-10-17)

Using await for fibers can cause confusion with JavaScript Promises.

**D225. `join` is a keyword** (supersedes D167). `join fiber` parses as the runtime call `$join(fiber)`, which is `Fiber.join`: its value is the fiber's and its failures join E. `join [a, b]` and `join { a, b }` join every fiber of an array, tuple, or object and keep the shape; when one fails, the fibers still running are interrupted and the failure propagates, as `Effect.all` fails fast. The operand binds as `fork`'s does (D166), and the keyword form needs its operand on the same line, starting with a name, `this`, `{`, or `[` after a space. `join(` stays a call and `join[i]` without a space stays an element access, so a local or imported function named `join`, `path.join`, and `words.join(",")` keep working. A `join` on anything but fibers is EK4611, and a `join` inside a hatch's function, which is plain TypeScript, is EK4612.

**D226. A plain `await` in VibeLang code is an error**. In JavaScript `await` waits for a promise, so VibeLang keeps that meaning and gives `await` no other: `await fiber` is EK4609, whose quick fix writes `join fiber`; `await d` on a Deferred is EK4610, whose quick fix writes `d.await()`; `await` before a call that already runs is EK4601; a promise is EK4602 and waits in a hatch, `try(async () => …)`; anything else is EK4603. The await operations, `await.all`, `await.allSettled`, `await.race`, and `await.any` (D196), stay, because they follow the `Promise` methods of the same names. Inside an `async` hatch body `await` keeps its JavaScript meaning, and in one that is not `async` it is EK4604.

**D227. A Deferred waits with `d.await()`**. Method syntax (D152) already reaches `Deferred.await`, so a Deferred needs no keyword: `ready.await()` returns its value and propagates its failure.

**D228. `join`'s types reach one level**. The runtime joins through nested arrays and objects, but `$join`'s types and the EK4611 check accept an array or object only of `Fiber`s themselves. Nest joins instead.

## Self-contained hatches (2026-10-17)

Hatch code is self-contained and accepts surrounding values through explicit inputs.

**D229. A hatch's TypeScript is self-contained** (amends D148). A hatch's first argument, the function or single expression of `sync`, `try`, or `callback`, may reference its own parameters and locals, globals, prelude names, imports, and the file's `error` declarations, but no other value binding of the `.vibe` file: not an enclosing local or parameter, and not a module-level declaration. A reference to one is EK4405, an error that names the binding, and its quick fix passes the binding as an input (D230). Types are exempt. Error declarations are exempt because an error class is a plain class, and failing with one, `new BadJson({ error })`, is what a hatch most often needs from its file. Controversial because a capture is the shortest way to hand a value to TypeScript. The rule makes a hatch's function read like a standalone TypeScript function that could move to a `.ts` file unchanged, and keeps a VibeLang value from entering TypeScript unannounced. This restriction may change.

**D230. Inputs fill the first parameters**. Values reach a hatch as inputs, the arguments after its function: `sync((a, b) => a + b, 2, 3)`, `try((text) => JSON.parse(text), text)`. They fill the function's first parameters, so TypeScript types each parameter from its argument. An async function receives its `AbortSignal` after them, `try(async (url, signal) => fetch(url, { signal }), url)`, and a callback's register function receives `resume` and the signal after them, `callback((ms, resume) => …, 2)`. The compiler lowers inputs with `bind`, `Effect.sync(((a, b) => a + b).bind(undefined, 2, 3))`, so Effect's own signal argument lands after them. A single expression takes no inputs. The alternative, Effect's arguments first, `callback((resume, signal, ms) => …, 2)`, keeps Effect's parameter positions but needs a wrapper function in the lowering and moves the inputs' parameters with each arity. Inputs keep `callback`'s type arguments from being written, because TypeScript infers no type argument once one is written; the prelude type `Resume<A, E>` annotates `resume` instead: `callback((source, resume: Resume<number, Error>) => …, source)`.

**D231. `try`'s error mapper stays second**. `try(code, mapper, ...inputs)`: the mapper keeps the place D148 gave it, and inputs follow it, `try((text) => JSON.parse(text), (error) => new BadJson({ error }), text)`. With inputs first, the mapper's place would move with the number of inputs; with the mapper last, `try(f, g)` would change meaning from D148's. The compiler tells a mapper from a function input by the overload TypeScript chose: a function in second place that accepts the `unknown` error is the mapper. The runtime's `try`, which TypeScript callers and a hatch passed as a value reach, sees only values, so there a function in second place is always the mapper.

**D232. Only the first argument is TypeScript** (amends D148). D148 made all of a hatch's arguments plain TypeScript; now only the first is. The inputs and the mapper are VibeLang code: the inputs run before the hatch starts, so a call among them runs, `sync((name) => name.toUpperCase(), readName())`, and a plain foreign call or a clock read among them is EK4401 or EK4403 as anywhere in VibeLang code. The mapper is an ordinary callback that may read the file's bindings, `(cause) => new ChargeFailed({ cartId, cause })`. The function decides between sync and async: an `async` function, or one whose return type has `then`, is `Effect.promise` for `sync` and `Effect.tryPromise` for `try`; an `any` or `unknown` return stays synchronous.

Amended 2026-10-23 (release correction): the runtime's `sync` and `try`, which TypeScript callers and a hatch passed as a value reach, see no types, so they decide by the function's declaration. An `async` function that declares a parameter after its inputs gets the AbortSignal there and runs as `Effect.promise` or `Effect.tryPromise`, so interruption aborts the signal; a rest or defaulted parameter gets none, as `Effect.promise` makes a signal only for a function that takes one. Any other function gets its inputs only, and a promise it returns is awaited without a signal. Before, no function got a signal there: `const run = sync; run(hasSignal)` read `undefined`, and interruption left a `fetch` running.

Amended 2026-10-23 (direct hatches): a direct `sync` or `try` gives an asynchronous function exactly its inputs, then the AbortSignal when the overload TypeScript chose passes one and the function declares a parameter for it, the rule the runtime's `sync` and `try` follow; both call it through the runtime's `$asyncHatch`. An arrow function without a rest parameter keeps D230's `bind`, under which `Effect.promise` applies the same rule. Before, `Effect.promise` passed `undefined` into a rest parameter, so `sync(async (...xs: number[]) => xs.length, 1, 2)` was 3, and gave the signal to a parameter typed for something else, so `sync(async (a: number, b?: number) => typeof b, 1)` was `"object"`. Called as a value, `sync` and `try` still give that parameter the signal: they see no types, and `length` counts `b?` as it counts `signal?: AbortSignal`.

## Catch expressions (2026-10-17)

Borrowed from Zig's inline catch (`parse(s) catch 0`), TypeScript has no such proposal, but `catch` after an expression is a syntax error today, so no code that parses changes meaning.

**D236. `catch` is also an expression** (amended by D305 and D306). `x catch fallback` is `Effect.orElseSucceed`: the fallback is evaluated only after an expected failure, and because it is VibeLang code it may run a program itself, as `Effect.orElse`'s would. `x catch (e) => expression` is `Effect.catch`: the handler receives the expected failure, typically `getUser(id) catch (e) => match (e) { when NotFound: guest; when Timeout: cached(id); }`. The left side is passed by name (D147), so it runs inside the catch. Defects and interrupts pass through, and so does a cause that mixes an expected failure with either, as the `catch (e)` statement lets them (D13); Effect's own `Effect.catch` would recover from such a mixed cause. The parser writes `$catchExpression(() => x, () => fallback)` or `$catchExpression(() => x, (e) => expression)`, and the runtime runs it with the kernel's `catchExpected`, which the statement uses.

**D237. `catch` binds between `??` and `? :`**. It binds looser than every binary operator, `??` and `||` included, and tighter than `? :`, assignment, arrow functions, and `|>`. It associates to the left: `a() catch b() catch c` tries `b()` after `a()` fails and falls back to `c` after `b()` fails. `lookup(id) ?? "unknown" catch "failed"` applies the default inside the catch, `ok ? find(id) catch "none" : "skip"` catches in one branch, and `id |> find(%) catch "none"` catches inside the pipe's body. A handler is an arrow function, `(e) => …` or `e => …`, whose body extends as far as an arrow function's does, so a `catch` after it belongs to the handler; parenthesize the handler to chain after it. Any other right side, a parenthesized arrow function included, is a fallback. After a try block's `}`, `catch` is the statement's.

**D238. A catch expression is typed and checked as the statement is**. The value is `A | B`, A from the left side and B from the fallback or handler. E is what the fallback or handler lets escape: the handler's parameter has the left side's expected failures as its type, so a `match` without `default` must handle every one of them (EK4701, D209) and then removes them all from E, and `default: throw e` passes the rest on with their types (D186). R joins both sides'. A left side with no expected errors is EK2004; defects pass through. A try statement gets that warning only when its block runs Effects with E = `never` (D260). A hover on the keyword names the Effect function, the failures it catches, the value, and the failures that escape.

**D239. No catch expression in a hatch body**. A hatch's function is plain TypeScript (D148, D232), where `catch` is only a statement, so a catch expression there is EK2114; move it out of the hatch, or use a try statement inside. At a module's top level it runs a program, so EK1001 applies.

**D248. Where L3 and D24 disagree, the switch keeps D24 or asks** (D250 withdrawn by D251). The text-only projector decides at run time whether a call's result runs (L3, `$isRun`), and to it an `Exit` is a program. D24 decided from types that a call returning an `Exit`, a `Config`, or an error instance returns data, and D43 relies on it: `resume(Exit.succeed(value))` passes the `Exit` as data. Wherever the fork's types say data and L3 would run, the switch keeps D24's meaning or reports EK9100, which asks for an annotation. It never changes what code does without a diagnostic. So `sync(() => Exit.succeed(42))` written without a return type reports EK9100 under the switch, and `sync((): Exit.Exit<number, never> => Exit.succeed(42))` is plain (L2) and returns the `Exit` as data under both compilers. Evidence: the case `vibelang-effect-value-calls`, migrated with that annotation, and a regression case that keeps the unannotated form and expects EK9100.

**D249. A trusted contract becomes a value, `trusted(impl, [Errors])`** (amends D23). The (B) projector reads one file at a time, so it cannot see a JSDoc tag on another file's declaration, and D23's `@vibelang trusted` and `@throws` cannot reach its emit. The TypeScript file states the contract as a value instead: `export const parsePortTrusted = trusted(parsePort, [PortError])`, a public `vibelang-runtime` export that takes the implementation's parameters and returns `Effect<A, E>`, where a listed class is an expected failure and any other exception is a defect, as `$trusted` does today. The contract stays beside the function it describes, which is why D23 put it there, and TypeScript callers keep calling `parsePort`. Under D248, a dropped tag must never change behavior silently. Until the switch, the fork's checker warns at every `.vibe` call of a D23-tagged declaration whose lowering uses the tag (in an Effect function, outside boundary callbacks), with a quick fix that adds `<name>Trusted` beside the declaration and rewrites the call. A call at top level or in a plain or boundary callback is plain under both compilers, so it gets no warning. From the switch on, such a call is an error, because a `PortError` would otherwise become a defect without a diagnostic. Rejected: passing tag contracts into Project's FileContext (cross-file input to the per-file mapper, which breaks stock TypeScript tooling, the reason for (B)), and `Effect.try` at each call site (moves the contract away from the function). The cases `trust-levels` and `ch10-typescript` migrate to `trusted(...)` values, so they keep proving typed failures from TypeScript.

**D250. L3 treats an `Exit` as data** (withdrawn by D251) (amends D248). The run check `$isRun` excludes an `Exit` by its type ID, as it already excludes a `Config`, a Context key, and an error, and `$run`'s types keep `Exit<A, E>` as a value. So D24 holds in both renderings by construction: a call that returns an `Exit` returns it as data, D43's `resume(Exit.succeed(value))` passes it as data, and calling an `Exit` value still runs it. This also covers an `Exit` that only the checker knows, such as one returned by a helper imported from a `.ts` file, which a text-level diagnostic could not see. It needs no annotation and no EK9100 for `Exit`, so D248's example `sync(() => Exit.succeed(42))` is correct code under both compilers, and `vibelang-effect-value-calls` passes unmigrated. D248's rule stands for every other place where L3 and the fork could disagree. Rejected: EK9100 where the text proves an `Exit` (it misses checker-only `Exit`s, so it would violate D248), and a fork-only checker diagnostic (it does not cover stock TypeScript tooling).

**D251. At run time an `Exit` runs; the checking rendering rejects running a D24 data type** (narrowed by D254). D250 was unsound. In Effect 4.0.5, `Effect.succeed` is `exitSucceed` (`effect/src/internal/effect.ts:957`), so an ordinary succeed or fail program is an `Exit` object at run time, and excluding `Exit` from `$isRun` turned those programs into data: `lambda-forms` and `ref1-existing-service` regressed, and two helpers that return the same `Exit`, one declared `Exit<number>` and one `Effect<number>`, could not be told apart. Only the static type separates data from a program, and the executable rendering has no types. So L3 runs an `Exit` at run time, as before. The checking rendering, which TypeScript type-checks for the fork and for stock tooling alike, rejects a run position whose static type is a D24 data type, such as `Exit`, with a type error that names the annotation. `$run`'s first overload takes `T & DataEffect`, which keeps `generic<T>(x: T)` inferred as `Effect<T>`. A helper declared `Effect` runs the same way in both renderings, and a value declared `Exit` can never run silently, which is D248's rule. Rejected: keeping D250 (silent wrong results for every opaque helper that returns `succeed` or `fail`), and carrying static types into the emit (not available to a projector that reads text only).

**D252. The (B) projector keeps D152's data methods by dispatching unproven receivers at run time** (amended by D253) (implements D152 under (B)). A projector that reads one file at a time cannot always prove from text which of D152's modules declares a receiver's type: the census of the docs found 131 such method calls. They type-check through the prelude's module augmentation in the checking rendering, as the fork's D152 does. The executable rendering emits the module's function where the text proves the module, and `$method(x, "isSome", args)` elsewhere. `$method` dispatches on the receiver's TypeId to exactly one of D152's modules. As D152 requires, a value's own member of that name wins, and arrays, strings, plain objects and any value without one of those TypeIds keep JavaScript's method call, so `$method` never calls a module function on a value D152 does not cover. Unproven calls lose tree-shaking for their module function; a proven call keeps it, and the docs and examples prefer forms the text proves. Rejected: errors at unproven receivers, and passing receiver modules from the fork into Project (it breaks the content mapper's per-file model for stock tooling).

**D253. A data method whose module the run time cannot tell apart asks for an annotation** (amends D252). In Effect 4.0.5 an `Exit` carries both the Exit and the Effect TypeIds: `makeExit` builds its prototype from `ExitTypeId` and the primitive prototype, which spreads `EffectProto` (`effect/src/internal/core.ts:100-101, 531-548`). `Effect.succeed` and its siblings are Exits, and Cause errors such as `NoSuchElementError` carry both the Effect and Cause TypeIds. So `$method` dispatches an unproven receiver only when exactly one module among the call's candidates matches a TypeId the value carries. For a method name that two such modules both define (Effect and Exit: `asVoid`, `isFailure`, `isSuccess`, `map`, `mapBoth`, `mapError`, `match`; Effect and the Cause errors), an unproven receiver is a projector diagnostic that asks for an annotation or for `Module.fn(x)`, never a run-time guess (D248). Likewise an optional or uncalled access to a data method on an unproven receiver is a diagnostic, matching the fork's TS2339 and EK4501. A value's own member wins only when it is callable, and candidates are only exported module functions.

**D254. The checking rendering rejects running only an `Exit`**. The run-time check `$isRun` already tells a `Config` (its `~effect/Config` key), a Context key (`~effect/Context/Service`), and an error (an `Error` instance, or a YieldableError by its Effect identifier across realms) from a program, and keeps each as data (`effect/src/Config.ts`, `Context.ts`, `internal/core.ts`; verified in the fast-call review). So `$run`'s types keep those values as data too, matching what runs, and D251's type error stays only for `Exit`, the one D24 type the run time cannot separate from a program, because an `Exit` carries Effect's TypeId. Types and run time agree on every other D24 type, so nothing changes silently (D248), and code such as `function withFallback(name: string): Config.Config<string> { return Config.orElse(…) }` followed by `withFallback("MISSING")()` needs no annotation or wrapper. Rejected: keeping the guard on Config, keys, and errors, which makes users wrap every such value reached through a call although the run time already handles it.

## Launch audit corrections (2026-10-18)

**D256. D15 binds VibeLang's own cleanup; Effect operators keep Effect's semantics** (D22 governs). VibeLang never drops a failure from cleanup it runs itself: `using`, `finally`, scope closing, and `abandon` under interruption. This does not extend to failures an Effect operator discards by design, including `timeout`/`race` dropping a loser's cleanup failure. In Effect 4.0.5, `timeout` calls `timeoutOrElse`, which calls `timeoutOption`, which races the source against the timer with `raceFirst` (`effect/src/internal/effect.ts:3870, 3836, 3895`). `raceAllFirst` resolves on the first fiber's exit and interrupts losers on the parent's exit through `onExitUnsafe` and `fiberInterruptAll`; their exits do not join the parent's cause (`effect/src/internal/effect.ts:1668-1700`). Keep this limitation visible and pin the observed behavior with a runtime case so an Effect upgrade that changes it shows up. Report the lost finalizer failure upstream; do not fork `timeout`.

**D257. Overload ranking applies D147 per candidate and prefers passing a program by name**. Among applicable overloads, a candidate whose parameter expects an `Effect` and passes a program argument by name outranks one that would run that same argument. A running call whose result type is `never` makes no parameter applicable during ranking: it means the call fails, not that every parameter accepts it by vacuity. Thus `Effect.race(Effect.fail(a), Effect.fail(b))` selects the two-program form, passing both programs by name, instead of running the second argument as the curried form's `options`. The same rule covers `raceFirst`, `zip`, and `orElse`; a genuinely data-last call such as `pipe(x, Effect.race(y))` keeps the curried form.

**D258. `await.allSettled` never fails with a typed error; defects and interruption propagate** (amends D196). It captures every typed failure, E, as a `Result.fail`, and propagates defects and interruption exactly as `Effect.all(…, { mode: "result" })` does. A defect is a bug, and interruption is the caller's cancellation, rather than an outcome to settle. In Effect 4.0.5, `Effect.result` calls `matchEager` with `onFailure: Result.fail`; `findError(cause)` leaves a cause with no typed failure, including defect-only and interruption-only causes, unchanged (`effect/src/internal/effect.ts:3534, 3718-3745`). `all` applies `result(effect)` in mode `"result"` (`effect/src/internal/effect.ts:4697`). Keep the per-element `Result` type; an `Exit` per element would expose Cause to every caller. Pin defect and interruption propagation with runtime cases.

**D259. The language server treats `null` as absent for optional client fields**. In client-to-server messages, the VibeLang language server reads `null` as absent wherever LSP 3.17 permits the client to omit the field. It never sends `null` for an optional field itself, and required fields stay strict. This tolerates Zed 0.195.3's actual payload so VibeLang works by default in that editor. Implement the tolerance in the fork's LSP decoder, retain the payload as a fixture, and report the spec violation upstream to Zed so the tolerance can eventually be retired.

**D260. Plain contracts keep JavaScript try/catch** (amends D37 and D54). A function with a plain contract keeps JavaScript's `try`, `catch`, `finally`, and `throw`: its catch receives every exception its try block throws, as `unknown`, exactly as TypeScript does. The lowering inserts no `$caught` rethrow and no expected-failure wrapper there. Defects are an Effect-level notion: an exception becomes a defect only where it escapes a plain function into an effectful caller, unchanged. An Effect region still catches expected failures only and lets defects and interruption pass through (D13). EK2004 applies to a try statement only when its block runs Effects and E is `never`; its message says defects pass through the catch, rather than claiming the catch can never run. compiler regressions pin coercion through a throwing `Symbol.toPrimitive`, a throwing getter, a revoked Proxy, and a throwing prototype lookup; an Effect try with E = `never` still warns and propagates a defect at runtime. Amended 2026-10-23 (release correction): D282 supersedes this decision's JavaScript `throw` and `catch`. In a plain function `throw` is a typed failure, one that can escape it is EK2003, and its catch receives typed failures only; EK2004's text stands.

## Type checking and lowering corrections (2026-10-18)

**D261. Projects may trust TypeScript packages by name** (extends D22). `compilerOptions.vibelang.trustedPackages` lists package-name globs, for example `["@smthrs/*"]`, matched against the nearest `package.json` name, including workspace packages outside `node_modules`. Globs match the whole name: `*`, `?`, and character classes match within a slash-delimited segment. A matching package receives D22's terms: an export that does not return an Effect is a synchronous call whose exceptions are defects, its Effects run where called, and calls into it do not report EK4401. The option does not list expected failures: D249's `trusted(impl, [Errors])` remains their per-function contract. Without a matching option, foreign calls keep EK4401.

**D262. An explicitly Effect-typed top-level const holds a program** (extends D147 and D103). At a module's top level, a `const` whose declared type is an Effect is a program position: `export const migrate: Effect.Effect<void, E, R> = Effect.suspend(() => …)` builds the cold value and runs nothing when imported. Running `migrate` later executes its body. Calls retain their Effect value at the top level; operands still follow D147's parameter positions. The annotation must be on the const declaration, rather than inferred or asserted on its initializer. Without it, the same top-level Effect call still reports EK1001 (D103); mutable bindings and non-Effect annotations do not opt in.

**D263. Plain contracts keep JavaScript throws and calls** (completes and amends D260). A function with an explicit non-Effect return annotation, or a plain contract inferred by the checker, is plain JavaScript. Every `throw` in that function, inside or outside `try`, is JavaScript's throw: it does not run an Effect, infer an error channel, or cause EK2003. Its declaration keeps its plain return type, and its emitted function returns a value or throws, never an Effect object. Calls whose types return non-Effect values, including plain-function parameters and trusted or untrusted TypeScript imports, are JavaScript calls there: no EK4401 and no Effect inference. Exceptions propagate unchanged and become defects only where they escape into an effectful caller. Running an Effect under a plain contract remains EK2003. compiler regressions A-1, B-4, and E-1 pin synchronous validation and callback APIs.

**D264. Shared web-standard globals keep their names** (amends D146). Web-standard globals defined by every runtime VibeLang targets win over effect-root names, as JavaScript's built-ins do: `Request`, `Response`, `Headers`, `URL`, `URLSearchParams`, `TextEncoder`, `TextDecoder`, `AbortController`, `AbortSignal`, `Blob`, `FormData`, `structuredClone`, and `fetch`. Of effect@4.0.5's root names, only `Request` collides today: `new Request("https://x.test")` constructs the web Request, and Effect's module requires `import { Request } from "effect"`. DOM-only globals such as `Option` still lose to Effect's modules. Explicit imports and local declarations keep precedence.

**D265. Contextually Effect-typed object fields hold programs** (implements D147, no new rule). D147 already names the fields of a record among the places where an expected `Effect` takes a program by name (spec 213), as D262 is D147's top-level case. The compiler now applies it to every object-literal field whose contextual type is an Effect: a service implementation's member, a parameter's record field, or a field of a declared type. `Layer.sync(Journal, () => ({ read: Effect.sync(() => …) }))`, `make({ read: work() })`, and `const journal: { read: Effect.Effect<number, never, never> } = { read: work() }` build values and run none of the stored programs. Running the field later executes the program, on every invocation. A field whose contextual type is not an Effect keeps the ordinary rule: a program call runs where it stands. Operands retain their ordinary program positions, as in D262.

**D266. EK diagnostics belong to VibeLang files** (supersedes D242). A `.ts`, `.tsx`, `.mts`, or `.cts` file keeps TypeScript's verdict: no VibeLang-specific EK diagnostic attaches there, regardless of project diagnostic options or inline directives. The shared EK diagnostic constructor enforces the source-file boundary for every registered code. This removes EK4801, EK4819, and EK4820 from ordinary TypeScript; other EK rules already enter through VibeLang-only checks, including EK4813's replacement of TS2339. Ordinary TS errors remain. Editor hints may be offered separately. The Ownership.ts terminal `yield* logWarning.pipe(annotateLogs, andThen(onLapse), andThen(Effect.interrupt))` is valid TypeScript; the identical generator in `.vibe` still receives EK1002 because `function*` there declares a producer.

**D267. A tagged template runs like a call of its tag** (extends D24 and D147). A tagged-template expression whose return type is Effect itself runs where a call would run, in a statement or an expression, and evaluates to its success value. Its failures and requirements join the enclosing program's channels. A program position passes it by name under D147; hatches keep TypeScript, and positions that cannot run follow the call diagnostics, including EK1001 at module top level and EK4301 in a synchronous callback. Plain tags and D24 data results keep their JavaScript meaning. A discarded structured Effect result (such as SQL Statement) reports EK4301 and asks for an explicit call of the result or an Effect return annotation; an Effectful template in an unlowerable position also reports EK4301. The projector also runs an explicit `Effect.service(Key)` lookup: Effect returns the key itself at run time, which this call runs rather than keeping it as D24 data. Both compiler renderings preserve native tag invocation, its receiver, template object, and substitution order. Never emit an Effect-valued template cold in a position where a call would run. Evidence: `tagged-template-runs`, including the fake SqlClient migration shape that left Smithers' tables uncreated.

**D268. Purity crosses files with the function**. A provably pure export carries a runtime marker, `f[$direct] = f$direct`, in both the native compiler and (B), including local named exports and aliases. Re-exports and import-then-export preserve the same function object. The checking projection merges a phantom namespace containing `$plain: $Plain<typeof f>` into the exported function; its plain call signature survives aliases and barrels. Parity strips only this generated namespace, retaining the public Effect signature. In plain callback positions an importer passes `$adapt(f)`: its branded overload selects the brand's plain signature, and its unbranded overload is `<F>(f: F) => F`, preserving generics without a conditional inference boundary. Known unbranded Effect imports stay in their original contextual positions. At runtime it is `f[$direct] ?? f`; correctness never depends on types. Without a marker the function remains an Effect function. Evidence cases: `plain-export-lists` maps to `[2, 4]`, `plain-imports` maps to `[3, 6]`, and an impure import running `Effect.log` retains its Effect behavior.

**D269. A function declared to return an Effect may return a program; a typed `const` holds one at any scope** (extends D7, D262, and D265; D24 and D147 unchanged). In a function whose declared return type is `Effect<A, E, R>` (its annotation, its binding's annotation, or for a lambda the declared member or parameter type it is checked against, D44), a `return` whose expression is a program that TypeScript would reject as an `A` returns that program unrun. A program is a function literal with no parameters, converted as D7 converts it, or a non-call expression whose type is `Effect` itself (D24). Such a function is a factory: its body runs when it is called, as plain JavaScript under D263, and running its result runs the program, every time. Every path of a factory returns a program (EK2116); its body runs no Effect and looks up no service (EK2115); it has no plain variant, so D9 rejects it where a plain function is expected (EK4301). A `const` whose declared type is `Effect` holds its initializer in any scope, as D262 holds it at the top level and D265 in a declared field: `const built: Made = make(config)` calls `make` now and runs nothing. VibeLang callers do not change: a call to a factory runs it (D24), is passed by name where a program is expected (D147), and is held where a declared Effect type holds it. Only TypeScript callers and held programs see the two phases, and the phases are TypeScript's. Code that compiles today keeps its meaning: each new form is TS2322 today, and where `A` is a type parameter that the call infers, as in `Effect.suspend(() => () => 1)`, the returned function stays the value. Rejected: inferring the phases from a plain prefix (it silently moves work in existing exports to call time and recursion onto the JavaScript stack), a `hold(…)` marker (the quotation operator Chapter 5 rules out), and a recipe alone (it unblocks 1 of 29 files). Evidence: `smithers-lanes/a4-probes-opus/`. 2026-10-23 (real-world migration): the initializer is held through parentheses, a type assertion, a `satisfies` clause and a non-null assertion, which leave its value as it is, so `const p: number!! = make() as any` calls `make` and runs nothing; before, such a wrapper ran the call. Evidence: `held-assertion-initializer`. 2026-10-23 (real-world migration): a conditional initializer is held too, `const p: number!! = ready ? make() : Effect.succeed(0)`: its value is one of its branches, so neither branch runs at the const, only the condition is evaluated there, and the chosen branch runs each time the const is run. Before, the branch ran at the const, and its value did not fit the declared type (TS2322). Evidence: `held-conditional-initializer`. 2026-10-23 (real-world migration): a pipe initializer is held too, `const p: number!! = make() |> Effect.map(%, f)`: the pipe's value is its body's, so the body builds the program and the left side keeps its parameter position (D154); at a module's top level a left side whose topic lands where a program is expected is not EK1001, as a call argument there is not. Before, the body ran at the const, and at the top level both calls drew EK1001. Evidence: `held-pipe-initializer`, `held-pipe-initializer-returned`, `held-pipe-initializer.fail`. 2026-10-24 (real-world migration): an unannotated factory lambda whose returns TypeScript types as an Effect, as `() => Effect.void` is, keeps TypeScript's type where the declared program type names the candidate's type parameters, as `R2` in `(a: A) => void!!R2`: it took the declared type, so inference read `R2` from `R2` and the call's type and declaration named an unbound `R2`. The same holds for such a lambda in a branch of a conditional argument, `run(watching ? observe : () => Effect.void)`, which takes the argument's contextual type (2026-10-24, real-world migration). Case `factory-lambda-infers-channels`.

**D270. A union consisting entirely of Effects runs where it stands** (clarifies D24 and D147). A call whose type is a union in which every member is Effect<A, E, R> itself counts as an Effect for D24 and D147. It runs where it stands; its success is the union of the members' successes, its error channel the union of their errors, its requirements the union of theirs. A union that mixes an Effect with a non-Effect, or with a structured Effect subtype, is not an Effect and stays data. The checker's call types, the execution plan, and the lowering share one predicate. Evidence: `union-effect-calls` and `union-effect-channels.fail`.

**D271. An explicit JavaScript iterator contract keeps a JavaScript generator** (extends D263 to generators and amends D26). A generator function (`function*`, `async function*`) whose explicit return annotation is a JavaScript iterator type (`Generator`, `Iterator`, `IterableIterator`, `Iterable`, `AsyncGenerator`, `AsyncIterator`, `AsyncIterableIterator`, `AsyncIterable`) is plain JavaScript: it compiles to the same generator TypeScript would, and its `yield` is JavaScript's. A generator function with no annotation, or one annotated as a `Stream`, keeps VibeLang's stream-producer form. JavaScript iterator contracts preserve `.next()`, spread, `yield*` delegation and its return value, throws and catches, and async iteration with `for await`. EK1002 still rejects an unannotated producer passed to a JavaScript generator API; an explicitly iterator-annotated generator may be passed to that API. Evidence: Smithers mcp McpClient cooperative coroutines silently returned Streams despite their `Generator` types, so `.next()` died at runtime; cases `plain-generator`, `plain-async-generator`, `generator-stream`, and `plain-generator-yield.fail` pin the ruling and TypeScript's invalid-yield diagnostic.

**D272. A curried topic-only pipe stage keeps method-pipe inference** (extends D154). A stage `g(%)` whose callee `g` is itself a call expression, as in `x |> f(args)(%)`, types and lowers exactly as `x.pipe(f(args))`. The stage receives the method pipe's contextual type, preserving data-last Schema combinators whose outer call infers the input schema from that context. The parser normalizes this form before checking and lowering; both compiler renderings emit the method call. Other topic forms retain D154/D155, including extra arguments, member reads on the topic, and additional topic references inside the stage factory. The left side must call nothing (no call, tagged template, or `new` outside nested functions), and every earlier stage of the chain must be such a stage: a call there may run a program (D24), and `.pipe` would then reach its result instead of the program, so `load() |> Effect.map(f)(%)` keeps D154 and passes `load()` by name. A function literal on the left, `(() => { ... }) |> f(args)(%)`, is a program passed by name as well, since a function has no pipe method (real-world migration, 2026-10-24). Bind a schema built by a call first: `const s = Schema.NullOr(Schema.String)`, then `s |> f(args)(%)`.

**D273. Block-param calls accept ordinary postfix operations** (clarifies D188). A block-param call is a primary expression like any call: member access, element access, and another call may follow its closing brace. Thus `Layer.unwrap { return Layer.empty }.pipe(Layer.fresh)` parses like the corresponding parenthesized program argument. Parsing resumes the ordinary call/member loop after the block; D188's existing argument placement and block boundaries stay in force. Invalid members, indices, and calls on the result keep TypeScript's diagnostics.

**D274. A single-result Effect body returns its Effect without a generator** (amends D36 and D104). When an Effect function's lowered body is empty or one return, and every call in it that runs is in a result position (through conditionals, commas, and parentheses), the function returns that Effect: `Effect.suspend(thunk)` when a result runs a program, `Effect.sync(thunk)` when every result is a value, or `Effect.void` for an empty body. A value result beside a program result becomes `Effect.succeed(value)`, as for by-name results (D147). The body still runs each time the Effect runs, a throw in it is still a defect, and nothing in the thunk can capture or park, so the frame invariant holds. The thunk is an arrow, so `this`, `arguments`, and `super` are the function's, and it is the property of an object literal named after the source, so a stack frame reads `PrimitiveImpl.<name>` at the `.vibe` line (Effect calls the thunk as a method). Functions with a default or destructured parameter, async and generator functions, traced functions, and handler clauses keep the generator. Evidence: `Effect.fnUntraced` costs every call two run-loop operations more than the TypeScript a twin replaces (suspend, iterator, final success), and Effect yields every 2048 operations, so in the agent/harness twin the supervisor fiber ran inside CellTurn's last frame and judged it (4 failures, A-12's extra evaluator request). With D274 the twin fails exactly the tests TypeScript fails at budgets 1024 (11), 1792 (4), and 2048 (none). Cases `debug-stack` (the thunk's frame), `vibelang-lower`, `vibelang-infer`, and `vibelang-concise-comments` pin the emitted forms.

**D275. VibeLang settings may sit at the tsconfig's top level** (amends D34). A `vibelang` object at the top level of `tsconfig.json` holds the same settings as `compilerOptions.vibelang`, with the same validation, and a config that `extends` another inherits them as it inherits compiler options. TypeScript 5.x, typescript-eslint, and editors' TypeScript servers reject `compilerOptions.vibelang` as an unknown compiler option (TS5023), so a VibeLang project's tsconfig broke every stock tool that reads it; they ignore an unknown top-level key. The docs show the top-level form; `compilerOptions.vibelang` stays accepted for existing projects. Evidence: `@smthrs/fs`'s ESLint target failed with TS5023 until its settings moved to the top level.

**D276. dprint formats .vibe files through a process plugin that writes them as TypeScript**. The `vibelang` package ships a dprint process plugin, `npm:vibelang/dprint-plugin.json`, which is the native compiler started with `--parent-pid`. For each `.vibe` file it parses the file, writes each VibeLang form as TypeScript of the same shape, asks dprint to format that with the configuration's own TypeScript plugin and `typescript` settings (a host format request), and writes the result back: `A!E!R`, `mutable x`, patterns, and headers such as `provide X` become identifiers of the same width; a block param `f(args) { }` becomes `f(args)(($v) => { })`, which dprint lays out as Effect's `Effect.fn(name)(body)`; `match` becomes an object literal whose properties are the arms, so `catch (e) => match (e) {` stays on one line; `x catch y` becomes `x.$v(y)`, so a line break before `catch` stays; `|>` becomes `||`; `fork`, `join`, `throw`, and await operations become `void`; `is` becomes `in`; `provide` and mask blocks become labeled blocks; `error` and `schema` become type aliases and `service` and `control` classes; extra try clauses become labeled blocks glued back after formatting. A module declaration (D283) keeps its head, which TypeScript reads as a namespace, and its body first formats as a `.ts` file of its own, since dprint does not sort a namespace's imports, before the file's pass indents it inside the braces; an identifier specifier, `from text`, becomes the string `"./$vtext"`, which sorts with relative imports. The parser records each form's tokens for this (`parser.ParseVibeLangSyntax`), since the tree holds only the TypeScript a form abbreviates. A file whose result would not parse to the same tree, each module body's tree included and parentheses, the braces around an if or loop body of one statement, and the order of imports and re-exports aside, fails instead of changing; so does a file with a syntax error or a comment inside a form's own tokens. The superseded `layer` declaration and the retired `select` stay as written. Rejected: a wasm plugin (dprint's wasm ABI and the size of the Go compiler), dprint-plugin-exec with a nested dprint run per file (a second configuration and a process per file), the language server's formatter (TypeScript's formatter, not dprint's style), and a new formatter (it would not follow the repository's dprint settings). Not controversial.

2026-10-21 crash fix: language-server document formatting reuses D276's reversible TypeScript projection, with the editor's TypeScript formatting settings. It no longer walks the synthesized checker tree, whose match-arm token ranges overlap. dprint remains the formatter that follows the project's dprint configuration.

**D277. ESLint lints `.vibe` files through the compiler's ESTree** (amends D35). `vibelang/eslint`, an ESLint parser in the `vibelang` package, runs `vibelang --estree`, which converts the VibeLang parser's tree to ESTree (`internal/vibelangestree`). TypeScript forms convert as `@typescript-eslint/typescript-estree` 8 converts them, so typescript-eslint's rules and the plugins that read TypeScript apply unchanged; the test holds the two to the same output node for node on every `.ts` file in this repository, and a run over Smithers' 8,524 `.ts` files found one difference, now fixed. The forms whose TypeScript long form would mislead a rule take node types of their own: `VibeEffectType` for `A!E!R`, `VibeInferType` for D57's `infer` outside a conditional type, `VibePipeExpression` and `TopicReference` for `\|>` and `%`, `VibeCatchExpression`, `VibeProvideStatement` and `VibeServiceProvider`, and `VibeMaskStatement`. A pipe is not a `BinaryExpression`, as Babel has it, because a pipe statement runs its body and `no-unused-expressions` would report it. Every other form keeps the TypeScript the checker reads, so a block param starts its own code path and an `error` is a class. A module declaration (D283) is `VibeModuleDeclaration`, its `id` and a `TSModuleBlock` whose statements convert from the body's own source file as a `.ts` file's do (the differential test holds a body to typescript-estree too), and scope analysis gives the body a module scope of its own beside the file's, so a name both declare is no redeclaration and a file name the body reads is undefined. An identifier specifier, `from text`, is an `Identifier` whose `value` is its name, never the `./main.vibe.text.js` the compiler resolves. Names the parser writes for the checker are marked `synthesized` and kept out of scope analysis; a typed catch clause's `$caught`, a handle clause's `$performed` chain, a match statement's label, and a schema's interface are left out. Ranges are UTF-16 offsets into the `.vibe` text, and the tokens and comments are one scan of the source, so reports, fixes, and `eslint-disable` comments land on what the author wrote. Rules that need type information do not run on `.vibe` files, as D35 has it: no TypeScript program loads one. Rejected: linting the TypeScript 7 projection (`packages/ts-mapper`), whose lowering (`$gen`, `$run`, `$use`) changes the shapes rules match and has no source position for most of what it writes; rebuilding TypeScript 5 nodes for typescript-estree's own converter, which walks token children that synthesized nodes do not have; and switching Smithers to Oxlint, whose built-in TypeScript parser rejects VibeLang syntax and which accepts no custom parser (D35 assumed VibeLang added no syntax). ESLint's custom parser interface is the one vue-eslint-parser and svelte-eslint-parser use. Evidence: `@smthrs/fs`'s lint target checks its `.vibe` sources with the repository's rules and fails on a seeded violation; `packages/compiler/test/eslint`.

**D278. Declarations that stand for classes are classes** (amends D126 and D128). `error`, `service` and `control` declare named TypeScript classes. The keyword supplies only the base class and what VibeLang derives from the name; everything else a class declaration accepts keeps its TypeScript meaning, and the transform lowers the declaration to that class. For `error` this includes `abstract`, `extends` another error, `implements`, constructors with `super`, methods, accessors, `override`, static members and private members, so `SmithersError` with its validating constructor and `toJSON` is an `error` declaration. Two rules are VibeLang's own. Every `error` class, a subclass included, is tagged with its own name: `catchTag("IntegrationError")` matches the subclass, and `is SmithersError` and `match` match the whole family through `instanceof`. A tag is the bare class name, never qualified by package and module as a service key is (D93), because `catchTag("NotFound")` is how Effect code names a failure; two packages that declare `error NotFound` share the tag and are told apart by class. Behaviour that is not idiomatic Effect is dropped rather than given syntax: a base error renamed at construction (`new SmithersError(…, { name: "AdapterError" })`) becomes a subclass. Services and controls keep D128's EK2103 for a member with a body, because an Effect service implementation is a plain object that would not inherit it. Class-based declarations preserve ordinary TypeScript class behavior through their generated classes. The goal is to retain idiomatic Effect behavior. Evidence: today's parser rejects `extends`, `implements`, constructors, methods and static members in an `error` (TS1128, TS1005, TS1434), which kept `@smthrs/errors`' `SmithersError` a 219-line `Data.Error` class.

**D279. `schema error` declares an error that serializes** (extends D126, D133 and D278). `schema error FsError { code: Code; method: string; description: string; path?: string }` is short for `class FsError extends Schema.TaggedError<FsError>()("FsError", { code: Code, method: Schema.String, description: Schema.String, path: Schema.optional(Schema.String) })`. Fields map to schemas as a `schema` declaration's do (D133), and D278's class rules apply: `extends`, constructors, methods, and a tag of its own per class. A field whose type has no schema, such as a function, is a compile error that names the field. The tag is the bare class name (D278). Where code has already persisted an error under a qualified tag such as `"flows/fs/FsError"`, the package that reads those records keeps them readable by also accepting the old tag when decoding; that is data compatibility in the package, not syntax. Evidence: Smithers declares `Schema.TaggedError` in 327 files and `Data.TaggedError` in 147, and 228 of the Schema tags are qualified, so without this form most of its errors would stay Effect's TypeScript class form in `.vibe`.

**D280. `schema Name = <type>` declares a schema of any mapped type** (extends D133). The alias form writes the schema of a type with D133's mapping, unchanged: `schema Code = "root_missing" | "read_failed"` is short for `const Code = Schema.Literals(["root_missing", "read_failed"])` and `type Code = typeof Code.Type`, and the same holds for a union of other forms (`Schema.Union`), arrays, tuples, `Record<K, V>`, object types and named schemas. One name is both the schema and its type, as with the struct form. Refinements and transformations stay `Schema` constants, as D133 has it, and a type outside the mapping is EK2109. Evidence: Smithers writes `Schema.Literal` or `Schema.Literals` 1,666 times, most beside a hand-written type of the same union.

**D281. `service Name: Type` declares a service of any shape** (extends D128, D223 and D278). `service Search: SearchApi` is short for `class Search extends Context.Service<Search, SearchApi>()(key) {}`, with the key derived as for every service (D93). `Type` is any type: an interface declared elsewhere, a primitive (`service Prefix: string`), a function type. The body is optional and holds only static members, such as a layer; an instance member there is EK2103, as D278 keeps for services. Reading is unchanged: `Prefix()` returns the implementation (D90) and `Search.find(q)` calls a member (D41, D90). Evidence: Smithers declares 103 services as `Context.Service<X, Service>` with the interface beside them, 8 with a plain `string` shape, and about 60 with other named shapes; the fs rewrite had to wrap a string service in an object member, which changed every caller.

2026-10-21 crash fix: a shape cannot refer to its declared service key, directly or through a named shape (EK2103). This includes `service X: X`, `typeof X`, `ReturnType<typeof X>`, and `keyof typeof X`; name the implementation's type instead. The check resolves names before constructing the base type, so locally shadowed names and property names remain valid.

**D282. `throw` always fails; plain functions never fail and need nothing** (supersedes D263, amends D260 and D67). In a `.vibe` file, `throw` is a typed failure everywhere outside a hatch, and `try`/`catch` keep VibeLang's meaning. Only a hatch (`sync`, `try`, `callback`), whose function is plain TypeScript, has JavaScript's `throw` and `catch`. A function with a plain return annotation (D67) is plain JavaScript because it never fails and never needs a service: a `throw` in it is a compile error, as running an Effect in it already is (EK2003), and the fix is an Effect contract (`A!E`) or a hatch. Exceptions thrown by TypeScript code it calls still propagate unchanged and become defects where they reach an effectful caller. To catch such an exception, use the `try` hatch. Throw keeps one meaning throughout VibeLang; plain functions never fail or need services. Reading any `.vibe` code as Effect code is never wrong. Amended 2026-10-23 (release correction): a constructor, an accessor and a class static block run as plain JavaScript wherever they stand, as a module's top level does, so they never fail either. A throw that can escape one is EK2003, and EK1001 at a module's top level; a throw that their own catch handles stays inside. Code that must throw a JavaScript exception, such as a test's throwing getter, belongs in a `module` declaration (D283). Evidence: `plain-code-throw.fail`, `plain-code-throw-caught`. 2026-10-25 (real-world migration): EK2004 also warns where a plain function's try block can fail, so its catch runs, and the block calls TypeScript code whose exception passes through that catch: an untrusted function, a tagged declaration without `@throws`, or a trusted package's export whose name says it throws in Effect's API, one that ends in `Sync` or has `OrThrow` in it. Ported from TypeScript, whose catch received every exception, `try { return Schema.decodeUnknownSync(Schema.String)(JSON.parse(text)) } catch { return undefined }` caught `JSON.parse`'s SyntaxError (D101) and threw the decoder's SchemaError, and `JSON.parse(JSON.stringify(identity(schema)))` threw the `.ts` helper's exception, both with no diagnostic; before, EK2004 warned only when the try block could not fail at all. It reports the first such call of each try block, and its note names `Result.try` and a `module` block, whose catch is TypeScript's. Calls of built-ins are not reported, though their exceptions pass through too (D101): a block of them would warn at every array method. The catch itself is unchanged, as this decision rules. It fires in one of the 496 acceptance cases on `main`, `plain-throw-caught`, at the call whose exception that case shows passing through (its expected diagnostics now list it), and none of the 747 documentation blocks. Cases `plain-catch-passing.fail`, `plain-catch-result-try`.

**D283. A `module` declaration escapes to TypeScript** (2026-10-21; with D148 and D229 the escapes from VibeLang; syntax from TC39's [module declarations](https://github.com/tc39/proposal-module-declarations)). `module text { export function clean(value: string): string { … } }` declares an inline module whose body is TypeScript, checked and compiled as a `.ts` file would be: JavaScript's `throw` and `catch`, `async`/`await` and platform APIs mean there what they mean in TypeScript. Its exports are reached only through an import, `import { clean } from text`, so a hatch may use them as it uses any import (D229). The module is self-contained: it imports what it needs itself, its relative specifiers resolve from the `.vibe` file's directory, and it cannot read the `.vibe` file's own bindings. In a `.vibe` file `module` never means a TypeScript namespace. The module form provides a TypeScript escape after D282 limited JavaScript's `throw` to code that has escaped to TypeScript.

## TypeScript-style Effect forms (2026-10-21)

TypeScript-style constructs that have a VibeLang form should draw a warning and an automatic fix. D284-D290 make each such construct a warning with a quick fix, and D291 applies the fixes to a project. They write the forms the parser accepts today; D278-D281, decided the same day, add forms (classes in `error` declarations, `schema error`, `schema Name = type`, `service Name: Type`) that widen these rules once the parser accepts them, as each entry says. All eight codes, EK4830-EK4837, are lint in D241's sense: warnings by default, adjustable in the `vibelang` setting `diagnostics` and by `@vibelang-diagnostics` comments, and never errors that change emit or the exit status. A fix is offered only where the VibeLang form keeps the program's meaning; where it would not, the warning says what would change and offers none; where VibeLang has no form, nothing is reported. Every fix comes from one plan that also words the warning (`tsforms*.go`), so the editor, the CLI note, and `--fix` cannot disagree. Measured on the migrated Smithers packages at the T2 base (`@smthrs/errors` and `@smthrs/fs`, 27 `.vibe` files): EK4830 0, EK4831 1, EK4832 2, EK4833 9, EK4834 11, EK4835 4, EK4836 0, EK4837 1. `vibelang --fix` applied 26 fixes in 9 files and left the two without one; both packages still type-check, `@smthrs/errors`' suite passes (65 tests), and `@smthrs/fs`'s passes (197 tests) when its `.vibe` suites load one copy of vitest, as before the fixes. The three `throw new Error(…)` it wrote from `Effect.fail(new Error(…))` draw EK4804, which `Effect.fail` hid.

**D284. An error class that an error declaration writes draws EK4830, and a Schema error class EK4837**. A class that extends `Data.TaggedError(tag)`, the prelude's `TaggedError(tag)`, `Data.Error`, or `Schema.TaggedError<Self>()(tag, fields)` with an empty body, no `implements` clause, and no modifier other than `export`, draws the warning. The fix writes `error Name<T> { fields }` in place of `class … {}`, keeping `export`, the type parameters, and the JSDoc above, and dropping the fields' `readonly`, which every error field already is (D134). It applies only when the base is a TaggedError, the tag is a string literal equal to the class name, and the fields are an object type written in place: then the declaration is the same class, `TaggedError` being `Data.TaggedError` with a custom matcher (D3, D215). It removes the import of `Data` or `effect/Data` when the class was its last use. Without a fix, the note says what a declaration would change: a tag other than the name would become the name, `Data.Error` would gain a `_tag`, and fields from a named type must be written out. A Schema error class draws EK4837 instead, also without a fix: a declaration would stop it being a Schema (decoding, encoding, and the checks at construction) and, with a tag other than its name, change its tag. D279's `schema error` is the declaration that writes a Schema error; until the parser accepts it, EK4837 has no fix, and with it the fix applies when the tag is the class name and every field maps as D286 maps a struct's, while a qualified tag such as `"flows/fs/FsError"` still changes, the data-compatibility step D279 leaves to the package. It has its own code so that a project whose errors are Schemas by design can turn it off meanwhile and keep EK4830. A class with members, a constructor, decorators, or another base draws nothing for now: D278 gives an `error` declaration everything a class declaration accepts, but the parser does not accept it yet, and the rule widens to those classes when it does. Evidence: cases `tsforms-errors` and `tsforms-errors-fixed` return the same result; `@smthrs/fs`'s `FsError` (a Schema error tagged "flows/fs/FsError") draws the warning without a fix, and `@smthrs/errors`' `SmithersError` (a constructor and members) draws nothing.

**D285. A Context.Service class draws EK4831** (D308 made the fix write a member's Effect type as `Effect<…>`, and D309 restores the `!` form). `class X extends Context.Service<X, Shape>()(key) {}` draws the warning when Shape is an object type. The fix writes `service X { members }` when Shape is an object type written in place, the class has no type parameters, members, `implements` clause, or `make` option, and every member is a property, which becomes a value member, or a method whose return type is an Effect type, which becomes an operation with the `!` form of that type (D127), as a member without a body must write its contract (EK2101). A comma between members becomes a line or a semicolon. The declaration's key is derived from the package, the module, and the name (D93), so the written key string goes away: lookups through the class are unchanged, because providing and requiring both use the class, but the key appears in "Service not found" messages, and a `Context.Service` declared elsewhere with the same string would no longer share its slot. The note says what the key becomes. Effect's own `deterministicKeys` rule rewrites keys in the same spirit. A shape that is a named type draws the warning without a fix, since the declaration needs its members written out; static members also refuse the fix; a shape that is not an object type, such as `Context.Service<Port, number>`, draws nothing. D281's `service Name: Type` writes both of those, and the fix extends to them, keeping the class's static members as the declaration's body, once the parser accepts it. Evidence: `tsforms-services` and `tsforms-services-fixed`; `@smthrs/fs`'s `FlowInvoker`, whose shape is the exported interface `Service`, draws the warning without a fix.

**D286. A constant that holds a Schema.Struct draws EK4832**. `const X = Schema.Struct({ … })`, a single `const` binding without a type annotation, exported or not, at any scope, draws the warning when a `schema` declaration (D133) writes the same struct. The parser writes a declaration's fields back into Schema calls, so the fix writes each field's type from its schema and applies only when every field maps back exactly: the keyword schemas (`Schema.String` is `string`, `Schema.Null` is `null`, and so on), `Schema.Literal` of a literal, `Schema.Literals` of two or more, `Schema.Union` of two or more members that are not all literals and not unions, `Schema.Array`, `Schema.Tuple`, `Schema.Record`, a nested `Schema.Struct`, `Schema.optional` and `Schema.mutableKey` around a field in the order the parser writes them (`name?:` and `mutable name:`), and a name or a dotted name of any other schema, which a field names as a value, as in `count: Schema.Finite`. The declaration also declares the interface X, the struct's Type, so the fix applies only when no other type of that name is in scope, or when the only one is the struct's own type written beside it with the same export: `type X = typeof X.Type`, `type X = Schema.Schema.Type<typeof X>`, or an empty interface extending the latter, which it removes. A type alias becomes an interface, which has no implicit index signature; `vibelang --fix` refuses the rewrite where that adds an error. A check, an annotation, a pipe, `Schema.optionalKey`, `Schema.NullOr`, a spread, a computed key, or a comment keeps the constant and draws nothing: no declaration says the same. D280's `schema Name = <type>` extends the rule to a constant that holds any schema the mapping writes, such as `const Code = Schema.Literals([…])` beside `type Code = typeof Code.Type`, once the parser accepts it. Evidence: `tsforms-schemas` and `tsforms-schemas-fixed` decode the same values and refuse the same input.

**D287. An Effect type written with its type arguments draws EK4833** (amended by D308, which narrows it to `Effect.Effect<…>`, and by D309, which keeps that scope and restores the `!` form in the fix). `Effect.Effect<A, E, R>`, the prelude's `Effect<A, E, R>`, or an imported `Effect`, any type that names effect's Effect interface written with one to three arguments, draws the warning, and the fix writes the `!` form, which the parser expands back to `Effect.Effect<A, E, R>` (D127). An empty slot is `never`. In the return annotation of a function with a body, where a `!` form without dependencies infers them, `Effect<A, E, never>` becomes `A!E!` and `Effect<A, E, infer R>` becomes `A!E` (`A!never` when E is `never`); elsewhere a missing slot is `never`, so `Effect<A, E>` becomes `A!E` and `Effect<A>` becomes `A!!`. A slot holding a function, conditional, or `!` type, or an object type after a `!`, is parenthesized, and so is the whole form where it would join its surroundings: as a union or intersection member, an array element, an indexed access, an operand of `keyof` or `readonly`, a conditional type's part, or a slot of another `!` form. Refused: a return annotation with a body that writes fewer than three arguments (EK2003 already asks which channels), `infer` in another slot or outside such an annotation, and references the parser wrote or JSDoc holds. Evidence: `tsforms-types` and `tsforms-types-fixed`, including a `@vibelang-diagnostics-next-line EK4833:off` that keeps one spelling.

**D288. A running Effect.succeed or Effect.fail draws EK4834**. In a VibeLang function a call runs where it stands (D147), so a running `Effect.succeed(x)` is `x`, and a running `Effect.fail(e)` fails as `throw e` does (D46), a throw being a typed failure everywhere outside a hatch (D282). Only a call that runs counts, as the lowering decides it: one passed by name, held by a declared Effect type, or in a hatch builds a program and draws nothing. The fix of `Effect.succeed(x)` writes `x` where a value stands (a return, an initializer, an argument, an element or field, an arrow function's body, a branch of `?:`, the right side of `??`, `||`, or `&&`), parenthesized where `{` or a comma would misparse; it refuses an `x` that is itself an Effect, and refuses a call whose removal could change the function's form: it applies only when the function keeps an Effect contract, is a declaration that D10 compiles with its Effect form beside it, is a lambda or method whose expected type asks for an Effect function or a program, or performs another Effect operation the fixes keep. Without that rule, `{ exists: () => Effect.succeed(true) } as unknown as FileSystem` would become a plain function returning `true`, which its caller would see (a regression the gate below did not catch, since it type-checks; found by `@smthrs/fs`'s FileRouterFailures test). The fix of `Effect.fail(e)` writes a throw statement for a statement or a return, and a throw expression (D186) for an arrow function's body, a branch of `?:`, and the right side of `??`, `||`, or `&&`; it refuses an `e` whose type is a Cause, which `throw` rethrows reason by reason (D177). Calls with type arguments are refused. The value can have a narrower type than the success type, a literal staying a literal, so `--fix` refuses a rewrite whose program would then report an error. Evidence: `tsforms-direct` and `tsforms-direct-fixed`.

**D289. Effect's catch combinators draw EK4835**. `Effect.catchTag(self, "Tag", handler)`, `Effect.catchTags(self, { Tag: handler, … })`, and `Effect.catch(self, handler)` in a VibeLang function body draw the warning, and the fix writes a catch expression (D236): one `match` arm per tag and `default: throw e;` (D216, D218), or, for `Effect.catch`, the handler itself, or a fallback when the handler takes no parameter. An arm tests the failure's `_tag` with an object pattern, `when { _tag: "Tag" }:`, which is what catchTag tests; it names the error class instead, `when NotFound:`, when the failures with that tag are the instances of one class the file can name, whose declaration fixes the tag (an error declaration, or a class extending a TaggedError or Schema.TaggedError with that literal tag), and no other failure extends it. Every failure in the program's E must have a literal `_tag` for catchTag and catchTags, so that the arms remove exactly the failures catchTag would. The left side runs inside the catch as the program argument did; an Effect value is called to run it, and so is a handler value that is an Effect value, since catchTag runs what its handler returns. A handler must be an arrow function with at most one plain parameter and an expression body, or a block that only returns one; the catch variable takes its parameter's name. A catch expression is parenthesized where it does not stand alone, such as the left side of another catch, since its handler extends as far as an arrow function's body. One difference is VibeLang's by design (D13, D236): a cause that mixes an expected failure with a defect or an interruption passes through a catch expression, while Effect's combinators recover the failure and drop the rest. Refused: the data-last forms inside `pipe`, type arguments, a tag that is not a string literal, and any other handler. Evidence: `tsforms-catch` and `tsforms-catch-fixed`; `@smthrs/errors`' tag-routing tests, whose `SmithersError<Tag>` carries a tag from its options, keep passing with object patterns.

**D290. Effect.withSpan, Effect.provide, and Effect.provideService draw EK4836**. In a VibeLang function body, `Effect.withSpan(self, name)` becomes the block param call `withSpan(name) { return self }` (D188, D151) wherever it stands, unless a local `withSpan` shadows the prelude's; the block's return gives the program's value, so the span covers the same program. `Effect.provide(self, layers)` and `Effect.provideService(self, key, value)` become a provide block (D130, D172, D173) where a block can stand: as a return, whose `return` inside the block returns from the function, and as an expression statement. A layer array becomes the block's comma list. The program runs inside the block as the call ran it: a call runs where it stands, and an Effect value is called. Refused: an options argument, the data-last forms inside `pipe`, a provide anywhere a block cannot stand (such as an initializer), and a key that is not a name or a dotted name. Evidence: `tsforms-blocks` and `tsforms-blocks-fixed`.

**D291. vibelang --fix applies every safe fix to a project**. `vibelang -p tsconfig.json --fix [other flags]` applies the quick fixes of EK4830-EK4836 and of the retired spellings (EK1009, EK2112, EK2113, EK2120, EK2121, whose fixes D172, D219, D221, and D223 make exact) to the project's `.vibe` files outside `node_modules`, writes the files it changes, prints one line per file with its fixes by code, and then compiles as the rest of the command line says, so `--noEmit` checks the result and the remaining diagnostics print as usual. Only diagnostics the project reports are fixed, so the `diagnostics` setting and `@vibelang-diagnostics` comments choose what it touches. Fixes come from the language server's own code actions, through its public request, so the editor and the CLI write the same text. They apply in rounds: each takes, per file, the fixes whose edits do not overlap, and the next round rechecks the edited program for the rest, so nested constructs converge. A round's fixes are kept only when the edited program reports no error that the original did not, compared by file, code, and message: when the round as a whole would add one, each file's fixes are tried together, then one at a time, and each fix that adds an error is refused, named with its line and the first error it adds, and not tried again. After the last round, an import of `effect` or one of its modules that the fixes left unused is removed, again only if that adds no error. Nothing is written until the rounds end, and a second run finds nothing to fix. `--fix` with `--build` or `--watch` is an error. Not a subcommand, because `vibelang` adds no commands (D30); not a separate binary, because the fixes need the checker and the language service in-process. Not controversial.

Gaps remaining after D284-D291, with the syntax each would need. No new syntax was added. ## Effect 4.0.6 (2026-10-25)

**D305. VibeLang follows Effect 4.0.6's defect precedence** (2026-10-25; amends D13 and D236). VibeLang pins `effect@4.0.6`. Where Effect's runtime combines an expected failure with a cleanup's or a concurrent sibling's defect (`ensuring`, `onExit`, `acquireRelease`, scope close, `callback` cleanup, concurrent `forEach` and `all`, and `raceAll` when every racer fails), each `Fail` becomes a `Die` of the same error, in order, original first (Effect-TS/effect#9433). Every typed recovery (`catch`, `catchTag`, `result`, `option`, `match`, `ignore`, `retry`, Stream) skips a cause with a defect and re-fails with its failures made defects; an interruption beside a failure doesn't block recovery; `mapError` maps every failure in place (#9516). VibeLang's forms that lower to those operators follow unchanged: `finally`, `finally (exit)`, `using`, `await.all`, `await.any`, `await.allSettled`, `for concurrent`, `retry` and `exit`. Where VibeLang handles causes itself it applies the same rule. When the kernel abandons a continuation, it combines the clause's or fiber's exit with the cleanup failures defects first (K16a, K16b). Source `catch` and catch expressions re-raise a cause with a defect with its failures as defects (K16d). A retired typed clause before a Cause clause never matches a failure beside a defect. Consequences for existing code: a failure whose cleanup crashed is now observed as a defect (`cause.hasFails()` is false, and `Effect.catchDefect` receives the original error); Effect's recovery operators no longer swallow the defect; `await.allSettled` propagates it instead of settling `Result.fail`. Nothing changes in types or syntax: `Effect.catchDefect(p, f)` and `match (exit(p))` (D217) already recover defects in the fewest tokens, and a `catch` form for defects would make catching a bug look as ordinary as catching a domain error. Evidence: F11a-F11e (Effect alone, `experiments/tests/defect-precedence.test.ts`), K16a-K16d, and the case `failures-mixed-causes`. D256's `timeout` limitation stands on 4.0.6 (F11e).


**D306. `catch` recovers a failure beside an interruption, as `Effect.catch` does** (2026-10-25; amends D13 and D236; separable from D305). When a cause holds no defect, `catch` and the catch expressions receive its first expected failure and drop any interruption or further failure beside it, exactly as `Effect.catch`, `catchTag` and `result` treat that cause on Effect 4.0.5 and 4.0.6; `retry` follows the same rule on 4.0.6 (F11c). Under D13, VibeLang's `catch` was the only recovery form that refused such a cause. A cause made only of interruptions still passes, so `catch` never stops cancellation. A fiber that is itself interrupted skips every `catch` while it unwinds interruptibly, as Effect skips every recovery frame. One rule stays VibeLang's own: a failure raised while a handler abandons a continuation carries the abandonment's internal interrupt and passes every `catch` inside that continuation (K14d), because recovering it would resume code the handler abandoned. Programs that observe the change: `try { join f } catch (e) { … }`, where `f` was interrupted while its cleanup threw `e`, and `try { interrupt() } finally { throw e }` inside a `catch`; both now reach the handler.


## Data types (2026-10-25)

**D307. `data` declares a tagged union with Effect's own `Data.TaggedEnum`** (extends D126, D133 and D206-D209). `data Delivery { Waiting; Sent { tracking: string }; Rejected { reason: string } }` declares what Effect's documentation writes for a tagged union: the type `type Delivery = Data.TaggedEnum<{ Waiting: {}; Sent: { tracking: string }; Rejected: { reason: string } }>` and the constructors `const Delivery: Data.TaggedEnum.Constructor<Delivery> = Data.taggedEnum<Delivery>()`, under one name. A variant without fields is a bare name, and `Delivery.Waiting()` constructs it; a variant's fields are written as an `error`'s are, `name: Type` or `name?: Type`, and are readonly, as `Data.TaggedEnum` makes them. A line break or `;` separates fields and variants, and a comma is EK1013, as in an `error`'s body, so the two change together if the field separator rule changes. A generic data type, `data LoadState<A, E> { Idle; Loaded { value: A }; Failed { error: E } }`, passes its type parameters through the interface `Data.TaggedEnum.WithGenerics` asks for, named `LoadStateDefinition`, `interface LoadStateDefinition extends Data.TaggedEnum.WithGenerics<2> { readonly taggedEnum: LoadState<this["A"], this["B"]> }`, and its constructors are `Data.taggedEnum<LoadStateDefinition>()`. `export data` exports the type, the constructors and, for a generic type, the definition, so a declaration file that infers a type from the constructors can name it. The constant's type is written out, `Data.TaggedEnum.Constructor<Delivery>`, or, for a generic type, the object `Data.taggedEnum` returns for its definition without the `Types.Simplify` around it: a declaration file then names Effect's types instead of expanding them, which TypeScript cannot do for a recursive data type such as `data Tree<A> { Leaf { value: A }; Node { left: Tree<A>; right: Tree<A> } }` (TS5088). Construction, `$is`, `$match`, `Equal` and `Hash` are Effect's: a value is a plain record with a `_tag`, and two values with equal fields are `Equal.equals`.

A variant is a pattern. `when Delivery.Sent:` and `x is Delivery.Sent` test the tag, as `when { _tag: "Sent" }` does, and `when Delivery.Sent { let tracking }` also reads the fields its braces list, binding each from the matched value: the variant fixes its fields, so a field needs no presence test, and an optional field the value leaves out binds `undefined` where `{ _tag: "Sent", let note }` would not match. What makes `Delivery` a data type is its value's type, constructors whose `$is` Effect's `Data` module declares, so a tagged union a `.ts` file declares with `Data.taggedEnum` matches the same way. The checker narrows a variant's test by its tag, keeping the members of a union whose tag may be the variant's, or, for a subject of no tagged type, narrowing it to the variant's values, as `Delivery.$is("Sent")` does; the lowering runs the test as that guard. A match without `default` over a data type must handle every variant (D209): EK4701 names what is left by variant, `This match does not handle every case of Delivery: Delivery.Rejected is left.`, and its last arm runs untested (D294), since a tag is a literal. Hover shows the declaration as written, and go to definition goes from `Delivery.Sent` to the variant. EK2122 reports a data type without variants, EK2123 a variant declared twice, EK2124 a name `Data.taggedEnum` reserves (a variant named `$is` or `$match`, a field named `_tag`, or another declaration of `NameDefinition`), EK2125 a variant member that is not a readonly typed field, EK2126 more than four type parameters or a constrained one, which `WithGenerics` cannot pass, EK2127 `Name.Variant` naming no variant, in place of TypeScript's TS2339, EK4706 a field list after a matcher that is not a variant or an argument list after one that is, and EK4707 a variant pattern whose subject's type has no such case.

Rejected: a variant with an unnamed payload, `Sent(string)` (Effect's `TaggedEnum` has named fields only; unnamed payloads are not supported); a class per variant with `Data.TaggedClass` (a union of classes is not what Effect writes for a tagged union, and `$match` would be missing); recognizing `when Name.Variant` by its syntax, as D208 recognizes `Option.Some` (the parser cannot see an imported data type, nor one a `.ts` file declares); leaving the test to `$is` at run time (`Data.taggedEnum`'s object makes a new constructor each time a variant is read, so nothing tells `$is` a variant from a predicate, and `when Delivery.Sent:` used to match every value); narrowing by the constructor's result type (the run-time test reads only the tag, so a different data type's variant with the same tag would reach the arm unnarrowed); field patterns after any class matcher, `when NotFound { let id }`. Evidence: cases `data-declaration`, `data-import` (a recursive generic type across files), `data-ts-consumer` (TypeScript constructs and matches through the declaration file), `data-match-emit`, `data-declaration.fail` and `data-patterns.fail`.

## Contracts (2026-10-25)

**D308. A contract is written `Effect<A, E, R>`; the `!` form is retired** (superseded by D309, which restores the `!` form and keeps this decision's meaning of `Effect<…>`; supersedes D127; amends D57, D93, D285 and D287). Effect uses ordinary type arguments; a concise alias remains a possible proposal. His rule for every detail: "Least surprising; follow idiomatic Effect patterns." A contract in a `.vibe` file means exactly what the same `Effect<…>` type means in TypeScript.

- A type argument left out means what it means in TypeScript: `Effect<A>` is `Effect<A, never, never>` and `Effect<A, E>` is `Effect<A, E, never>`, in the return annotation of a function with a body too. EK2003's rule that such an annotation write all three channels (D57) is retired; it existed so that `Effect<A, E>` would not be read as the `!` form's `A!E`, whose dependencies were inferred.
- Partial inference is unchanged: in the return annotation of a function with a body, a channel written `infer Name` comes from the body, as in `Effect<User, NotFound, infer R>` (D57). An unannotated function is still fully inferred.
- A plain return annotation keeps its meaning (D67, D282): `: number` is a plain function that never fails and needs nothing. The retired `number!!` was an Effect function that cannot fail and needs nothing; it is `Effect<number>`.
- Service and control members, `declare function` and other declarations without bodies write an Effect type, and a bare return type there is EK2101, reworded: "has no body to infer from, so its contract must be written as an Effect type." D93's rule that those types write all three arguments is retired with EK2003's, so `find(id: string): Effect<User, NotFound>` fails with `NotFound` and needs nothing, as the retired `User!NotFound` there did.
- The `!` form is EK1014, an error. The parser still reads it as the type it stood for, so a file that has one checks, and EK1014's quick fix writes that type: `A!E!R` becomes `Effect<A, E, R>`, `A!E!` becomes `Effect<A, E>`, `A!!R` becomes `Effect<A, never, R>`, `A!!` becomes `Effect<A>`, and `A!E` becomes `Effect<A, E, infer R>` in the return annotation of a function with a body and `Effect<A, E>` anywhere else. The parentheses the form needed around a slot or around itself go away, since a type argument and a type reference need none. `vibelang -p tsconfig.json --fix` applies the fix (D291), so a project migrates in one command. The fix writes the prelude's `Effect`, which a file that imports the `Effect` namespace from `effect` still has as a type.
- Hovers, messages, quick fixes and refactors write Effect types as `Effect<…>`, in TypeScript's short form where the defaults allow: `Effect<string>`, not `Effect<string, never, never>`. Declaration files write a contract as it is written, `Effect<A>` included, through the runtime's `Effect` type, an alias of effect's `Effect.Effect` with the same defaults, so TypeScript callers see Effect's own type.
- EK4833 (D287) now reports only an Effect type written through the Effect module, `Effect.Effect<A, E, R>`, where the prelude's `Effect` names the same type, and its fix drops the module and keeps the type arguments as written. The prelude's `Effect<…>` and an `Effect` imported as a type draw nothing. EK4831's fix (D285) writes a service member's Effect type the same way.
- The ESTree converter keeps `VibeEffectType` (D277) for the retired form, which still parses. The experimental content mapper (`internal/vibelangmapper`) keeps projecting the retired form and does not report EK1014; it now reads a written `Effect<A>` or `Effect<A, E>` as the compiler does.

The `!` form moves to the [proposals page](https://vibelang.sh/proposals#effect-type-shorthand) as a potential proposal, because Effect is used enough to warrant its own syntax that reduces tokens. Measured with o200k_base (js-tiktoken 1.0.21), the README's program is 117 tokens against 202 for Effect TypeScript, 42.1% fewer (116 tokens and 42.6% with the shorthand), and the shorthand saves 1 to 5 tokens per contract: `User!!` is 2 tokens and `Effect<User>` 3; `User!!Db` is 3 and `Effect<User, never, Db>` 7. Breaking: every `.vibe` file that writes the `!` form reports EK1014 until `--fix` or a hand edit rewrites it. Evidence: cases `retired-effect-types.fail` (each form's EK1014 and its message) and `retired-effect-types-fixed` (what `--fix` writes, which compiles and runs), `effect-type-defaults` and `effect-type-defaults.fail` (`Effect<A>` and `Effect<A, E>` check the channels they leave out as `never`; `infer` still infers; a service's members written `Effect<…>`).

**D309. The `!` form is restored as an alias of `Effect<A, E, R>`, and is the documented form** (supersedes D308; restores D127; keeps D308's meaning of `Effect<…>`). The shorter contract spelling reduces tokens while preserving Effect's type semantics. Both spellings are valid and interchangeable in every position a type can take. The guides, the skill, the README, the examples and the templates write the `!` form, as they did before D308, and say once, where they introduce contracts, that `Effect<A, E, R>` is accepted too.

- The `!` form means what D127 defined: `A!E!R` is `Effect<A, E, R>`; an empty slot is `never`, so `A!E!` needs nothing, `A!!R` cannot fail, and `A!!` neither fails nor needs anything; dependencies left out entirely, `A!E`, are `infer R` in the return annotation of a function with a body and `never` everywhere else. Service and control members and other declarations without bodies write a contract in either spelling; `A!E` there needs nothing.
- `Effect<A, E, R>` keeps D308's meaning, TypeScript's: a type argument left out is `never`, so `Effect<A>` is `A!!` and `Effect<A, E>` is `A!E!`, in the return annotation of a function with a body too; `infer Name` infers a channel (D57). EK2003's three-channel rule and D93's three-argument rule for EK2101 stay retired, and EK2101 keeps D308's wording. The two spellings differ only where a channel is left out: `A!E` on a function with a body infers R, while `Effect<A, E>` checks R as `never`.
- EK1014 is retired. No diagnostic reports the `!` form, its quick fix and its entry in `vibelang --fix` (D291) are gone, and the number is not reused. A file that `--fix` rewrote under 0.0.8 or 0.0.9 keeps its `Effect<…>` types, which still mean the same.
- EK4833 keeps D308's scope: it reports only `Effect.Effect<A, E, R>`, and the prelude's `Effect<…>` draws nothing. Its fix writes the `!` form again, as D287 described; since a type argument left out is now `never` in a body's return annotation too, `Effect.Effect<A>` there becomes `A!!` and `Effect.Effect<A, E>` becomes `A!E!`, where D287 refused them. EK4831's fix writes a member's Effect type in the `!` form (D285).
- Diagnostics, quick fixes, refactors, hovers, inlay hints and signature help print Effect types in the `!` form, as before D308. Declaration files write the types the parser expands: `Effect.Effect<A, E, R>` for the `!` form, and the written `Effect<…>` through the runtime's alias.
- The grammars (tree-sitter, TextMate), the formatter, the ESTree converter (`VibeEffectType`, D277) and the content mapper read both spellings, and the formatter keeps the spelling the source used.
- The shorthand leaves the proposals page, since it is implemented again.

Measured with o200k_base (js-tiktoken 1.0.21) after the docs went back to the `!` form: the README's program is 116 tokens against 202 for Effect TypeScript, 42.6% fewer (117 and 42.1% under D308); the 46 cheat-sheet pairs save 11.4% (10.9%), and their Effect types entry 28.4% (19.8%); the skill is 4,772 tokens (4,787). Not breaking: everything that compiles on 0.0.9 compiles the same, and code written for 0.0.6 with the shorthand compiles again. Evidence: cases `terse-contracts` (each `!` form that 0.0.8 reported as EK1014, compiled and run), `effect-type-spellings` (the `Effect<…>` spellings `--fix` wrote, compiled and run), `effect-type-defaults` and `effect-type-defaults.fail` (`Effect<A>` and `Effect<A, E>` check left-out channels as `never`; `infer`; service members), `contract-spellings-mixed` (both spellings in one file, a service implemented across them), and `tsforms-types-fixed` (EK4833's fix).

## The platform standard library (2026-10-26)

**D312. The file that exports `main` names its platform once, with a platform import at its top: `import "vibelang/platform/node"`, `"vibelang/platform/bun"` or `"vibelang/platform/browser"`. When `main` needs services that the named platform's bundle provides, its entry statement provides the bundle around it: `runtime.$entry(import.meta.main, import.meta.url, main, () => NodeRuntime.runMain(Effect.provide(main(), NodeServices.layer)))`. `node` names `@effect/platform-node`'s `NodeServices`, `bun` `@effect/platform-bun`'s `BunServices`, and `browser` `@effect/platform-browser`'s `BrowserServices`, which Effect 4.0 does not declare; the program resolves the named platform's modules as implicit imports of the entry module, as D135 resolves `@effect/platform-node`. A bundle's services are the `Out` of its `layer`'s declared type, read from the installed declarations, not from a list in the compiler. When `main` needs a service that only the platform's experimental bundle provides (D313: `NodeServices` from `vibelang-runtime/experimental/platform-node`, `BunServices` from `vibelang-runtime/experimental/platform-bun`, `BrowserServices` from `vibelang-runtime/experimental/platform-browser`), the entry provides that bundle too, inside Effect's, so its layer may build on Effect's services. A `provide` inside `main` wins for the code inside it, as `Effect.provide` does. The import loads nothing: the compiler removes it from the JavaScript and the declarations, and TypeScript's TS2882 for the unresolved specifier is not reported. The runner is D135's: `NodeRuntime` when `@effect/platform-node` resolves, else the runtime's copy. Without a platform import nothing changes: the entry provides no layer, and EK3205 names the services `main` needs and, for those `@effect/platform-node`'s bundle provides, the import that would provide them; with a platform import whose package does not resolve, it says the package is not installed. EK3205 names only the services the bundles do not provide; when `main` needs both kinds, the entry still provides the bundle, so a program run despite the warning fails at start naming a service EK3205 named. Tests never run the entry statement (`import.meta.main` is false in a module a test imports): `it.effect` provides its own layers, and EK3201 names what it leaves out. The trigger is one function, `namedPlatform` in `entry.go`, so the alternatives still in the owner's queue, a library call such as `export default Node.run(main)` or a `"vibelang": { "platform": "node" }` setting, replace it without touching how the layer is provided. Rejected for now: an implicit default that picked the platform by which package resolves (the owner prefers the platform named in the program). The ts-mapper projection, which cannot resolve packages, still runs `main` without a layer and keeps the import. Evidence: cases `entry-platform-layer` (the import with no provide, with an inner provide, and with a `main` that needs nothing, whose JavaScript and declarations carry no trace of the import), `entry-platform-layer-bun` (the import picks Bun with both packages installed), `entry-platform-layer-experimental` and `entry-platform-layer-services.fail` (EK3205 beside the import, without it, and with an uninstalled platform; EK3201 in a test); `examples/file-tree` and the platform guide's snippets, run with the installed `@effect/platform-node` and `@effect/platform-bun`.


## Experimental platform APIs (2026-10-26)

**D313. `Experimental` holds what Effect lacks** (provisional, pending the owner's review 2026-10-27; part 1: the namespace, `Experimental.FileSystem` and `Experimental.Crypto`; part 2 adds `Experimental.Process` and `Experimental.Locks`). The owner's rules: platform APIs are wrapped, effectful and injected; VibeLang implements nothing that Effect has; what Effect lacks goes under `Experimental`. Each addition lives in `vibelang-runtime/experimental/<Effect module name>` and extends that Effect module: a superset of Effect's interface under its own `Context.Service` key (`vibelang/experimental/FileSystem`), `PlatformError` failures, Effect's member names, and a test layer. The aggregate `vibelang-runtime/experimental` exports each module as a namespace, and the runtime's root exports the aggregate as `Experimental`, a prelude name (D4), so a `.vibe` file reaches `Experimental.FileSystem` without an import, a local declaration or import of the name shadows it, and the emitted JavaScript imports it from the runtime like the other prelude names. A file may instead import a service by name from its module's subpath, which shadows the prelude's Effect module of that name (D146); Effect's members, `lstat` among them, keep working on the experimental service because its interface is a superset. Per-platform layers live in `vibelang-runtime/experimental/platform-node`, `-bun` and `-browser`, as `NodeFileSystem.layer`, `NodeCrypto.layer`, `NodeServices.layer` and their Bun and browser counterparts. Each provides the experimental service and Effect's service of the same name from one implementation, the Effect platform package's own with the additions, so Effect's users of a service, such as `Logger.toFile`, and the experimental one share it; `NodeServices.layer` and `BunServices.layer` there are the Effect bundles plus every experimental service. Platform-neutral modules import only `effect`; `node:` modules appear only under the Node and Bun layers; `@effect/platform-node`, `-bun` and `-browser` 4.0.6 are optional peer dependencies of the runtime. A program that does not use `Experimental` carries none of it: the service keys are marked pure, so a browser bundle of the runtime drops them.

- `Experimental.FileSystem` adds `access(path, { executable })` (`X_OK`; on Windows existence only, as Node's), `open(path, { nonBlocking })` (`O_NONBLOCK`; `BadArgument` where the platform lacks it, as `noFollow` fails) and `File.chmod(mode)` (`fchmod`). The proposal also listed `lstat`, but Effect 4.0.6, which VibeLang now follows, has `FileSystem.lstat`, so the experimental service has Effect's. Every other member, and every open without `nonBlocking`, is Effect's own; `File.chmod` on Effect's file reads the descriptor that Effect's Node file keeps. Effect does not export the helpers a nonblocking open needs, so the Node and Bun implementation copies `@effect/platform-node-shared` 4.0.6's file class, its `makeFileInfo`, the open flags and the errno mapping. Browsers have no layer, as in Effect. `layerNoop` provides both keys from Effect's `makeNoop`, with `open` failing with `NotFound`.
- `Experimental.Crypto` adds `hmac(algorithm, key: Redacted<Uint8Array>, data)` (raw key; Effect's digest algorithms), `sign("ECDSA-P256-SHA256" | "Ed25519", privateKey: Redacted<Uint8Array>, data)` (PKCS#8 DER) and `verify(algorithm, publicKey, signature, data)` (SPKI DER; `false` for a signature that does not match). One WebCrypto implementation serves every platform: `globalThis.crypto.subtle`, read when the service is made. ECDSA signatures are WebCrypto's r‖s, 64 bytes. A key of the wrong kind fails with `BadArgument`, whose message names no key bytes; without WebCrypto the members fail with `Unknown`, as Effect's browser `digest` does. `layerTest` provides both keys with zero random bytes and real digests and signatures.
- Lifetime: each addition has an Effect patch prepared (not opened). When Effect releases a member, the experimental module re-exports Effect's, then a later VibeLang release deletes it.

Rejected: separate `vibelang-platform-*` packages (more installs for the same code); module-level accessor functions, Effect 3's style; a fork of Effect's open for every open (only `nonBlocking` needs the copy); importing each experimental module explicitly with no prelude name (the owner put additions under a global `Experimental`); and an experimental fork of Effect's child process spawner for a child's exit signal, which goes to Effect as a patch only. Evidence: the runtime's tests run both services through every layer on Node and Bun against the real file system (execute bits, a FIFO opened without blocking, a refused final symbolic link, `fchmod` after a rename, unsupported platforms) and against known vectors (RFC 4231 HMAC-SHA-256 and HMAC-SHA-512, RFC 8032 test 1 for Ed25519, RFC 6979 A.2.5 for ECDSA P-256), bundle the browser layer, and compile a stock TypeScript consumer of the declarations; case `experimental-platform` runs both from a `.vibe` program through the prelude's `Experimental` and an explicit import, with its declarations.
