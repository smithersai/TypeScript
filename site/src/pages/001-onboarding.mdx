# Welcome to VibeLang

VibeLang is a language for writing [Effect](https://effect.website) programs with TypeScript syntax. Its compiler checks `.vibe` and `.ts` files together and emits JavaScript and `.d.ts` declarations.

:::code-group

```vibe [VibeLang]
interface User { id: string; name: string }

error UserNotFound { id: string }

service Users {
  find(id: string): User!UserNotFound
}

function greet(id: string) {
  const name = Users.find(id).name catch "guest"
  return `Hello, ${name}`
}
// string!!Users
// Output: Hello, Ada
```

```ts [Effect]
// fragment
// Uses the User type from the VibeLang tab.
class UserNotFound extends Schema.TaggedError<UserNotFound>()("UserNotFound", {
  id: Schema.String
}) {}

class Users extends Context.Service<Users, {
  find(id: string): Effect.Effect<User, UserNotFound>
}>()("app/Users") {}

const greet = Effect.fn("greet")(function* (id: string) {
  const users = yield* Users
  const user = yield* users.find(id).pipe(
    Effect.catchTag("UserNotFound", () => Effect.succeed({ name: "guest" }))
  )
  return `Hello, ${user.name}`
})
```

:::

A user service, a typed error, and a fallback in Effect and in VibeLang. The comment under `greet` is the type your editor shows: `string!!Users` means `Effect<string, never, Users>`. It returns a `string`, has no expected failures (defects and interruption remain possible), and needs the `Users` service. The compiler infers all three from the body, and TypeScript code that imports `greet` sees the Effect type. The TypeScript example's `Effect.fn("greet")` adds a tracing span; the VibeLang function is untraced by default.

VibeLang is v0: the language will change in major, breaking ways and is not ready for production use.

## Why a language

**Effect tracks failures and services.** A TypeScript signature says what a function returns, not what can fail or what it depends on. Effect puts all three in one type the compiler checks, `Effect<Success, Error, Requirements>`, and brings retries, timeouts, concurrency, resource cleanup, and tracing.

**Effect expresses sequencing through library calls.** As a library, Effect builds every feature from TypeScript's own tools: generators and `yield*` run steps in order, `pipe` composes them, and classes declare errors and services. The code reads like a separate language written in library calls.

**VibeLang adds language syntax.** Each Effect idea gets syntax: calls run in order, `throw` fails with a typed error, `catch` handles it, `service` declares a dependency, and `fork` starts a fiber. The compiler builds the Effect program you would write by hand.

## TypeScript stays one step away

VibeLang shares TypeScript's ecosystem in two ways:

1. **It shares TypeScript's compiler and types.** VibeLang's compiler is TypeScript's, extended, so you use existing Effect code and npm packages through [TypeScript interop](/vibelang-features/114-vibelang-for-effect-users), and TypeScript calls exported VibeLang functions as ordinary Effect functions.
2. **You can opt out to plain TypeScript.** `sync`, `try`, and `callback` take a plain TypeScript function, and a `.ts` file can sit beside any `.vibe` file.

A hatch adapts Promise or callback APIs and platform code that VibeLang cannot call directly. Based on [Effect’s Creating Effects](https://effect.website/docs/v4/getting-started/creating-effects#trypromise), this adapter awaits the platform `fetch` API.

```vibe
error TodoFailed { cause: unknown }

function getTodo(id: number) {
  return try(async (id, signal) => {
    // Plain TypeScript inside this hatch, not VibeLang.
    const response = await fetch(`https://jsonplaceholder.typicode.com/todos/${id}`, { signal })
    if (!response.ok) throw new Error(`HTTP ${response.status}`)
    return await response.text()
  }, (cause) => new TodoFailed({ cause }), id)
}
// string!TodoFailed!

function todoOrFallback(id: number) {
  return retry(getTodo(id), Schedule.recurs(2)) catch "Todo unavailable"
}
```

A hatch's function receives `.vibe` values as inputs, here `id`; its final parameter is the cancellation signal.

## Effect's features, in VibeLang syntax

VibeLang runs on Effect and its library modules; common operations have syntax:

| Effect feature | VibeLang |
| --- | --- |
| Effect types | `User!NotFound!Users`: returns `User`, fails with `NotFound`, needs `Users` |
| Typed errors | `error NotFound { id: string }`, `throw new NotFound({ id })`, `x catch fallback` |
| Dependency injection | `service Users { ... }`, `provide UsersLive { ... }` |
| Structured concurrency | `fork`, `join`, `await.all [a(), b()]`, `for concurrent(8) (const id of ids)` |
| Retries and timeouts | `work() \|> retry(%, policy) \|> timeout(%, "1 second")` |
| Resource safety | `using conn = connect()`, `finally` |
| Tracing | `withSpan(() => { ... }, "checkout")` |
| Schema validation | `schema User { id: string; role: "admin" \| "member" }` |
| Pattern matching | `match (e) { when NotFound: ...; }` |

Streams, configuration, and Effect's HTTP, SQL, CLI, and AI packages have no syntax of their own: call them as in TypeScript. The [cheat sheet](/vibelang-features/115-cheat-sheet) puts every VibeLang form beside the Effect code it replaces.

## Check application code

The compiler tracks each function's expected failures and required services. A written failure slot rejects an added unhandled failure. A contract such as `A!E` still infers requirements from the body; write the requirements slot too, as in `A!E!` (no requirements) or `A!E!R`, to reject an added dependency outside that slot. Type checking does not establish behavior: run focused tests for it, including recovery, cancellation, and cleanup.

## Try it

```sh
bun create vibelang@latest my-app
cd my-app
bun run dev
```

Then open the folder in VS Code or Cursor and install the editor extension that ships with the compiler: `code --install-extension node_modules/vibelang/editor/vibelang.vsix`. [Installation](/getting-started/004-installation) covers existing projects.
