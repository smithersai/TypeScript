# Managing Services

A service is a named capability a program uses without passing an implementation through every function. `service` declares it as an abstract class whose members state contracts; its uses are inferred in the `R` channel.


## Declaring typed service keys

```vibe
service Sequence {
  next(): number!!
}

service Reporter {
  write(message: string): void!!
}
// Output: ticket-17
```

A service has no superclass or type parameters, and every instance member is abstract. Methods state full contracts, having no body to infer from; `abstract readonly` value members are allowed. Static fields can hold layers or other helpers.

Services are nominal: the compiler derives the key from package, module path, and class name, so two services with identical members are different dependencies. Implement one with an object literal or a class that `implements` it; don't construct, extend, or use `instanceof` on it.

## Declaring a service of any shape

```vibe
interface SearchApi {
  find(query: string): string!!
}

service Search: SearchApi
service Prefix: string

function lookup(query: string) {
  return `${Prefix()}${Search.find(query)}`
}
// Output: > hit:vibe
```

`service Name: Type` declares a service whose implementation has any type: an interface declared elsewhere, a primitive such as `string`, or a function type. Like Effect's `class Search extends Context.Service<Search, SearchApi>()(key) {}`, it is a service key, with the key derived as for every service. The body is optional and holds only static members, such as a layer: `service Search: SearchApi { static readonly layer = Layer.succeed(Search, impl) }`. An instance member there is error EK2103; declare it in the shape. Reading is the same as for any service: `Search.find(q)` calls a member and `Prefix()` returns the implementation. As for every service, the type `Search` is the service's identifier and `Search.Shape` is `SearchApi`, so type an implementation `SearchApi`.

## Requesting and supplying implementations

```vibe
function nextLabel() {
  return `ticket-${Sequence.next()}`
}
// string!!Sequence

function fixedLabel() {
  return Effect.provideService(nextLabel(), Sequence, {
    next: () => 17
  })
}
// string!!

function readImplementation() {
  const sequence = Sequence()
  return sequence.next()
}
// number!!Sequence
// Output: ticket-17
// Output: ticket-23 23
```

A service can declare `static readonly default` to supply an implementation without a provider. The initializer is checked against the service shape, with the same member failure and call-time requirement checks as `Layer.succeed`: a shape mismatch is a TypeScript error, an excess failure is EK2001, and an undeclared call-time requirement is EK3101.

`Sequence.next()` looks up the service and runs the method; `Sequence()` returns the implementation, to capture it or read value members. Supply every requirement before running the program. A missing provide at an entry `main` produces warning EK3205 by default; the starter sets EK3205 to `"error"`, so the build stops.

```vibe
service Settings {
  baseUrl: string
}

function endpoint(path: string) {
  return `${Settings().baseUrl}/${path}`
}
// string!!Settings
// Output: https://example.test/tickets
```

Read value members from the implementation, as `Settings().baseUrl`. A member call through the service adds the service to `R` whatever the member returns: `Path.join(a, b)` returns a plain string and still requires Effect's `Path` service. Members from Effect's packages, or from packages matching the `vibelang` setting `trustedPackages`, are trusted; any other plain TypeScript member needs a boundary or `trusted(impl, [Errors])`, else the call is EK4401. A member that is itself an Effect value runs when called: `Terminal.readLine()`.

Declared members win over the key's own, including `pipe`, `use`, `key`, and `call`. A static member named like a service member is error EK3006.

`provideService` removes the dependency only within its program. Nested overrides are local, a captured implementation stays the same object across later overrides or pauses, and forked fibers inherit the context present when they start.

## Service identifiers and shapes

```vibe
type SequenceImplementation = Sequence.Shape
type SameImplementation = Context.Service.Shape<typeof Sequence>
```

A service has two types, as an Effect `Context.Key` has. As a type, `Sequence` is the service's identifier: its members plus a brand that only `Sequence` carries, so neither another service with the same members nor a structural type such as `{ next(): number!! }` can stand for it in `R`. `Sequence.Shape`, which Effect spells `Context.Service.Shape<typeof Sequence>`, is the members alone, the type of an implementation. `Layer.succeed`, `Layer.effect`, `provideService`, `provide Sequence = …`, and a default check an implementation against the shape, and `implements Sequence` in a `.vibe` file checks a class against it.

`Sequence()` returns the implementation typed as the identifier, so a parameter typed `Sequence` takes it. A plain object has the shape, not the identifier: type a parameter or a default that takes one `Sequence.Shape`, or passing `{ … }` is TS2741. A TypeScript class implements the emitted service with `implements Sequence.Shape`.

Providers infer and check the implementation from the key argument, so most layers don't need either name. At a TypeScript boundary, the shape describes the emitted implementation's Effect-returning methods.

## Combining multiple dependencies

```vibe
function announceTicket() {
  const label = nextLabel()
  Reporter.write(`Created ${label}`)
  return label
}
// string!!Sequence | Reporter

const SequenceTest = Layer.succeed(Sequence, {
  next() { return 17 }
})
const ReporterTest = Layer.succeed(Reporter, {
  write(_message) {}
})

function testAnnouncement() {
  provide wire(SequenceTest, ReporterTest) { return announceTicket() }
}
// Output: "ticket-17"
```

A union in `R` needs both capabilities. Layers supply the group together; `wire` composes their graph, rejecting duplicate providers and cycles. Inputs no argument provides stay requirements of the resulting layer, reported as missing where a runner or contract needs them satisfied. For a small local override, nest direct service provision.

```vibe
const testContext = Context.add(
  Context.make(Sequence, { next: () => 17 }),
  Reporter,
  { write: (_message) => {} }
)

function testWithContext() {
  provide testContext { return announceTicket() }
}
// Output: ticket-17
```

A `Context` holds existing implementations; a `Layer` describes how to build them. A `provide` block, like `Effect.provide`, accepts either. `provide` is a statement: using it as an expression, as in `const ticket = provide testContext { … }`, is EK1017; return the value from inside its block. Keep resource-owning implementations within the lifetime that created them.

## Requesting optional services

```vibe
function optionalAnnouncement(message: string) {
  const reporter = Effect.serviceOption(Reporter)
  if (reporter.isNone()) return false
  reporter.value.write(message)
  return true
}
// boolean!!
// Output: false
// Output: hello
// Output: true
```

`serviceOption` returns `None` when an application service is absent and `Some(implementation)` when present, without adding the service to `R`. Calling a found implementation still carries the method errors and call-time requirements the service declares.

## Handling dependencies between services

```vibe
service ReportSettings {
  prefix: string
}

const ReporterLive = Layer.effect(Reporter) {
  const settings = ReportSettings()
  return {
    write(message) {
      Console.log(`${settings.prefix}: ${message}`)
    }
  }
}
// Layer<Reporter, never, ReportSettings>
// Output: audit: ready
```

Capture construction dependencies in the layer factory: `Reporter.write` then requires only `Reporter`, because the implementation retains `settings`. Looking up `ReportSettings()` inside `write` would add a call-time requirement, which its declared `R = never` rejects.

## Coming from Effect

Abstract classes replace hand-written `Context.Service` declarations in `.vibe` files. A `Context.Service` class there draws EK4831, whose quick fix writes the `service` declaration when its members are written in the class's type argument ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). Call service methods directly; `ServiceName()` replaces yielding the key in a TypeScript generator to get its implementation.
