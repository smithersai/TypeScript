# Expected Errors

Expected errors are situations callers can handle: invalid input, a denied operation, an unavailable dependency. VibeLang infers them in `E` and narrows them inside `catch`.


## Constructing typed failures

```vibe
error InvalidCode {
  input: string
}
error ItemMissing {
  code: string
}

function normalizeCode(input: string) {
  const code = input.trim()
  if (code.length === 0) throw new InvalidCode({ input })
  return code.toUpperCase()
}
// string!InvalidCode!
```

```text
PEN
InvalidCode
```

`error InvalidCode { input: string }` declares an expected failure class, short for `class InvalidCode extends TaggedError("InvalidCode")<{ readonly input: string }> {}`, which also compiles; the global `TaggedError` is Effect's `Data.TaggedError`. The constructor takes the fields, all readonly, and each instance has a readonly `_tag` equal to the class name. `error Timeout` has no fields. In an Effect function, `throw` adds the class to `E`. `Effect.fail(error)` also works; `Effect.failSync(() => error)` defers construction to execution, as a function body already does.

In Effect functions, trusted built-ins can add expected failures too: `JSON.parse` adds `SyntaxError`. A plain TypeScript function needs the `try` hatch or a wrapper made with `trusted(implementation, [ErrorClass])` in a `.ts` or `.vibe` module, importing `trusted` from `vibelang-runtime`: instances of listed classes join `E`; unlisted exceptions are defects. The older `/** @vibelang trusted */` and `@throws` declaration tags are deprecated: calls that rely on tagged expected failures get warning EK4406 now and become errors when the per-file emitter replaces the current lowering. Effect's own packages are trusted, so calls such as `Option.isNone` need no boundary.

`throw` is a typed failure everywhere outside a hatch, and `catch` receives typed failures only. A function with a plain return annotation is plain JavaScript because it never fails and needs nothing. It may throw what its own `catch` handles, and it still returns a value:

```vibe
error InvalidQuantity { text: string }

function quantityOr(text: string, fallback: number): number {
  try {
    const quantity = Number(text)
    if (!Number.isInteger(quantity)) throw new InvalidQuantity({ text })
    return quantity
  } catch {
    return fallback
  }
}
// Output: 3
// Output: 0
```

A failure that can escape a plain function is EK2003. The message names the function and what it throws, then lists the ways out, and the quick fix writes the first, the Effect contract:

```vibe
// expect-error: EK2003
function quantity(text: string): number {
  const value = Number(text)
  if (!Number.isInteger(value)) throw new InvalidQuantity({ text })
  return value
}
```

```text
error EK2003: quantity can't throw InvalidQuantity: its return annotation, number, makes it a plain function, which never fails.
  Make it an Effect function: number!InvalidQuantity!
  Or fail with a defect instead: die(new InvalidQuantity({ text })), annotated number!!
  Or escape to TypeScript: move quantity to a .ts file or a module block, or wrap the throw in sync(() => { … }), annotated number!!
```

An Effect function's callers run it, so they become Effect functions too. A defect is for a failure no caller should handle: `catch` never receives one. In a `.ts` file or a `module` block, `throw` is JavaScript's, and a `sync` hatch turns that exception into a defect.

The same holds for a throw expression and for a `match` arm or `do` block that throws. A method's plain return annotation is checked the same way: it is the method's type in the declaration file, so a body that runs an Effect is EK2003 too; write the contract, or leave the method unannotated. A method that implements a plain-function member of a JavaScript protocol, such as `[Equal.symbol]`, is checked against that member instead (EK4301). A plain function calls TypeScript code directly. A call whose contract lists a failure, such as `JSON.parse`, is a typed failure only inside a `try` whose `catch` belongs to the function, which receives it with its type; elsewhere its exception propagates unchanged. Other TypeScript code's exceptions pass through the `catch` unchanged and become defects where they reach an effectful caller; to catch one, use the `try` hatch in an Effect function. Running an Effect inside a plain-annotated function is EK2003 too.

An Effect function cannot stand for a plain function type, even one returning `void`: that is EK4301 at an initializer, assignment, return, property write or typed literal element. This also checks members of objects and class instances. Declare an Effect function type at the destination, or provide a plain function; otherwise a plain caller would receive a program whose work never runs.

## Trusting a TypeScript function

```ts
// TypeScript (.ts)
// quantity.ts
export class InvalidQuantity extends Error {
  readonly _tag = "InvalidQuantity"
}

export function parseQuantity(text: string): number {
  const quantity = Number(text)
  if (!Number.isInteger(quantity)) throw new InvalidQuantity(text)
  return quantity
}
```

```vibe
import { trusted } from "vibelang-runtime"
import { InvalidQuantity, parseQuantity } from "./quantity.ts"

const quantity = trusted(parseQuantity, [InvalidQuantity])
// Trusted<(text: string) => number, readonly [typeof InvalidQuantity]>
```

```text
3
InvalidQuantity
```

`trusted` works in a `.vibe` file as it does in TypeScript. `quantity` calls the TypeScript `parseQuantity`: an `InvalidQuantity` it throws is an expected failure in `E`, and any other exception is a defect.

## Failing in an expression

```vibe
error MissingPort

function port(env: Map<string, string>) {
  return env.get("PORT") ?? throw new MissingPort()
}
// string!MissingPort!
```

```text
3000
MissingPort
```

`throw` also works as an expression, per the TC39 [throw expressions](https://github.com/tc39/proposal-throw-expressions) proposal, and fails as the statement does. The right side of `??`, `||`, `&&`, and `?:` runs only when chosen. A throw expression takes only a unary operand: EK1010 refuses an unparenthesized throw that is, or ends, an operator's left operand, a conditional's condition, or the operand of `as` or `satisfies`, so write `throw (cond ? a : b)` to throw a whole conditional. The statement `throw cond ? a : b;` still throws the selected value.

## Tracking several error cases

```vibe
function findItem(input: string) {
  const code = normalizeCode(input)
  if (code !== "PEN") throw new ItemMissing({ code })
  return { code, label: "Fountain pen" }
}
// { code: string; label: string }!InvalidCode | ItemMissing!
```

```text
Fountain pen
ItemMissing
InvalidCode
```

A function collects the failures it throws and those its calls can produce. Sequential statements stop at the first failure: no lookup follows a failed normalization. An explicit full contract checks this inferred union; it doesn't replace it.

## Turning failures into values

```vibe
function inspectItem(input: string) {
  const result = Effect.result(() => findItem(input))
  return result.match({
    onFailure: (error) => `unavailable: ${error._tag}`,
    onSuccess: (item) => item.label
  })
}

function optionalItem(input: string) {
  const item = Effect.option(() => findItem(input))
  return item.isNone() ? "No item" : item.value.label
}
```

```text
Fountain pen
unavailable: InvalidCode
unavailable: ItemMissing
Fountain pen
No item
```

`Effect.result` moves `E` into the success channel as `Result<A, E>`. `Effect.option` gives `Some` on success and discards a typed error as `None`; use it only when every domain failure means absence. Causes with no expected failure still propagate, and so do causes with a defect, their expected failures as defects; both consume an expected failure beside an interruption, as ordinary catch does. Match on `exit(...)` when interruption must always propagate intact.

## Recovering all failures

```vibe
function itemLabel(input: string) {
  try {
    return findItem(input).label
  } catch (error) {
    return `Unavailable (${error._tag})`
  }
}
// string!!
```

```text
Fountain pen
Unavailable (InvalidCode)
Unavailable (ItemMissing)
```

The catch receives `InvalidCode | ItemMissing` and handles both, but only in causes with no defect or interruption; given several expected failures together, it receives the first and handles their whole cause.

```vibe
function itemLabelInline(input: string) {
  return findItem(input).label catch (error) => `Unavailable (${error._tag})`
}
// string!!
```

```text
Fountain pen
Unavailable (InvalidCode)
Unavailable (ItemMissing)
```

After an expression, `x catch (error) => handler` runs `x` and passes an expected failure to the handler, as `Effect.catch` does, with the statement's guard: defects and interruption pass through. `x catch fallback` evaluates the fallback instead, as `Effect.orElseSucceed` does; see [Fallback](/error-management/016-fallback).

`Effect.catch(() => findItem(input), handler)` also recovers expected failures, with the same rule as source catch. `Effect.catchEager` has the same policy and can recover immediately when given an already computed `Exit`.

## Recovering selected failures

```vibe
function labelOrMissing(input: string) {
  try {
    return findItem(input).label
  } catch (error) {
    return match (error) {
      when ItemMissing: "Out of catalog";
      default: throw error;
    }
  }
}
// string!InvalidCode!

function labelByTag(input: string) {
  return Effect.catchTag(
    () => findItem(input),
    "ItemMissing",
    (error) => ({ code: error.code, label: "Out of catalog" })
  )
}
```

```text
Out of catalog
InvalidCode
Out of catalog
InvalidCode
```

Catch, then `match` on the failure: an arm such as `when ItemMissing:` handles that error class, and `default: throw error` passes the others on with their types (`string!InvalidCode!`). The expression form takes the same `match`: `findItem(input).label catch (error) => match (error) { when ItemMissing: "Out of catalog"; default: throw error; }`. A `match` without `default` must handle every failure the `try` block can raise (compile error EK4701), so a complete match needs no rethrow. `error is ItemMissing` tests one class in an `if`. `Effect.catchTag` removes the selected tagged case, and accepts a nonempty array of tags for one handler; `Effect.catchTags` takes a table of separate handlers.

```vibe
function withTagTable(input: string) {
  return Effect.catchTags(() => findItem(input), {
    InvalidCode: () => ({ code: "", label: "Enter a code" }),
    ItemMissing: (error) => ({ code: error.code, label: "Out of catalog" })
  })
}

function withFilter(input: string) {
  return Effect.catchFilter(
    () => findItem(input),
    Filter.tagged("ItemMissing"),
    (error) => ({ code: error.code, label: "Out of catalog" })
  )
}

function withPredicate(input: string) {
  return Effect.catchIf(
    () => findItem(input),
    (error) => error is ItemMissing,
    () => ({ code: "", label: "Out of catalog" })
  )
}
```

```text
Enter a code
Out of catalog
Out of catalog
InvalidCode
InvalidCode
```

`catchIf` selects errors with a predicate or type guard; `catchFilter`, with reusable selection logic from `Filter`. A narrowing filter removes the handled subtype; a boolean condition that handles only some values can't promise the whole subtype is gone.

## Filtering nested reasons

```vibe
error Busy { seconds: number }
error Rejected
error CatalogError {
  reason: Busy | Rejected
}

function remoteLabel(): string!CatalogError! {
  throw new CatalogError({ reason: new Busy({ seconds: 4 }) })
}

function explainBusy() {
  return Effect.catchReason(
    () => remoteLabel(), "CatalogError", "Busy",
    (reason) => `Try again in ${reason.seconds} seconds`
  )
}

function explainReasons() {
  return Effect.catchReasons(() => remoteLabel(), "CatalogError", {
    Busy: (reason) => `Wait ${reason.seconds} seconds`,
    Rejected: () => "Request rejected"
  })
}

function exposeReasons() {
  return Effect.unwrapReason(() => remoteLabel(), "CatalogError")
}
// string!Busy | Rejected!
```

```text
Try again in 4 seconds
Wait 4 seconds
Busy
```

These operators inspect the tagged error's readonly `reason` field. `catchReason` keeps the parent wrapper for unhandled reasons; `catchReasons` selects several at once; `unwrapReason` replaces the wrapper in `E` with its nested reason, without recovering.

## Errors are classes

```vibe
/** The base of a family: each subclass carries its own tag. */
error AppError {
  _tag: string
  code: string
}
error Missing extends AppError { path: string }
error Expired extends AppError

function raise(error: Missing | Expired): never!(Missing | Expired) {
  throw error
}

function describeFailure(error: Missing | Expired) {
  return Effect.catchTags(() => raise(error), {
    Missing: (missing) => `missing ${missing.path}`,
    Expired: (expired) => `expired ${expired.code}`
  })
}
// string!!

error Normalized {
  code: string
  static readonly docs = "https://example.com/codes"

  constructor(input: string) {
    super({ code: input.trim().toUpperCase() })
  }

  get label(): string {
    return `${this._tag} ${this.code}`
  }
}
```

```text
missing /a
expired E2
true
Normalized PEN
```

An `error` declaration is a named class. The keyword supplies its base and its tag; every other class feature keeps its TypeScript meaning: `abstract`, `extends` another error, `implements`, a constructor that calls `super`, methods, accessors, `override`, and static and private members. A field is a property written with a type and no initializer, and as in a class body, `;` or a new line ends it: a comma between fields is EK1013, whose quick fix writes `;`. A field is readonly, and the constructor takes it: a declaration without a constructor takes its fields as one object, and a constructor passes them to `super`.

Every error class is tagged with its own bare name, a subclass included, so `catchTag("Missing")` and `catchTags` route each subclass, while `is AppError` and a `when AppError:` arm match the whole family by class. Because a value of the base's type may be a subclass, the base of a family declares its tag type with a `_tag` field, `_tag: string`, and `catchTag("AppError")` then matches only instances of the base itself. An `abstract error` has that tag type without the field. A subclass whose base keeps the literal tag `"AppError"`, a `_tag` field whose type leaves out its error's own name, or an error that extends a class that is not an error, is EK2117. A subclass that declares fields and no constructor takes its base's fields and its own, as `new Missing({ code, path })` does; when the base's constructor takes other arguments, the subclass writes a constructor that calls `super` and sets its fields (EK2118).

## Errors that encode

```vibe
schema error StoreError {
  _tag: string
  key: string
}
schema error NotStored extends StoreError { attempts: number }
```

```text
{"_tag":"NotStored","key":"a","attempts":2}
true
```

`schema error` declares an error whose fields are schemas, so it encodes and decodes. It is short for `class StoreError extends Schema.TaggedError<StoreError>()("StoreError", { key: Schema.String })`: each field's type maps to a schema as a `schema` declaration's fields do, and a field whose type has no schema, such as a function, is EK2109, which names the field. The class rules above apply. A subclass extends another schema error with `Base.extend`, so its schema holds the base's fields and its own, and its own tag. A family's base schema accepts its subclasses: it encodes each instance with its class's schema and decodes by tag. Use `error` for a failure nothing encodes.

## Coming from Effect

Functions replace `Effect.gen`; calls run the callee. Where it runs, `Effect.fail(error)` draws EK4834, whose quick fix writes `throw error`, and `Effect.catchTag(program, "Tag", handler)` draws EK4835, whose quick fix writes `program catch (e) => match (e) { … }` ([TypeScript-style Effect code](/getting-started/012-devtools#typescript-style-effect-code)). Pass a program such as `() => findItem(input)` when a recovery operator needs work it can control.
